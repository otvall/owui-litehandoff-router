# Установка OWUI Lite Handoff Router

Целевые версии — **Open WebUI 0.12.3 и 0.11.1**, Python 3.11/3.12. Каждой
версии нужен свой комплект Functions с точной проверкой версии. Окружение,
зависимости и модели подготовьте до переноса в закрытый контур.
Для работы комплект использует только стандартную библиотеку и установленный OWUI.

## Inline Visualizer в дочернем выполнении

Этот раздел относится к комплекту 0.12.3 с параллельными заданиями.

Используйте согласованные Tool **2.2.3** и Skill из
[`bcc224db138b6901a8d4b99e7f8a8859bea5629b`](https://github.com/Classic298/open-webui-plugins/tree/bcc224db138b6901a8d4b99e7f8a8859bea5629b/inline-visualizer-v2).
Локальные исходники, лицензия, URLs и SHA-256 находятся в
[manifest](../tools/fixtures/inline_visualizer/manifest.json). Подготовьте их
до переноса в закрытый контур. Прикрепите Tool/Skill только к нужной Workspace
Model агента; Router и другие агенты их не требуют. Владельцу модели должны
быть доступны оба ресурса.

Перед ручным обновлением сохраните content старых Tool/Skill, их IDs,
attachments, access grants и Valves. Обновляйте существующие записи с сохранением
IDs; проверьте attachments после обновления. Опубликованная функция Tool 2.2.3 —
**`visualize`**, вместо прежней `render_visualization` версии 2.1.1. Обновите
также содержимое связанного Skill. Его ID может отличаться от upstream имени
`visualize`: модель читает Skill по фактическому разрешённому ID перед Tool.

В Settings → Interface пользователь явно проверяет **iframe Sandbox Allow
Scripts** и **iframe Sandbox Allow Same Origin**. Same-origin нужен observer
плагина для чтения окружающего дочернего сообщения; Router его не включает.
Для локального SVG/HTML без внешних библиотек проверены Valves
`security_level=offline`, `chime=false`. Valve `offline` отсутствует в 2.1.1.

Контроль: запустите минимум два параллельных задания, одно с Visualizer.
Оставьте основной чат открытым до завершения группы. В карточке source агента
нажмите «Открыть выполнение»: SVG должен отрисоваться без loader, кнопка —
менять состояние. Повторите после reload и в другой своей сессии. Backend
успех и наличие `embeds` отдельно не доказывают интерактивность.
Команды стенда — [tools/README.md](../tools/README.md).

Rollback восстанавливает сохранённые Tool/Skill/Valves и прежние IDs/attachments;
дочерние чаты и связи сохраняются. Если менялись Functions, восстанавливайте
прежнюю согласованную пару exports. В этом change runtime Router не меняется.
Возврат к неизменённому 2.1.1 возвращает известное ожидание browser `execute`
из ещё не открытого дочернего чата и не является совместимым обходом.
Автоматического обновления плагина в пользовательской установке нет.

## Два установочных файла

В checkout выполните:

```sh
python3 tools/build_functions.py
python3 tools/build_functions.py --owui-version 0.11.1
```

Импортируйте `dist/router_preparation.py` как Filter Function,
`dist/lite_handoff_router.py` как Pipe Function. Активируйте обе Functions.
`lite_delegate` встроен в Pipe; отдельный Workspace Tool устанавливать не нужно.
После импорта исходники проекта на сервере не нужны. Сборка не скачивает пакеты.

Первая команда собирает 0.12.3 в прежний `dist/`, вторая — 0.11.1 в
`dist/owui-0.11.1/`. В каждой директории используйте только свою пару
`router_preparation.py` / `lite_handoff_router.py`. Заголовки legacy Functions
содержат `OWUI 0.11.1`; runtime обеих Functions проверяет точное совпадение.
Обновление не требует установки Python-пакета Router, переноса или downgrade
БД. Перед заменой сохраните обе Functions, Valves, `AGENTS` и metadata моделей.
Для rollback остановите активные запросы и восстановите согласованную пару
своей версии с её настройками. Общие файлы terminal backend не удаляйте.

В административных Valves Pipe укажите `orchestrator_model_id` — ID настоящей
локальной LLM Router, поддерживающей native function calling. Сам Pipe
в качестве LLM указывать нельзя.

Создайте публичную Workspace Model Router на базе этого Pipe. Прикрепите к ней
Router Preparation: обязательный Filter, без toggle и с выключенным Global.
Системный промпт и параметры Router задайте в его Workspace Model.
Поля **Tools и Skills в карточке Router оставьте пустыми**.

В административных Valves **Router Preparation** задаются базовые ресурсы:

```json
{
  "base_tool_ids": [],
  "base_skill_ids": []
}
```

Это значения по умолчанию. Можно добавить свои базовые Tools и Skills.
При непустом персональном реестре Pipe сам создаёт `lite_delegate` со схемой
и callable текущего запроса. Его ID в `base_tool_ids` указывать не нужно.
Filter заранее создаёт общий реестр, а Pipe обновляет его in-place для
штатного исполнителя OWUI; отправки одной схемы в LLM недостаточно.
UserValves и клиентские списки ресурсов этот набор не задают.
Подключения выполняются на сервере; базовые IDs не записываются в выбранные
пользователем ресурсы чата. Реальные вызовы видны в истории ответа.

## Первый агент и routing Skill

В OWUI 0.11.1 создавайте native текстовый Skill через Workspace → Skills.
Его `content` содержит инструкции; файловый пакет не требуется. Например:

```json
{
  "id": "route-a",
  "name": "route-profile-a",
  "description": "Вопросы по профилю A",
  "content": "Прочитай профиль. Для вопросов по профилю A вызови отдельный lite_delegate(agent_id=\"agent-a\")."
}
```

Для рабочего Skill используйте отдельный ID, например `a-working-guide`,
и прикрепите его к `meta.skillIds` агента. Формат `AGENTS`, `base_skill_ids`
и attachments одинаков в обоих комплектах. Владельцу Router нужен доступ к
routing Skill, владельцу агента — к рабочему. Пользователю достаточно доступа
к моделям: прямые grants на приватные Skills/Tools ему не выдаются.

Комплект 0.11.1 публикует только `view_skill(id)`. В инструкции ниже упоминания
`lite_parallel` относятся исключительно к 0.12.3; не включайте их в routing
Skill 0.11.1. Общий обычный handoff работает в том же чате в обеих версиях.

Используйте существующую активную Workspace Model, например `agent-a`,
с собственной базовой LLM, промптом и параметрами. Её LLM также должна
поддерживать native Tools. В карточке агента прикрепите его рабочие Tools/Skills.
Отдельный preparation Filter агенту не нужен.

Создайте Skill с ID `route-a`, именем `route-profile-a` и описанием
«Вопросы по профилю A». Минимальные инструкции:

```markdown
# Профиль A

Используй для вопросов по профилю A.
Передай текущий запрос настоящим отдельным вызовом
lite_delegate(agent_id="agent-a").
Не запускай другие Tools одновременно с передачей.
Для независимой части составной задачи можно вызвать lite_parallel:
передай agent_id="agent-a" и точное задание в поле task одного элемента tasks.
Всю группу вызывай отдельно от чтения Skills и других Tools.
```

В конфигурационной секции установленного **Router Preparation** задайте:

```python
AGENTS: dict[str, str] = {
    "agent-a": "route-a",
}
```

Слева — точный Workspace Model ID, справа — существующий routing Skill ID.
В `base_skill_ids` этот routing Skill добавлять не нужно. Router получит его
из персонального каталога. Полезная инструкция в системном промпте Router:
«Отвечай на общие вопросы самостоятельно. Для профильной задачи прочитай
подходящий routing Skill и вызови lite_delegate с его точным agent_id».

## Параллельные задания

Preparation Valves: `max_parallel_tasks=4`, `parallel_timeout_seconds=300`.
Предел `0` отключает `lite_parallel`; остальные допустимые значения — целые
от двух. Timeout — положительное целое число секунд. Это административные
настройки; UserValves и поля клиентского запроса их не переопределяют.
В OWUI включите `subagents.enable`, сохранённый основной чат и поддерживаемый
режим Tools approval `full`. При необходимости пауз `ask` группа недоступна:
роутер сообщает причину, а требования подтверждения не меняются.

Оба управляющих Tools встроены в Pipe, используют один персональный реестр
и регистрируются для native middleware автоматически. Карточка Router может
иметь пустые Tools/Skills. Имена `lite_parallel`, `lite_delegate` и
`delegate_task` зарезервированы; не подключайте одноимённые рабочие Tools.

Пример отдельного вызова Router:

```json
{"tasks":[{"agent_id":"agent-a","task":"Составь прогноз по сфере A"},
          {"agent_id":"agent-b","task":"Составь прогноз по сфере B","file_ids":[]}]}
```

Это аргументы `lite_parallel`, а не новый тип сообщения. Каждое задание
содержит только `agent_id`, `task` и необязательные `file_ids` доступных входных
вложений OWUI. Повторение агента разрешено. Весь список проверяется до запуска.
Разрешена одна группа на текущий пользовательский запрос. Вызов должен быть
единственным Tool call фактической генерации; после его результата Router
может отдельной генерацией вызвать `lite_delegate(agent_id="agent-c")` либо
ответить сам. При неполном исходе группы handoff блокируется до нового запроса.

Дополнение к системной инструкции Router:
«Независимые задания выполни одной группой lite_parallel. Дождись всех исходов.
После полного успеха при необходимости передай финальную задачу подходящему
агенту отдельным lite_delegate. Результаты группы уже будут его входными данными.
При ошибках сообщи доступные результаты и причины. Не повторяй действия сам».

Работники используют свои Tools/Skills/параметры и не получают управляющих
Tools. Следующее сообщение снова начинает обычный цикл Router.

## Как посмотреть выполнение задания

1. В основном ответе раскройте источники. Карточки подписаны номером задания
   и агентом; два задания одного агента имеют разные карточки.
2. Нажмите нужную карточку, затем ссылку **«Открыть выполнение»**.
3. В открывшемся чате раскройте **«Показать/скрыть подробности»**, чтобы увидеть
   сохранённые вызовы Tools и результаты. Там же доступны итог и файлы задания.
4. Вернитесь кнопкой Back браузера в основной чат.

Ссылки доступны и во время выполнения, и после Stop/reload. Просмотр не
перезапускает работу. Дочерние чаты остаются скрытыми из обычной истории,
поиска и папок. Доступ к чатам и файлам определяется правами OWUI. При открытии
удалённого выполнения OWUI возвращает на главную без уведомления; работа не
запускается повторно. Несохранённые внутренние рассуждения модели не показываются.

## Группы и скрытие агентов

Предоставьте группам read-доступ к публичному Router, моделям агентов и всей
цепочке их базовых моделей. В v0.12.3 незарегистрированная базовая модель
доступна только администратору: при настройке обычных пользователей создайте
для базовых моделей записи и выдайте необходимые read-grants.
Индивидуальные разрешения и унаследованные группы проверяются штатно.

Отдельные read-grants пользователям на Tools, Skills и MCP-подключения не нужны.
Базовые ресурсы из Valves и routing Skills загружаются с правами владельца
публичной Router Workspace Model. Рабочие ресурсы агента — с правами владельца
его Workspace Model. Владельцу должны быть доступны соответствующие ресурсы;
при отсутствии владельца или обязательного ресурса подготовка завершается ошибкой.
Права пользователя на модели проверяются отдельно, в том числе перед запуском.
Вызов через модель не выдаёт grants на её ресурсы для прямого чтения или
самостоятельного подключения. Нужные права владельцу можно выдать группой или
индивидуально; права на ресурс другого владельца не возникают автоматически.
Отдельного read-grant на встроенный `lite_delegate` нет: Pipe проверяет
своё доверенное состояние запроса и заново проверяет доступ к адресату.
Редактировать Functions, административные Valves и карточки должен администратор.

Сделайте агентов активными и установите в их metadata `hidden=true`.
Публичный Router оставьте видимым и при необходимости выберите моделью
по умолчанию. `hidden` скрывает модель в штатном селекторе;
это не запрет прямых API-вызовов. Скрытый агент с действующими правами
остаётся в персональном реестре. Проверяйте результат от имени участников
разных групп, а не только администратора.

На каждом новом сообщении реестр строится заново. Отсутствующий, неактивный
или нечитаемый владельцу Router routing Skill исключает адресата с диагностикой
в журнале. Отсутствие read-grant пользователя на Skill адресата не исключает.
Перед handoff доступ проверяется повторно: отзыв прав после публикации
манифеста не разрешает запуск по прежнему `enum`. `lite_delegate` принимает
именно Model ID, никогда Skill ID или имя базовой LLM.

Единственный аргумент `lite_delegate` — `agent_id`. Задача и контекст берутся
из текущего чата. Если модель всё же добавила `task` или другое лишнее поле,
штатный исполнитель OWUI игнорирует его; роутер проверяет оставшиеся аргументы
и сохраняет исходный вызов в истории. Содержимое лишнего `task` не заменяет
пользовательский запрос. Несколько Tool calls в одном ответе LLM по-прежнему
блокируют передачу.

## Рабочие ресурсы и MCP

Для агента A выбирайте рабочие Tools и Skills **в карточке A**. Для B — в
карточке B. Эти наборы заменяют возможности Router при handoff. Рабочие IDs
не нужно копировать в `AGENTS` или прикреплять preparation Filter к агентам.
Недоступный обязательный ресурс приводит к ошибке подготовки целиком.

Настройте MCP как серверное подключение OWUI с типом `mcp`, активным
`config.enable` и собственным `info.id`, например `internal-a`. Разрешите это
подключение владельцу модели или его группе. В `toolIds` модели используйте
нативный ID `server:mcp:internal-a`. Для базового MCP Router такой ID задаётся
в административном `base_tool_ids`.

```json
{
  "toolIds": ["a_lookup", "server:mcp:internal-a"],
  "skillIds": ["a-working-guide"]
}
```

Это пример metadata агента, а не параметров пользовательского запроса.
ACL подключения проверяется от владельца модели. Для пользовательского OAuth,
session auth и заголовков идентификации используется пользователь текущего
запроса. Отсутствие его обязательного OAuth возвращает ошибку без подстановки
токена владельца. Общий bearer key остаётся серверной настройкой подключения.
У каждого локального Tool сохраняются его собственные административные Valves
и UserValves пользователя исполнения. Через эти UserValves нельзя изменить
базовые списки Router или attachments модели.

MCP-сессия принадлежит запросу, пользователю исполнения и выбранной модели/владельцу. Её открытие,
вызовы и закрытие выполняются в одной задаче SDK; native Tool-продолжения
используют ту же сессию. Доступ повторно проверяется при подготовке и вызове.
Смена владельца или отсоединение ресурса останавливают старый callable.
Ресурсы другого агента не добавляются по его прежнему присутствию в чате.

## Терминал у выбранных агентов

Этот binding поддерживается обоими комплектами. В 0.11.1 используются его
штатные transport/context helpers и только основной chat ID, без child tasks.

По умолчанию терминал выключен у всех агентов. Для выбранного агента задайте
в **его серверной metadata** ID уже настроенного подключения из раздела
терминалов OWUI:

```json
{
  "toolIds": ["a_lookup"],
  "skillIds": ["a-working-guide"],
  "capabilities": {"terminal": true},
  "lite_handoff": {"terminal_id": "internal-analysis"}
}
```

Это фрагмент `meta` Workspace Model, а не тело пользовательского запроса.
Для остальных агентов поле не добавляйте. Отсутствующее поле, `null` или пустая
строка отключают терминал; неверный тип вызывает ошибку. Непустая привязка
при `capabilities.terminal=false` также вызывает ошибку. Один флаг Terminal
без `lite_handoff.terminal_id` терминал не подключает. Публичный Router остаётся
без терминала.

Штатный редактор OWUI не содержит отдельного поля этой привязки. Администратор
может экспортировать Workspace Model, добавить `lite_handoff` в её `meta`
и сохранить модель штатным импортом JSON либо API обновления модели. Сохраняйте
Model ID, остальные metadata, параметры и grants; не заменяйте весь объект
приведённым фрагментом. После сохранения повторно экспортируйте модель и
проверьте наличие поля. OWUI 0.12.3 и 0.11.1 сохраняют дополнительные поля `ModelMeta`;
миграция БД не требуется. `AGENTS` менять не нужно.

Подключение должно быть доступно владельцу Workspace Model. Прямой grant
пользователю чата не требуется и автоматически не выдаётся. Несколько выбранных
агентов могут использовать один ID подключения.

После обновления двух Functions:

1. Проверьте ID, активность и ACL существующего серверного подключения.
2. Сохраните привязку только у выбранной модели и выполните обычный handoff
   или параллельное задание. Её Tools подключаются автоматически.
3. Для отключения удалите привязку либо установите `null`. Следующая подготовка
   не подключит терминал, а старый callable уже не сможет отправить команду.

Выбор терминала в поле ввода родительского чата не влияет на привязку агента.
Переключение на агента без привязки и новое сообщение Router убирают активные
терминальные Tools и серверные инструкции. Для управления командами не нужно
открывать терминальную панель. Прямой вызов модели в обход Router не использует
эту подготовку. Серверные Tools, требующие интерактивной панели пользователя,
не подключаются.

Поддерживаемая поверхность: промпт и inference-параметры Workspace Model,
локальные/штатные серверные Tools, серверный MCP, Skills, необязательный серверный
терминал выбранного агента и дополнительные
inlet-фильтры адресата. Actions, произвольные outlet/stream-фильтры адресата,
интерактивная терминальная панель, вложенные группы и фоновое возобновление
в комплект не входят. Прямой доступ к terminal file downloads не выдаётся;
терминальный путь не становится автоматически обычным OWUI вложением.

Терминальные запросы используют штатный `X-Session-Id` по chat ID: при обычном
и финальном handoff — основной чат, в параллельном задании — его дочерний чат.
Два задания одному агенту получают разные дочерние IDs. Для orchestrator
`X-Terminal-Context-Id` вычисляется штатной политикой подключения. Router не
создаёт отдельные среды и не меняет сохранение файлов/cwd. Подключение с общей
средой может разделять filesystem между агентами и пользователями; разделение
callables и chat IDs этого не меняет.

Stop и deadline отменяют локальное ожидание и дальнейшие команды задачи,
не запускают C и не повторяют команду. Уже переданный терминальному backend
процесс может продолжаться по правилам этого backend. Общий сервер и его
файлы при остановке Router не удаляются.

Результаты команд передаются текстом. Входные OWUI вложения автоматически не
копируются в filesystem терминала. Для передачи артефакта следующему агенту
по-прежнему нужен обычный OWUI file ID, доступный пользователю исполнения.
Путь `/tmp/result.csv` или запись `source=open_terminal` таким ID не является:
непригодное файловое вложение даёт явную ошибку и не считается успешной группой.
Терминальный download endpoint не открывается правами владельца модели.
Обычный внешний цикл Router сохраняется в OWUI; код сервера и схема БД
комплектом не меняются.

Задайте `function_calling=native` в настройках Router. Preparation закрепляет
native режим для запроса; legacy не поддерживается. Отключите автоматическое
сжатие контекста OWUI (`chat.context_compaction.enable=false`): комплект
рассчитан на полную историю без автоматического пересказа. При включённом
сжатии Pipe возвращает ошибку настройки. Представления истории и ограничения
описаны в [context.md](context.md).

## Проверка первого сценария

1. Задайте общий вопрос: отвечает Router без отдельного классификатора.
2. Задайте вопрос профиля A: Router читает `route-a` и вызывает
   `lite_delegate(agent_id="agent-a")`.
3. Агент выполняет свой локальный Tool, получает результат и отвечает в том же
   чате и том же сообщении. Router после него не пересказывает ответ.
4. Отправьте новый вопрос: решение снова принимает Router.

Воспроизводимый автоматический вариант пункта 3:

```sh
.venv/bin/python tools/run_native_tests.py --owui-version 0.12.3
```

Тест `tests/native/test_chain.py` загружает два exports настоящими загрузчиками
OWUI, создаёт ресурсы в отдельной БД и проходит штатный streaming Tool loop.
Тестовый провайдер заменяет транспорт генерации и браузерную доставку событий.
Он проверяет инфраструктуру исполнения; качество маршрутизации настоящей LLM
проверяется отдельно. Состояние браузерной приёмки фиксируется в `acceptance.md`.

## Обновление и откат

Перед заменой файлов сохраните текущие exports, словарь `AGENTS` и Valves.
Обновите оба файла как один комплект и восстановите конфигурацию.
Для отката импортируйте сохранённые версии и верните их Valves/словарь.
Удалять чаты, модели и Skills для отката не требуется.

При переходе с исходного комплекта из трёх файлов удалите ID отдельного
delegate Tool из **сохранённых** `base_tool_ids`: новый default сам по себе
не перезаписывает существующие Valves OWUI. Остальные базовые IDs сохраните.
Старый Workspace Tool больше не используется и может быть удалён после
проверки обновления. Его метод `lite_delegate` не должен попадать в базовый набор:
коллизия с зарезервированным встроенным Tool вызывает ошибку подготовки.
Для отката к исходному комплекту восстановите также старый Tool и его read-grants.


## Серверные подключения в 0.11.1

Для OpenAPI используйте native server ID в `toolIds`, например
`server:openapi:internal-a|lookup`; subset не расширяет фильтр функций
подключения. Для MCP — `server:mcp:internal-a`. Настройте enable и ACL
подключения для owner модели, не выдавая actor прямой grant.

Native 0.11.1 использует `ENABLE_PLUGINS`. Bearer берёт ключ подключения,
session — текущие token/cookies, system OAuth — token actor из middleware,
`none` не добавляет auth. OAuth 2.1 для OpenAPI/MCP получает token actor из
native manager. Требуемая отсутствующая пользовательская авторизация
останавливает подготовку; сохранённая client metadata её не заменяет.
У terminal поддержаны bearer/session/system OAuth/none. В 0.11.1 cookies
передаются только в session/system OAuth, независимо от `forward_cookies`.
Режимы и границы native/synthetic auth-проверок — в [compatibility.md](compatibility.md).

Terminal binding, контекст сессий, Stop, общий filesystem и требование обычных
OWUI file IDs описаны выше и применяются к обеим версиям. В 0.11.1 используйте
`display_file(..., inline=true)`, если нужен native inline file result;
это не предоставляет пользователю прямой download grant терминального сервера.
