# Передача контекста для GLM-5.3-Flash

Исследование от 20 ноября 2026 года для Lite Handoff Router и последовательности `Router → A → Router → B`. Проверены исходники проекта, документация Z.ai и сериализация в официальном шаблоне открытых весов. Рекомендации по поведению модели ниже требуют прогона на целевом провайдере.

## Рекомендация

**Собственные вызовы и результаты оставлять нативными. Агенту передавать выбранные итоги чужой работы одним предзагруженным пакетом по образцу каталога Skills.** Основной кандидат для этого проекта — служебная пара `list_handoff_results` в модельной копии истории. Полезную нагрузку составляют точные данные с автором, шагом и статусом. Большой результат передаётся доступным артефактом или запрашивается через реальный инструмент чтения. Для Router после возврата агента тот же подтверждённый итог можно показать в модельном представлении собственного `lite_delegate`, сохранив серверный receipt для подтверждения перехода. [Каталог Skills](context.md#пример-третьего-запроса-router) · [Текущая проекция Router](../src/lite_handoff_router/history.py#L156)

Для агентского запроса это развивает подход, который уже использует `delegate_task`. В нём данные группы передаются как служебное сообщение, а история агента строится отдельно. Для исторического обзора Router можно сохранить текущую хронологию и компактное содержимое результата его собственного `lite_delegate`. Записи о работе других агентов из обзора можно выбирать для адресного обмена по правилам запланированного `add-handoff-data-transfer`. [Контекст агента](../src/lite_handoff_router/history.py#L369) · [Пакет группы](../src/lite_handoff_router/parallel.py#L414) · [Обзор Router](../src/lite_handoff_router/history.py#L156) · [Дизайн исторического обмена](../openspec/changes/add-handoff-data-transfer/design.md)

## Что подтверждено для GLM-5.3-Flash

- Открытый шаблон кодирует `user` маркером пользователя, а результаты инструментов — как наблюдения. Исторические вызовы из `assistant.tool_calls` он печатает даже при отсутствии одноимённой схемы в текущем `tools`. Поэтому чужой `lite_delegate` будет выглядеть как предыдущий вызов модели. Исполнимые инструменты по-прежнему определяет серверный реестр. Документация Z.ai описывает `role=tool` как ответ на фактически сгенерированный вызов с совпадающим `tool_call_id`. [Шаблон](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/main/chat_template.jinja) · [Z.ai Function Calling](https://docs.z.ai/guides/capabilities/function-calling) · [Публикация реестра](../src/lite_handoff_router/runtime.py#L80)
- При `clear_thinking=true` проверенный шаблон оставляет переданные блоки размышлений после последнего сообщения с ролью `user`. Поиск границы смотрит на роль, включая служебное сообщение с этой ролью. В Jinja можно передать параметры шаблона напрямую. Для опубликованного OpenAI-совместимого API Z.ai соответствующий документированный параметр называется `thinking.clear_thinking`. Путь передачи настройки через конкретный self-hosted сервер или посредник нужно проверить отдельно. [Шаблон](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/main/chat_template.jinja) · [Z.ai Chat Completion](https://docs.z.ai/api-reference/llm/chat-completion)
- У публичного шаблона по умолчанию `clear_thinking=false`, а карточка весов советует явно задавать `true` для чата. Общий API-справочник Z.ai приводит default `true`. Документация самой модели для hosted API рекомендует `false`, а справочник требует для такого режима полный, неизменённый и правильно упорядоченный исторический `reasoning_content`. Для пересобранной истории Router сохранение чужих размышлений через границу исполнителей не требуется. Собственный `reasoning_content` уместен в полном раунде инструментов того же исполнителя, если провайдер его поддерживает. Переключение одного параметра может оставить чужой блок, если тот расположен после того же пользовательского вопроса. [Карточка весов](https://huggingface.co/zai-org/GLM-5.3-Flash#note) · [Рекомендации hosted API](https://docs.z.ai/guides/vlm/glm-5.3-flash) · [Семантика API](https://docs.z.ai/api-reference/llm/chat-completion) · [Текущая фильтрация reasoning](../src/lite_handoff_router/history.py#L123)

### Локальная проверка сериализации

Jinja 3.1.6, ранее сохранённая копия официального шаблона, SHA-256 `2614a3c896d53e265f564c23701173c0049f985dacfbae79fc4bcd9f5ba083f4`. Способ преобразования совпадает с ранее задокументированной проверкой проекта. Проверенные ветви присутствуют в просмотренной версии `main`. Байтовое совпадение этой копии с `main` не устанавливалось. [Предыдущий прогон](tool-history-context-validation.md#сериализация-glm) · [Текущий шаблон](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/main/chat_template.jinja)

| Вариант входа | Что получилось |
| --- | --- |
| Служебный `user` перед исходным вопросом | Два маркера пользователя. Размышление из собственной Tool-пары после вопроса присутствует при обоих значениях `clear_thinking`. |
| Служебный `user` после собственной Tool-пары | При `clear_thinking=true` размышление пары исчезает. При default локального шаблона остаётся. |
| Историческая пара с чужим `lite_delegate` | Имя вызова видимо, даже если нет в `tools`. Чужое размышление из более раннего хода сохраняется при default и исчезает при `clear_thinking=true`. |
| Настоящее чтение результата инструментом получателя | Вызов и наблюдение видны после вопроса. Смежные результаты параллельных вызовов помещаются в один блок наблюдения и упорядочиваются по порядку вызовов при однозначных IDs. Имена из полей `assistant.name` и `tool.name`, как и сами `tool_call_id`, в текст не выводятся. |
| Отдельный `developer`, `system` или осиротевший `tool` | Первый текст исчезает из этого шаблона, второй рендерится как системное сообщение. Шаблон способен показать осиротевшее наблюдение, но оно расходится с документированным контрактом пар. |

В HTTP payload аргументы транспортируются в JSON-строке, а для прямого рендера Jinja их предварительно разбирали в объект. При прямой передаче строки шаблон пытался вызвать у неё `.items()`. В приложении control tags формирует шаблон провайдера. Проверка сериализации не измеряет, как часто модель копирует чужой вызов или следует метке входных данных. Например, у vLLM есть нативный Rust-рендерер GLM5Next и отдельный маршрут с Hugging Face через Python. Для проверки на живой модели нужно зафиксировать фактический рендерер и маршрут. [Z.ai Function Calling](https://docs.z.ai/guides/capabilities/function-calling) · [vLLM GLM-5.3-Flash](https://recipes.vllm.ai/zai-org/GLM-5.3-Flash) · [Предыдущий прогон](tool-history-context-validation.md#сериализация-glm)

## История работы других агентов

Для нового агента полезна история результатов. Сохранять видимую переписку и подписывать опубликованные ответы, когда сервер установил автора. В пакет отбирать относящиеся к текущему шагу подтверждённые выводы, принятые решения, точные значения и ссылки на артефакты. Неудачные попытки имеют смысл, если меняют следующий шаг, например первый источник не дал данных и его повторный запрос бесполезен. Статусы источника и этапа нужно сохранять явно. Если актуальность результата зависит от версии или периода, указывать их рядом с данными.

Сырые Tool-вызовы, служебные аргументы, инструкции и reasoning чужого исполнителя остаются в исходной трассе. В публикации использовать фактически видимый ответ. Удаление отдельного поля reasoning не очищает текст, если в `assistant.content` ещё лежит встроенный блок размышлений. Автора указывать в `content` или поле пакета. Доступность результата проверяется при сборке контекста. Сводка может объяснить, что выполнено, а точные значения берутся из разрешённого источника. [Проекция агента](../src/lite_handoff_router/history.py#L369) · [Шаблон GLM](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/main/chat_template.jinja) · [Запланированная проверка источника](../openspec/changes/add-handoff-data-transfer/design.md)

Похожие решения есть в других системах. OpenAI Agents SDK позволяет фильтровать ввод при handoff отдельно от сохранённой истории. Его готовый фильтр убирает структурированные Tool items, поэтому обычный текст и созданные из него сводки требуют собственной проверки содержимого. LangGraph Supervisor позволяет выбирать между полной историей и последним ответом, отдельно настраивая вход следующего агента и включение handoff-сообщений. Anthropic описывает короткие итоги подагентов и сохранение датасетов вне контекста координатора. Эти источники подтверждают практику отбора, а формат пары для GLM — рекомендация для этого проекта. [Agents SDK](https://openai.github.io/openai-agents-python/handoffs/) · [LangGraph Supervisor](https://github.com/langchain-ai/langgraph-supervisor-py#message-history-management) · [Anthropic Context Engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) · [Anthropic Multi-Agent Research System](https://www.anthropic.com/engineering/multi-agent-research-system)

### Проверка одноимённых инструментов

Повторили локальный рендер с тем же шаблоном и `clear_thinking=true`. A и B вызывали `lookup` с разными источниками в одном пользовательском ходе. Полный перенос вывел оба вызова `lookup` и reasoning обоих агентов. Вариант с предзагрузкой вывел один `lookup` B и один служебный вызов, сохранил результат A и reasoning B. Эффект сохранялся и при вставке пары после завершённого раунда B. Маркированный `user` перед вопросом сохранил reasoning B, а вставка после раунда B сдвинула границу и скрыла его. Значения пакета совпали во всех вариантах. Тест также подтвердил, что имя автора в `assistant.name` не попадает в текст, имя в `content` видно, а встроенное размышление в чужом `assistant.content` может появиться даже без поля `reasoning_content`. Это результаты сериализации, а частоту ошибочных действий GLM покажет сравнение ответов на одном маршруте. [Шаблон GLM](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/main/chat_template.jinja)

## Применение к Router и агентам

| Переход | Что получает адресат |
| --- | --- |
| Router → A | Исходный запрос, доступная переписка, назначенное действие, выбранные данные прошлых ходов, собственные разрешённые инструменты A. |
| A → Router | Краткое состояние плана и итог A в модельном представлении ответа на собственный `lite_delegate` Router. |
| Router → B | То же исходное пользовательское сообщение, действие для B и выбранные результаты A. К собственным результатам B применяются обычные правила видимости и продолжения. |
| B → B после инструмента | Одна предзагруженная пара и собственный вызов B со связанным результатом. Служебная пара строится при подготовке модельного контекста. |

Для компактного пакета достаточно источника, идентификатора шага, статуса, типа результата и данных или ссылки. Источник указывать прямо в содержимом пакета, чтобы он был виден модели. Фактическое авторство, подтверждение выполнения и право доступа проверяет сервер. Текст результата может содержать произвольные фразы, поэтому инструкция получателя объявляет пакет входными данными и отдельно задаёт ожидаемое действие. Для сценария с графиком передаются точные периоды, значения, единицы и, когда требуется сохранить оформление, декларативная спецификация графика либо доступный исходник. Ответ инструмента рендеринга может содержать только инструкции вывода. [Записанный сценарий с визуализацией](agent-context-example.md)

Пример входа в запросе B после system и видимой переписки. Служебная пара отсутствует в реестре callable и собирается по серверному состоянию.

```json
[
  {
    "role": "user",
    "content": "Добавь на график продаж ряд из CRM."
  },
  {
    "role": "assistant",
    "content": "",
    "tool_calls": [{"id":"ctx1","type":"function","function":{"name":"list_handoff_results","arguments":"{}"}}]
  },
  {
    "role": "tool",
    "tool_call_id": "ctx1",
    "content": "{\"results\":[{\"agent_id\":\"sales-agent\",\"step\":\"collect_sales\",\"status\":\"completed\",\"unit\":\"RUB\",\"series\":[{\"month\":\"2026-09\",\"value\":120000},{\"month\":\"2026-10\",\"value\":140000}],\"chart_ref\":\"chart-sales\"}]}"
  }
]
```

Для возврата внутри того же хода понадобится атрибуция по отдельным передачам. Текущий код закрепляет одного активного агента и строит историческое соответствие по пользовательскому ходу. В изолированной проверке проекции имитация возобновления Router внутри того же хода оставляет `lookup` агента отдельной нативной парой, а после нового пользовательского вопроса тот же результат вложен в исторический пакет `lite_delegate`. Проекция B исключает вызов A даже при совпадении имён инструментов. Это проверка функций проекции, поскольку сам возврат пока не реализован. При `A → Router → B` факт возврата и связанные результаты стоит привязать к серверной записи передачи, чтобы собирать данные A отдельно от внутренних вызовов. Список задач в UI отражает прогресс, а подтверждение шага берётся из выполненной операции. [Протокол](../src/lite_handoff_router/protocol.py#L92) · [Атрибуция](../src/lite_handoff_router/history.py#L52) · [Open WebUI Task Management](https://docs.openwebui.com/features/chat-conversations/chat-features/task-management/)

## Сравнение вариантов

- **Предзагруженная служебная пара.** Основной кандидат для небольших обязательных данных. Она сохраняет пользовательскую границу и даёт данным форму наблюдения. Сервер добавляет ровно одну пару после исходного вопроса перед первым собственным вызовом агента и воспроизводит её при продолжении. Системные инструкции получателя объясняют назначение пары. В живом тесте проверять, пытается ли модель вызвать её повторно. [Образец каталога Skills](../src/lite_handoff_router/skills.py#L91)
- **Один маркированный пакет перед вопросом.** Контрольный вариант для сравнения и запасной формат при несовместимости провайдера со служебной парой. Вставку привязывать к исходному пользовательскому вопросу, учитывая служебное сообщение OWUI с изображением результата. [Распознавание сообщений с изображениями](../src/lite_handoff_router/protocol.py#L42)
- **Реальный инструмент чтения или штатный файл.** Подходит для больших и выборочных результатов, когда модель должна извлечь определённый срез. Если данные обязательны, Router передаёт разрешённую ссылку, а получатель явно читает её перед дальнейшим действием. Инструмент добавляет генерацию и возможность пропуска чтения. Сервер проверяет область ссылки и доступ пользователя. Штатная перепроверка файлов уже реализована для результата группы. [Проверка файлов](../src/lite_handoff_router/parallel.py#L414)
- **Историческая пара с `lite_delegate`.** Полезна в Router как запись о его собственном действии. В агентском payload тот же формат показывает чужую операцию как вызов в роли `assistant`. Для чужих результатов в этом варианте остаются вопросы точности атрибуции и поведения модели.

## Как решить по результатам пилота

Сначала перехватить фактический provider payload для `Router → A → Router → B → B` на закреплённом маршруте. Проверить исходный вопрос, автора входных данных, сохранение пар по ID, отсутствие чужих схем и размышлений и одну копию пакета на генерацию. Отдельно проверить, что старые записи не восстанавливаются из скрытого результата и что файлы по ссылкам читаются с действующими правами.

Затем сравнить на одном маршруте, с одинаковой полезной нагрузкой, одинаковыми настройками и несколькими повторами, служебную пару и маркированный `user` перед вопросом. Основные критерии — правильный автор результата, точность значений и единиц, выбор следующего шага, повторное выполнение завершённого или заблокированного шага, попытка вызвать `list_handoff_results`, число генераций и объём входа. Контрольные случаи — два агента с одноимённым Tool, скрытый источник и продолжение B после собственного вызова. Реальное чтение по ссылке оценивать отдельно на больших данных. Проверки сериализации обосновывают выбор кандидата, а качество на живой GLM-5.3-Flash остаётся открытым.
