# Как Router использует профиль агента

Применяй этот контракт при составлении routing Skill для текущего комплекта
Lite Handoff Router. Он описывает исполнение Router; отдельный помощник
Routing Skill Authoring читает конфигурации с правом записи и сохраняет
Skills через свои Tools, а изменение реестра остаётся администратору.

## Выбор и доступ

На новом пользовательском сообщении Router заново строит доступный каталог
из серверного `AGENTS`: точный Workspace Model ID → routing Skill ID.
Учитываются актуальный доступ пользователя к модели, активность модели
и пригодность routing Skill для владельца Router. Передача в прошлом
сообщении не закрепляет агента за всем чатом.

В каталоге сначала видны имя и описание Skill; полный профиль Router читает
по `skill_id`. Поэтому описание должно отличать назначение от соседних
агентов. Вызов адресуется по `agent_id`, а не имени или ID Skill.
Профиль помогает выбрать исполнителя, но не выдаёт разрешений и не меняет
конфигурацию модели.

## Контекст исполнения

| Сценарий | Что получает исполнитель | Что учесть в профиле |
|---|---|---|
| Обычный handoff | Текущий пользовательский запрос и отфильтрованный контекст чата; собственные промпт, Tools и Skills модели | Какие задачи целиком относятся к этому агенту и какие данные требуют уточнения |
| Самостоятельное параллельное поручение | Только `task` и выбранные входные файлы; родительская переписка не передаётся | Какую независимую часть можно поручить и какие факты Router должен включить в неё |
| Финальный handoff после успешной группы | Контекст handoff плюс подтверждённые результаты с авторами и доступными файлами | Какую обработку уже готовых результатов выполняет этот агент |

При handoff чужие Tool exchanges и инструкции прочитанных чужих Skills
не становятся собственным рабочим контекстом агента. Перечисли необходимые
входные факты, а не рассчитывай на неограниченную передачу всей Tool-истории.
Параллельные задания независимы: одно не может ожидать результата другого
задания той же группы. Итоговые результаты передаются как данные, без Tools
и рабочих инструкций их авторов.

Если самостоятельное поручение или финальная обработка не входят в профиль,
прямо укажи это в соответствующем поле. Описанные роли — критерии выбора,
а не новые технические переключатели или разрешения. Общую организацию
группы и handoff определяет системный промпт Router. Вложенная передача
от агента другому агенту не поддерживается; требующий её процесс нужно
переформулировать в доступных границах.

## Ресурсы и полномочия

Router использует базовые ресурсы из своих Valves. Агент использует свои
прикреплённые Tools/Skills и привязанный к своей модели терминал; ресурсы
Router и других работников автоматически не наследуются. Routing Skill
не подменяет рабочий Skill и не обязан быть прикреплён к агенту.

Загрузка ресурсов проверяется по владельцу модели, а выполнение обычных
Tools и доступ к пользовательским данным сохраняют пользователя чата.
Возможность вызвать Tool не доказывает право изменить конфигурацию Router.
Для заявлений о поддержке и администрировании нужны реальные Tools
с проверкой прав на операции.

В текущем Pipe из штатных Skills Tools добавляются только три reader:
`view_skill`, `read_skill_file`, `grep_skill_files`. Создание/изменение Skills
и `execute_code` автоматически не добавляются. Для них нужна обычная
OWUI-модель с соответствующими builtin возможностями либо отдельно
подключённые подходящие Tools. Файл скрипта в Workspace Skill не исполняется
самостоятельно.
