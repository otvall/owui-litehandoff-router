# Создание routing Skill

Подготовь готовый `SKILL.md`, который помогает Router уверенно выбрать
конкретного агента. Routing Skill описывает, **когда нужен агент**, а рабочие
Skills и системный промпт его модели — **как агент выполняет задачу**.
Перед изучением возможностей прочти
[контракт исполнения Router](references/router-contract.md) из файлов этого
Skill через доступный штатный reader. Он нужен для различения handoff,
самостоятельного поручения и финальной обработки результатов.

## Исходные данные

Используй предоставленные настройки модели и описание пользователя. Нужны:

- точный Workspace Model ID и понятное имя агента;
- задачи, ради которых его выбирают, и ожидаемый результат;
- похожие запросы вне специализации этого агента;
- обязательные входные данные, самостоятельная часть составного запроса
  и допустимая обработка готовых результатов других агентов.

Для обновления прочитай существующий Skill и сохрани применимые ограничения.
Сделай профиль самодостаточным: опиши только возможности и границы своего
адресата. Негативные критерии объясняют, почему этот агент не подходит;
они не назначают другого исполнителя. В готовом профиле не должно быть
ссылок на конкретных других агентов, их имён/ID/Skills и указаний передать
неподходящий запрос им или оставить Router. Выбор дальнейшего действия
остаётся Router по актуальному каталогу. При обновлении существующего
профиля замени такие отсылки описанием ограничения самого адресата.
ID модели бери из достоверной конфигурации или ответа пользователя. Если ID
неизвестен, запроси его до выдачи готового к установке Skill; предварительный
текст с незаполненным ID обозначь как черновик.

## Изучение возможностей модели

До заполнения шаблона изучи назначение модели в своём системном промпте,
схемы всех доступных Tools и содержимое остальных доступных Skills.
`routing-skill-authoring` исключи из обзора: это средство подготовки профиля,
а не специализация, ради которой Router должен выбирать агента.

Skills читай через доступные штатные readers с фактическими ID из текущего
каталога. Если назначение или ограничения Skill вынесены в его файлы,
прочти соответствующие файлы. Возможности Tools определяй по их схемам,
описаниям и относящимся к ним инструкциям. Для такого обзора не требуется
запускать рабочие Tools или выполнять пользовательские операции.

Сопоставь заявленное назначение с доступными средствами: какие задачи модель
может решать, какие входные данные ей нужны и какой результат она выдаёт.
Доступность Tool сама по себе не делает все его возможности специализацией
агента; учитывай ограничения и приоритеты системного промпта. Недоступный
Skill или непроверенный доступ к внешним данным обозначь как ограничение
обзора. Не включай такие возможности в профиль как подтверждённые.

Такой обзор описывает текущую модель. Если routing Skill создаётся для
другой Workspace Model, используй её предоставленные настройки, промпт
и сведения о Tools/Skills. Не переноси возможности текущей модели на
другого агента; запроси недостающие сведения у автора.

Если подключён комплект Routing Skill Authoring, найди адресата через
`list_agent_models` и прочти `inspect_agent_model`. Его прикреплённые Skills
и нужные файлы читай через `read_agent_skill_file`, следуя страницам
`next_offset`. Эти Tools проверяют право записи на модель и собственные
права пользователя на ресурсы. Статусы недоступности и `limitations`
учитывай как ограничения обзора. При обновлении routing Skill получи
его актуальные текст и `version_id` через `inspect_routing_skill`.

## Уточнение границ с автором

По итогам обзора кратко сформулируй для автора предполагаемый профиль:
подходящие задачи, похожие запросы вне профиля, обязательные входные данные
и ожидаемый результат. Отдельно обозначь, какую часть можно поручить
независимо от других заданий и что агент делает с уже готовыми результатами.
Если такая роль не входит в профиль, явно укажи это, а не придумывай её.
Описывай выводы о возможностях; содержимое системного
промпта и полные инструкции других Skills в ответ переносить не нужно.
Отделяй подтверждённые настройки от предположений о желаемой специализации.

Обязательно уточни у автора позитивные и негативные примеры вопросов
и запросов. По итогам обзора предложи конкретные формулировки обоих типов:

- Позитивные: запросы, с которыми Router должен выбрать этого агента.
- Негативные: похожие запросы, с которыми этого агента выбирать не нужно;
  поясни ограничение его профиля без указания другого исполнителя.

Попроси автора подтвердить, исправить или дополнить оба набора и дождись
ответа перед окончательным Skill. Этот вопрос обязателен и при кажущемся
очевидным профиле. Если автор уже привёл примеры, включи их в уточнение.
Для завершения нужны подтверждённые автором примеры обоих типов;
самостоятельно придуманные примеры без ответа автора остаются черновиком.

Уточни границы применения, которые ещё не следуют из требований автора.
Если пробелов несколько, задай их одним сообщением — обычно 2–4 коротких
вопроса, выбирая только существенные для этого агента. Например:

- Какие из обнаруженных задач должны быть основной причиной выбора агента?
- Какие близкие запросы выходят за границы специализации этого агента?
- Какие данные обязательны, а при каких пробелах допустим результат с оговорками?
- Какой итог нужен пользователю: расчёт, объяснение, файл или действие через Tool?
- Какое поручение агент выполнит без родительской переписки и результатов соседнего задания?
- Какую финальную обработку готовых результатов он должен выполнять, если она нужна?

Привязывай вопросы к изученным возможностям и конкретным примерам запросов.
Остальные уже заданные автором границы используй без повторных вопросов. Если ответ
существенно меняет условия выбора, дождись его до выдачи окончательного
Skill; до этого можно показать явно обозначенный черновик. Требования
автора сверяй с фактическими возможностями и ограничениями системного
промпта: несоответствие объясни и предложи достижимую границу профиля.

## Шаблон

Перед составлением прочитай приложенный файл
[references/routing-skill-template.md](references/routing-skill-template.md).
В OWUI используй доступный штатный reader файлов Skills, например
`read_skill_file`, с фактическими ID текущего Skill и путём вложения из
его каталога. Если файл недоступен, сообщи об этом и попроси добавить шаблон
к этому Skill; не выдавай восстановленный по памяти текст за прочитанный.

Подготовь поля для скрипта без ручной подстановки в Markdown:

| JSON-поле | Поле шаблона / содержание |
|---|---|
| `skill_name` | `{{SKILL_NAME}}`: имя из строчных латинских букв, цифр и дефисов, до 64 символов |
| `routing_description` | `{{ROUTING_DESCRIPTION}}`: условия применения для каталога Router, до 1024 символов |
| `agent_name` | `{{AGENT_NAME}}`: понятное имя агента одной строкой |
| `agent_model_id` | `{{AGENT_MODEL_ID}}`: точный Workspace Model ID, не ID Skill |
| `routing_criteria` | `{{ROUTING_CRITERIA}}`: признаки подходящего запроса |
| `other_route_criteria` | `{{OTHER_ROUTE_CRITERIA}}`: когда не выбирать этого агента, без назначения другого исполнителя |
| `required_inputs` | `{{REQUIRED_INPUTS}}`: необходимые факты, параметры и файлы; что уточнить до запуска и когда допустим ограниченный результат |
| `independent_task_scope` | `{{INDEPENDENT_TASK_SCOPE}}`: одно самостоятельное поручение и нужные данные для его текста; если профиль не подходит, укажи это |
| `final_result_scope` | `{{FINAL_RESULT_SCOPE}}`: допустимая обработка подтверждённых готовых результатов и нужные для неё входы; если не входит в профиль, укажи это |
| `expected_result` | `{{EXPECTED_RESULT}}`: проверяемый результат работы агента |
| `positive_examples` | Непустой массив согласованных с автором позитивных примеров |
| `negative_examples` | Непустой массив согласованных с автором негативных примеров |

Все поля обязательны. Десять текстовых полей — непустые строки, примеры — массивы
непустых строк. Передавай исходный текст значений; YAML-экранирование
и вставку списков примеров выполняет скрипт.

Пиши условия по намерению пользователя и нужному результату. Например,
«рассчитать прогноз по временно́му ряду» отличает профиль лучше, чем
«любые вопросы, содержащие слово прогноз». Примеры должны помогать выбрать
адресата, а не добавлять неподтверждённые возможности. Не приписывай агенту
доступ к данным, Tools или терминалу без сведений о его настройках.
Для `required_inputs` перечисли данные, которые должны попасть в поручение
самими значениями, включая даты, единицы и ограничения; если нужен полный
документ, назови его назначение. Для `final_result_scope` опиши обработку
готового результата без повторного получения тех же данных только ради
передачи. Эти поля описывают выбор адресата и входы, а не алгоритм работы
или управление другими агентами.
Историческое имя поля `other_route_criteria` сохраняется для совместимости
Tools и рендерера. Его содержание — только границы своего профиля.
Например: «Объяснение общих терминов без расчёта прогноза вне профиля».

Имя и описание согласуй с карточкой Skill OWUI: метаданные в тексте
не создают карточку и не назначают ей ID.
В YAML сохраняются только `name` и `description` самого Skill. Имя и ID
адресата из исходных полей остаются в тексте профиля. Router формирует свой
каталог по `AGENTS` и карточкам моделей; дублировать адресата в YAML не нужно.

Общие правила уверенного выбора агента и вызовов `lite_delegate` /
`delegate_task` принадлежат системному промпту Router. В созданный routing
Skill включай профиль адресата; процедуры выполнения задачи, схемы Tools
и общие правила handoff туда не копируй.

## Заполнение скриптом

Если доступны `render_routing_skill` и `save_routing_skill`, передай
согласованные JSON-поля объектом `fields` в `render_routing_skill`.
Он вызывает тот же рендерер со встроенным шаблоном; `execute_code`, терминал
и перенос файлов не нужны. Готовый Markdown бери из результата Tool.
При поручении сохранить используй `save_routing_skill` с теми же полями,
отдельным Skill ID и `expected_version_id`: пустым для создания, актуальным
из `inspect_routing_skill` для обновления. При конфликте версии перечитай
изменения перед новой попыткой. Далее переходи к разделу «Результат и подключение».

Если этих Tools нет, используй следующий переносимый способ.
После согласования примеров используй приложенный
[scripts/render_routing_skill.py](scripts/render_routing_skill.py).
Он принимает JSON-поля и шаблон, проверяет заполнение, добавляет примеры
в нужные разделы и возвращает готовый `SKILL.md`. Скрипт не создаёт Skill
в OWUI и не изменяет `AGENTS`; подтверждение примеров остаётся частью диалога.

Файлы Workspace Skill сами не исполняются. Используй фактически доступный
`execute_code` или Python 3 через терминальный Tool с его именем и схемой.
В нашем Router Pipe штатные `execute_code` и операции записи Skills
автоматически не добавляются: проверь наличие отдельно подключённого
исполняющего Tool или используй обычную OWUI-модель с нужными возможностями.
Отдельный Tool для заполнения шаблона не требуется. Если средства исполнения
нет, сообщи, что автоматическое заполнение требует его подключения.

В терминале, где уже размещены файлы Skill с сохранённой структурой каталогов,
сохрани согласованные поля в `fields.json` и из каталога Skill выполни:

```sh
python3 scripts/render_routing_skill.py --input fields.json
```

Скрипт также принимает JSON через stdin и путь к шаблону через `--template`.
Зависимости, кроме стандартной библиотеки Python 3, не нужны.
Файлы Workspace Skill автоматически в терминале не появляются: при
необходимости сначала прочти скрипт и шаблон штатными Skill readers
и перенеси их доступным файловым Tool с сохранением содержимого и путей.

Для `execute_code` прочти скрипт и шаблон через Skill readers и передай
их полное содержимое в строки `script_source` и `template_text`, а JSON-поля —
в словарь `fields`. Затем выполни:

```python
namespace = {"__name__": "routing_skill_renderer"}
exec(script_source, namespace)
print(namespace["render"](fields, template_text), end="")
```

Эти переменные нужно сформировать из фактически прочитанных файлов
и согласованных полей; они не предоставляются `execute_code` автоматически.
Используй готовую функцию, без переписывания её алгоритма моделью.
При ошибке исправь указанные поля и повтори запуск. Готовый Markdown бери
из успешного результата скрипта; если нужно изменить текст, скорректируй
поля и запусти скрипт заново.

## Результат и подключение

Перед выдачей проверь, что все `{{...}}` заменены, Model ID подтверждён,
позитивные и негативные примеры уточнены с автором, подтверждены им
и включены в соответствующие разделы шаблона, а ожидаемый результат
соответствует изученным возможностям агента и требованиям автора.
Проверь также, что входы самодостаточны для независимого задания, роли
в составном запросе явно ограничены, а профиль не требует чужих Tools,
рабочих Skills или вложенной передачи другому агенту.
Проверь все разделы и примеры: они должны описывать только адресата и его
границы, без маршрутов к другим агентам и зависимости от состава каталога.
Существенные вопросы о границах применения должны быть разрешены.
Выдай полный `SKILL.md`
и отдельно имя и описание для карточки OWUI.

Если пользователь поручил сохранить Skill и доступны штатные инструменты
создания/изменения Skills, используй их фактические схемы. Иначе выдай текст
для ручного сохранения. Сообщай о сохранении только по подтверждённому
результату инструмента; текст в ответе сам по себе ничего не устанавливает.

Объясни оставшиеся действия подключения:

1. Создать или обновить и активировать Skill в OWUI, добавить ему `SKILL.md`.
2. Получить фактический ID сохранённого Skill и обеспечить владельцу публичной
   модели Router read-доступ к нему.
3. Связать точный Workspace Model ID с фактическим Skill ID в `AGENTS`
   установленного Filter Router Preparation. Пример формы записи:
   `AGENTS = {"actual-model-id": "actual-skill-id"}`. При обновлении сохранить
   остальные записи реестра.
4. Проверить выбор на подходящем запросе, похожем запросе вне профиля
   и неоднозначном запросе, который требует уточнения.

Routing Skill не нужно добавлять к рабочим Skills агента или дублировать
в `base_skill_ids`. Собственные рабочие Skills агента настраиваются в его
Workspace Model. Если сохранение выполнено, но реестр ещё не изменён,
явно обозначь, что подключение к Router не завершено.
