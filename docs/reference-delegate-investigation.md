# Короткий delegate в референсе

Дата: 2026-10-22. Прочитан локальный `../owui-tools/handoff_router`, включая
его AGENTS, domain context и применимые ADR. Код референса не изменялся.
Рабочий Router в этом проекте также не изменён.

## Как устроена передача

`lite_delegate.py:12–24` возвращает небольшой JSON:

```json
{"__lite_delegate__": "v2", "agent_id": "agent-a"}
```

В результате нет request ID, nonce и audit вызовов. Это не буквально строка
`agent-a`: неизменённый parser требует v2 marker. Версия — распознавание формата,
полезная нагрузка передачи — ID адресата.

Pipe использует `HandoffProtocol.active(metadata)` либо
`HandoffProtocol.find_current(messages)`; последний читает завершённые пары
Tool call/result текущего пользовательского запроса. Выбор проверяется
по подготовленному Registry, затем `RequestRuntime.activate()` сохраняет
активного агента в metadata текущего запроса. Следующее сообщение сбрасывает его.
Отдельного server-witness pending/nonce протокола, как в новом Router, здесь нет.

## Как восстанавливается авторство истории

`shared/tool_history.py:139–201` сопоставляет вызовы и результаты внутри
assistant batch и пользовательского запроса, затем обходит результаты по порядку:

1. Новый настоящий user message устанавливает исполнителем Router.
2. До завершённого delegate результаты принадлежат текущему исполнителю.
3. Сам delegate принадлежит предыдущему исполнителю.
4. После него текущим исполнителем становится выбранный агент.
5. Незавершённый/противоречивый delegate или неизвестный адресат дают `unknown`.

Порядок элементов `assistant.tool_calls` не используется как порядок исполнения;
важен порядок связанных Tool results. Прошлая история разбирается тем же способом.
Для этого механизма референс не пишет `message.meta` и не хранит отдельный audit.
Следовательно, вопрос перезаписи `message.meta` при approval pause к этому
механизму хранения не относится. Полная поддержка approval-resume из этого не следует.

ADR 0003 референса отдельно предлагает хранить автора ответа в `message.meta`
для Actions. Это другая задача; в прочитанном Router нет соответствующего outlet
и записи в Chats. ADR не является свидетельством реализации такого хранения.

## Выполненные проверки

- **19/19** выбранных тестов референса: `test_tool_history` и
  `test_executor_history`. Это unit-проверки; OWUI boundaries в тестах stubbed.
  Запуск с `PYTHONDONTWRITEBYTECODE=1`, без записи в соседний репозиторий.
- Из настоящего сохранённого OWUI 0.12.3 прочитана цепочка A → B → Router,
  чат `d0c548ce-2e81-42fc-84af-b57bf4621925`. Через установленный native
  `convert_output_to_messages()` восстановлены сообщения. Большие delegate results
  заменены результатами настоящего `Tools.lite_delegate()` референса.
- Референс правильно определил авторов **10/10** завершённых exchanges;
  результат совпал с разбором исходной истории новым Router. Последний общий
  вопрос сбросил выбор агента. Дополнительные данные в `message.meta` не использованы.
- Проверена смешанная fixture нового проекта: в одной генерации Router есть
  `lite_delegate` и базовый `lookup`, результат `lookup` расположен после delegate.
  Референс приписал `lookup` агенту, тогда как сохранённый audit доказывает Router.
  Это контрпример для общей эквивалентности алгоритмов, не результат обычной
  последовательной передачи из выполненной HTTP-приёмки.
- При удалённом из текущего Registry агенте референс помечает последующие
  исторические Tools как `unknown`. Новый Router сохраняет исторический ID.
  В новом проекте точные Model IDs позволяют отделить историческое авторство
  от текущих разрешений, не копируя alias-resolution референса.

Артефакты: [сравнение](../.cache/reference-contract-results.json),
[проба](../.cache/reference-contract-probe.py). Они не содержат credentials.
Нативный loop самого референса на 0.12.3 не запускался: его объявленная версия

## Следствие для нашего контракта

Сохранение audit в `message.meta` — допустимый вариант, но не обязательное
условие короткого результата delegate. Принцип референса подходит для
последовательного Router → один агент на пользовательский запрос.

Для применения без потери текущих требований нужны серверная проверка
отдельного delegate-вызова без других Tools той же генерации, сохранение
текущего request binding/повторной авторизации/pending только на сервере
и независимая от сегодняшнего Registry атрибуция прошлых точных Model IDs.
Результат Tool можно сделать строкой ID, адаптировав parser и проверки exchange.
Повторять alias и восстановление активной передачи только из присланной клиентом
истории не требуется. Новый контракт и эти изменения здесь не реализовывались.
