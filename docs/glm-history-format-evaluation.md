# Формат истории для роутера и агентов на GLM‑5.3‑Flash

## Решение

Для агента сохранить предзагруженную пару `load_conversation_history` как основной формат на проверенном подключении. Маркированное сообщение `user` непосредственно перед текущим вопросом подходит как запасной формат для провайдеров с более строгой проверкой Tool-вызовов. В базовых сценариях оба формата прошли 4 из 4 строгих проверок. В уточнённом конфликте старого и свежего результата маркированный `user` дал 3 из 3, служебная пара — 2 из 3. Если выбирать формат с нуля для нового провайдера, маркированный `user` перед текущим вопросом — разумная отправная точка. Для существующего роутера данных пока мало, чтобы заменить проверенную упаковку в рабочем Tool-цикле. Для роутера сохранить хронологию собственных передач и отдельное сообщение со сводкой. Активную цепочку инструментов агента передавать отдельными сообщениями в исходном порядке. [Текущая упаковка агента](../src/lite_handoff_router/agent_history_block.py#L65) · [Подстановка общей сводки](../src/lite_handoff_router/shared_summary.py#L168)

## Что определяют роли

| Формат | Что видит GLM | Когда использовать |
|---|---|---|
| Служебная пара `assistant.tool_calls` + `tool` | Запись вызова и наблюдение. `tools` объявляются отдельно. | Готовая, структурированная история, которую сервер передаёт агенту. Имя зарезервировано, ID пары совпадает, сам вызов отсутствует в реестре доступных инструментов. |
| Маркированный `user` | Отдельная реплика пользователя с данными. | Запасной формат. Ставить перед реальным текущим вопросом, чтобы сохранить его последней репликой `user`. |
| Дополнительный `system` | История попадает в системную роль. | В `system` полезно объяснять, как читать историю. Сам текст прошлых запросов и Tool-данных лучше держать отдельно от инструкций. |
| Хронология `user` / `assistant` и выполненные Tool-пары | Модель видит ход за ходом, с привычной последовательностью сообщений. | Собственные действия и активная цепочка. Для старых действий другого агента нужна явная атрибуция, иначе его реплика выглядит как собственный ответ модели. |

Публичный шаблон GLM печатает имя исторического вызова даже при отсутствии его схемы в `tools`. По контракту Z.ai результат `tool` привязан к вызову через `tool_call_id`, а новый вызов в обычном цикле делает модель. Успешный запрос к Z.ai с заранее собранной парой подтверждает совместимость на проверенном маршруте. Перед использованием на другом шлюзе нужна его собственная проверка. В Open WebUI 0.13.3 есть оба прецедента: общая сводка добавляется в `system`, а серверный каталог Skills может передаваться как скрытая Tool-пара. [Шаблон GLM‑5.3‑Flash](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/b98f72538870b0dbf6b796581c19b99527eb6089/chat_template.jinja) · [Z.ai Function Calling](https://docs.z.ai/guides/capabilities/function-calling) · [Сводка и скрытая память Open WebUI](https://github.com/open-webui/open-webui/blob/v0.13.3/backend/open_webui/utils/middleware.py#L2804-L2841) · [Каталог Skills Open WebUI](https://github.com/open-webui/open-webui/blob/v0.13.3/backend/open_webui/utils/middleware.py#L2404-L2415)

Шаблон GLM ищет последнее сообщение `user` и использует его позицию в том числе для обработки `clear_thinking`. Служебный `user` после фактического вопроса меняет эту границу. Шаблон и API Z.ai документируют разные значения `clear_thinking` по умолчанию, поэтому параметры установленного SGLang следует сверять отдельно. Ещё одно различие важно для переносимости: в проверенном коде конвертация Chat Completions в Responses API берёт последнее обработанное системное сообщение в поле `instructions`. Два отдельных `system` в тесте отправлялись по Chat Completions. ## Проверка на реальной модели

Open WebUI 0.13.3 в Docker, подключение Z.ai, модель `glm-5.3-flash`, `stream: false`, `temperature: 0`, `reasoning_effort: low`, `max_tokens: 220`. Синтетические запросы шли через прокси Chat Completions Open WebUI. Варианты сравнивались с одинаковой системной инструкцией внутри каждого сценария и одинаковой доступной схемой `stock_snapshot`. Менялась упаковка старой истории. Для хронологического варианта те же поля распределялись между репликами. В тесте модель выдавала Tool-вызовы, их выполнение проверялось по имени и аргументам. В сценарии продолжения в запрос уже была вложена законченная рабочая Tool-пара. Сохранение чата, фильтры и исполнение Tool-цикла для всех вариантов отдельно не тестировались.

| Сценарий | Служебная Tool-пара | Маркированный user | Дополнительный system | Хронология |
|---|---|---|---|---|
| Извлечь складской кейс, число и автора рядом с похожим CRM-результатом | Верно | Верно | Вместо номера кейса вернула SKU | Вместо номера кейса вернула SKU |
| Учесть исправление старого остатка и проигнорировать старую просьбу о формате | Верно | Верно | Верно | Верно |
| Вызвать настоящий Tool с параметрами из нужного старого хода | Верно | Верно | Верно | Верно |
| Совместить старую сводку и новый ход без обращения к Tool | Верно | Верно | Верно | Факты верны, добавила подписи полей |
| Применить свежий результат из текущей Tool-пары | В исходной формулировке все четыре варианта взяли 11 вместо старых 15, без повторного вызова. Во всех ответах третьим полем пришёл склад; проверка ожидала буквальное значение `warehouse`. ||||

После уточнения третьего поля повторили этот запрос по одному разу на каждом формате. Маркированный `user`, `system` и хронология вернули свежие 11. Служебная пара вернула старые 15. В двух дополнительных повторах пары и `user` оба формата вернули 11. Получилось 3 из 3 для маркированного `user` и 2 из 3 для служебной пары на одном конфликтном сценарии. Ошибка с устаревшим числом наблюдалась один раз. Этой выборки мало для вывода о стабильном преимуществе.

Всего 28 запросов вернули HTTP 200. Ни один вариант не вызвал служебный `load_conversation_history` и не запросил Tool в сценарии чтения истории. По первому набору из 20 запросов средний вход составил 431,2 токена для служебной пары, 420,2 для `user` и `system`, 416,2 для хронологии. При одинаковом JSON служебная пара стоила **11 дополнительных токенов** во всех пяти сценариях. Публичный шаблон и токенизатор дали **13 дополнительных токенов**. На длинной истории разница в содержимом важнее этой обёртки. Всего тесты использовали **12 004 входных и 757 выходных токенов**. ## Что сохранить при дальнейших изменениях

Старые ходы, модельную сводку и чужие результаты хранить как данные с явным автором и порядком событий. Для своих завершённых операций сохранять реальные связи вызовов с результатами. Решение о повторном действии должно опираться на разрешённые инструменты и серверное состояние. Роль сообщения и текстовая метка помогают модели ориентироваться, но не гарантируют соблюдение ограничения. В предыдущем сквозном прогоне этой же GLM агент однажды повторил запрос к данным вопреки просьбе ответить по истории.

Большие редко используемые результаты можно отдавать через настоящий инструмент чтения по разрешённой ссылке. Это уменьшает обязательный вход, но требует дополнительного вызова, если данные нужны. Такой вариант имеет смысл сравнивать отдельно на больших наборах. Перенос на маркированный `user` имеет смысл проверить отдельным A/B-прогоном полного Tool-цикла роутера, включая передачу агенту, продолжение после Tool-ответа и повторное использование сводки. Выбор полей истории и проверка нужных фактов важнее разницы в 11 токенов.
