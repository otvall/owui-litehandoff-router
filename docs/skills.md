# Routing Skills и рабочие Skills

Routing Skill принадлежит контексту Router и объясняет, **когда передать запрос**.
Рабочий Skill прикреплён к модели агента и объясняет, **как решить задачу**.
Профиль задаётся автором и может быть подготовлен отдельным помощником после
согласования примеров. Runtime Router использует уже сохранённые Skills и
не генерирует их автоматически при обработке пользовательских запросов.

## Skill для подготовки routing Skills

Для отдельного помощника с чтением конфигураций и сохранением Skills используйте
[готовый комплект и инструкцию](routing-author-agent.md). Ему не нужен
`execute_code`: рендерер вызывается внутри специализированного Tool.

Готовый [routing-skill-authoring](skills/routing-skill-authoring/SKILL.md)
объясняет модели, как собрать данные об агенте, заполнить шаблон, проверить
границы профиля и подключить созданный Skill к Router. Приложенный Python-скрипт
принимает согласованные поля в JSON и возвращает готовый Markdown по шаблону.
При использовании переносимого скрипта нужен `execute_code` или терминал
с Python 3; комплект отдельного помощника вызывает рендерер внутри Tool.
Сами файлы Workspace Skills не исполняются.

Перед заполнением модель изучает своё назначение в системном промпте,
схемы доступных Tools и остальные доступные Skills, исключая сам
`routing-skill-authoring` из профиля. Затем формулирует границы применения
для автора и обязательно согласует с ним позитивные и негативные примеры
запросов. До ответа автора окончательный Skill не выдаётся. Остальные
уточняющие вопросы задаются по необходимости.
Рабочие Tools ради обзора не запускаются. Если Skill создаётся для другой
модели, нужны сведения о её настройках: возможности модели-автора
не переносятся на адресата автоматически.

Создайте и активируйте в OWUI Skill `routing-skill-authoring`, перенесите
его `name` и `description` в карточку, а содержимое — в `SKILL.md`.
Добавьте [файл шаблона](skills/routing-skill-authoring/references/routing-skill-template.md)
как файл этого Skill с путём `references/routing-skill-template.md`, а
[скрипт заполнения](skills/routing-skill-authoring/scripts/render_routing_skill.py) —
с путём `scripts/render_routing_skill.py`.
Добавьте также [контракт Router](skills/routing-skill-authoring/references/router-contract.md)
с путём `references/router-contract.md`: он объясняет различия входов при
handoff, самостоятельном поручении и обработке готовых результатов.
Модель должна иметь доступ к чтению Skill и его файлов, а для заполнения —
к `render_routing_skill` либо к средству исполнения переносимого скрипта.
Приложенная копия соответствует [основному шаблону](templates/routing-skill/SKILL.md);
при изменении основного шаблона обновляйте и этот файл.

Прикрепите Skill к обычной модели, которая помогает администратору создавать
Skills. Если эту роль выполняет сам Router, добавьте фактический ID Skill
в `base_skill_ids` Filter Preparation и правило чтения Skill для запросов
на создание routing Skills в системный промпт. Это вспомогательный Skill,
а не routing Skill адресата: отдельная запись в `AGENTS` ему не нужна.
Для скрипта и записи Skills нужны реально опубликованные Tools: наш Pipe
сам добавляет только три штатных Skill reader. Одного включения builtin
категорий OWUI для появления остальных операций внутри Pipe недостаточно.

Пример запроса: «Создай routing Skill для модели `forecast-agent`: она
строит прогнозы по временным рядам; общие объяснения терминов без расчёта
прогноза вне её профиля».
Модель изучит возможности, согласует с автором примеры, передаст JSON-поля
рендереру и выдаст готовый текст с инструкцией подключения. Отдельный помощник
сохраняет результат через `save_routing_skill`; при использовании только
переносимого Skill нужны штатные операции создания/изменения Skills OWUI
либо ручное сохранение.

## Шаблон и связь с агентом

Готовый [шаблон routing Skill](templates/routing-skill/SKILL.md) содержит
YAML-поля `name`, `description` и вложенные `metadata.agent_id` /
`metadata.agent_name`, специализацию агента,
условия выбора и ожидаемый результат. В `{{SKILL_NAME}}`
укажите имя routing Skill, а в `{{ROUTING_DESCRIPTION}}` — конкретные условия
его применения. Замените все `{{...}}`, согласуйте имя/описание с карточкой
Skill OWUI и свяжите его фактический
ID с моделью через `AGENTS`. Полная инструкция и примеры базовых Skills/Tools
Router — в [руководстве по конфигурации](router-configuration.md).

Пример метаданных созданного routing Skill:

```yaml
---
name: "route-forecast"
description: "Прогнозирование по временному ряду."
metadata:
  agent_id: "forecast-agent"
  agent_name: "Прогнозист"
---
```

`name` обозначает Skill; `metadata.agent_id` и `metadata.agent_name` — его
адресата. Дополнительные поля сохраняются в YAML файла `SKILL.md`, а не в
полях карточки OWUI. Рендерер экранирует их и использует те же исходные
значения в тексте профиля. Runtime Router продолжает брать связь из `AGENTS`,
а актуальное название — из Workspace Model. Старые routing Skills без этих
полей продолжают работать; сами метаданные не регистрируют и не перенаправляют
агента. Имя и адресат обновляются при следующей подготовке профиля.

Шаблон также описывает обязательные входы, границы независимого поручения
и финальной обработки готовых результатов. Скрипт требует соответствующие
JSON-поля `required_inputs`, `independent_task_scope`, `final_result_scope`
наряду с остальными полями и двумя массивами примеров. Если роль не входит
в профиль, это нужно указать явно; положительные возможности не выдумываются.

Routing Skill самодостаточен: он описывает только своего адресата.
Раздел «Когда не выбирать этого агента» и негативные примеры задают
ограничения профиля без ссылок на имена/ID/Skills других агентов и без
предписаний передать запрос кому-либо или оставить Router. Дальнейший путь
Router выбирает по текущему каталогу. Поэтому добавление, удаление или
переименование соседнего агента не требует правки этого профиля.
JSON-поле `other_route_criteria` сохраняет историческое имя для совместимости,
но содержит только такие локальные ограничения.

Метаданные в тексте шаблона не создают Skill в OWUI и не заменяют его
фактический ID или связь в `AGENTS`. Общие правила уверенного выбора агента,
уточнения запроса и вызовов `lite_delegate` / `delegate_task` находятся
в [системном промпте Router](templates/router-system-prompt.md). Поддерживайте
их там; routing Skills описывают только профиль конкретного агента.

```python
AGENTS = {"agent-a": "route-a"}
```

Здесь `agent-a` — Workspace Model ID, а `route-a` — Skill ID.
В манифесте Router это отдельные поля:

```json
{
  "skill_id": "route-a",
  "agent_id": "agent-a",
  "agent_name": "Агент A",
  "name": "route-profile-a",
  "description": "Вопросы по профилю A."
}
```

`agent_name` — название Workspace Model, `name` — название routing Skill.
На вопросы «что ты можешь», «что ты умеешь», «какие агенты доступны» Router
получает инструкцию перечислять всех агентов текущего персонального каталога
по `agent_name`, кратко поясняя их назначение. Запрос о возможностях сам по
себе не требует запуска агента. При пустом каталоге Router сообщает, что
сейчас доступных агентов нет. Для старой записи без названия используется
точный `agent_id`; недоступные пользователю модели не перечисляются.

Router читает `view_skill(id="route-a")`, затем вызывает
`lite_delegate(agent_id="agent-a")`. Skill ID не принимается как alias Model ID.
В рабочие attachments `agent-a` можно добавить другой Skill, например
`a-working-guide`. Его не нужно дублировать в `AGENTS`.

Для независимого задания routing Skill также может рекомендовать вызов
`delegate_task(agent_id="agent-a", task="...")` с тем же `agent_id`. Оба enum строятся из одного
реестра. Вызывайте группу отдельно от чтения Skill и других Tools, дождитесь
всех исходов, затем при полном успехе передавайте финальную задачу отдельным
`lite_delegate`. Работники не получают эти управляющие Tools; их Skills ограничены собственными attachments.

Финальный агент получает подтверждённые результаты группы как входные данные
с авторами и доступными файлами, без рабочих Skill instructions и Tools
работников. Его routing Skill может описывать этот сценарий, но не должен
требовать повторного получения прогнозов или считать чужую Tool-историю своей.

У Router допустимы `base_skill_ids` из административных Valves Preparation
и routing Skills его персонального реестра. У агента — свежие `skillIds` его
Workspace Model. Пустой `base_skill_ids` сохраняет routing Skills.
Attachments карточки Router, клиентские списки и упоминания Skills набор не расширяют.

## Особенность OWUI 0.13.3

Штатная подготовка Skills может перечислить все активные Skills, доступные
пользователю, и добавить инструкции выбранных/упомянутых Skills. Сам штатный
read-доступ не ограничен карточкой текущей модели. Поэтому одного исправленного
манифеста для изоляции недостаточно.

Pipe заменяет широкий контекст собственным манифестом и защищает все три чтения:
`view_skill`, `read_skill_file`, `grep_skill_files`. Сначала проверяется набор
текущей модели, затем существование, активность и штатный read-доступ владельца
модели. Для базовых/routing Skills используется владелец публичного Router,
для рабочих — владелец агента. Известный ID другого доступного владельцу или
пользователю Skill не обходит эту проверку. Контекст владельца применяется
только к трём reader; обычные Tools продолжают получать пользователя чата.

Guard остаётся исходной функцией при native callable refresh OWUI. Подмена
его callable/схемы дополнительным inlet-фильтром вызывает ошибку подготовки.
Имена трёх readers зарезервированы; одноимённые пользовательские Tools
вызывают ошибку конфигурации. Автоматические встроенные операции создания
и изменения Skills к этому адаптеру чтения не добавляются.

## Файлы, версии и права

Используются штатные операции файлов и страниц OWUI, включая `offset`,
`max_chars`, поиск и текущий снимок версии. В пределах одного запроса
прочитанный собственный Skill сохраняет версию для согласованных чтений файлов.
При смене исполнителя чужие версии исключаются. На новом сообщении версии
и полные прошлые инструкции не восстанавливаются как активный контекст:
при необходимости Skill читается заново.

Пользователям выдаётся доступ к моделям. Отдельные grants на routing и рабочие
Skills им не нужны: владелец соответствующей модели должен иметь read-доступ.
Прямые native APIs Skills остаются закрыты пользователю без собственного grant.
Непригодный владельцу Router routing Skill исключает адресата из реестра; недоступный обязательный
рабочий Skill прерывает подготовку агента. Имя и фактические чтения могут
отображаться в истории; механизм не предназначен для секретности инструкций.

Проверки: `tests/native/test_skills.py` и `tests/native/test_resource_access.py`
используют настоящие builtin readers, приватные ресурсы, файлы/страницы,
native refresh, разных владельцев и изменение attachments. Запуск:
`.venv/bin/python tools/run_native_tests.py`.

## Native-каталог OWUI 0.13.3

Скрытый list_available_skills не является источником разрешений Router.
В проекцию попадает существующий scoped-манифест выбранной модели; инструкции
читают только три штатных Skill readers. Приватный прикреплённый Skill читается
через владельца модели, исполнение остаётся от actor; прямые grants пользователю
не выдаются. Отсоединённый Skill исключается на следующей подготовке.
В диагностике проверяйте IDs и доступный набор readers, не публикуйте сырые
каталоги, инструкции или память. См. [контекст](context.md) и
[результаты проверки](owui-0133-context-validation.md).
