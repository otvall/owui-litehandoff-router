# Routing Skills и рабочие Skills

Routing Skill принадлежит контексту Router и объясняет, **когда передать запрос**.
Рабочий Skill прикреплён к модели агента и объясняет, **как решить задачу**.
Их содержимое пишет администратор; комплект не генерирует Skills из описаний моделей.

```python
AGENTS = {"agent-a": "route-a"}
```

Здесь `agent-a` — Workspace Model ID, а `route-a` — Skill ID.
В манифесте Router это отдельные поля:

```json
{
  "skill_id": "route-a",
  "agent_id": "agent-a",
  "name": "route-profile-a",
  "description": "Вопросы по профилю A."
}
```

Router читает `view_skill(id="route-a")`, затем вызывает
`lite_delegate(agent_id="agent-a")`. Skill ID не принимается как alias Model ID.
В рабочие attachments `agent-a` можно добавить другой Skill, например
`a-working-guide`. Его не нужно дублировать в `AGENTS`.

Для независимого задания routing Skill также может рекомендовать элемент
`lite_parallel(tasks=[...])` с тем же `agent_id`. Оба enum строятся из одного
реестра. Вызывайте группу отдельно от чтения Skill и других Tools, дождитесь
всех исходов, затем при полном успехе передавайте финальную задачу отдельным
`lite_delegate`. Работники не получают ни эти управляющие Tools, ни штатный
`delegate_task`; их Skills ограничены собственными attachments.

Финальный агент получает подтверждённые результаты группы как входные данные
с авторами и доступными файлами, без рабочих Skill instructions и Tools
работников. Его routing Skill может описывать этот сценарий, но не должен
требовать повторного получения прогнозов или считать чужую Tool-историю своей.

У Router допустимы `base_skill_ids` из административных Valves Preparation
и routing Skills его персонального реестра. У агента — свежие `skillIds` его
Workspace Model. Пустой `base_skill_ids` сохраняет routing Skills.
Attachments карточки Router, клиентские списки и упоминания Skills набор не расширяют.

## Особенность OWUI 0.12.3

Штатная подготовка Skills может перечислить все активные Skills, доступные
пользователю, и добавить инструкции выбранных/упомянутых Skills. Сам штатный
read-доступ не ограничен карточкой текущей модели. Поэтому одного исправленного
манифеста для изоляции недостаточно.

Pipe заменяет широкий контекст собственным манифестом и защищает все три чтения:
`view_skill`, `read_skill_file`, `grep_skill_files`. Сначала проверяется набор
текущей модели, затем существование, активность и штатный read-доступ владельца
модели. Для базовых/routing Skills используется владелец публичного Router,
для рабочих — владелец агента. Известный ID другого доступного владельцу или
пользователю Skill не обходит эту проверку. Контекст владельца применяется
только к трём reader; обычные Tools продолжают получать пользователя чата.

Guard остаётся исходной функцией при native callable refresh OWUI. Подмена
его callable/схемы дополнительным inlet-фильтром вызывает ошибку подготовки.
Имена трёх readers зарезервированы; одноимённые пользовательские Tools
вызывают ошибку конфигурации. Автоматические встроенные операции создания
и изменения Skills к этому адаптеру чтения не добавляются.

## Файлы, версии и права

Используются штатные операции файлов и страниц OWUI, включая `offset`,
`max_chars`, поиск и текущий снимок версии. В пределах одного запроса
прочитанный собственный Skill сохраняет версию для согласованных чтений файлов.
При смене исполнителя чужие версии исключаются. На новом сообщении версии
и полные прошлые инструкции не восстанавливаются как активный контекст:
при необходимости Skill читается заново.

Пользователям выдаётся доступ к моделям. Отдельные grants на routing и рабочие
Skills им не нужны: владелец соответствующей модели должен иметь read-доступ.
Прямые native APIs Skills остаются закрыты пользователю без собственного grant.
Непригодный владельцу Router routing Skill исключает адресата из реестра; недоступный обязательный
рабочий Skill прерывает подготовку агента. Имя и фактические чтения могут
отображаться в истории; механизм не предназначен для секретности инструкций.

Проверки: `tests/native/test_skills.py` и `tests/native/test_resource_access.py`
используют настоящие builtin readers, приватные ресурсы, файлы/страницы,
native refresh, разных владельцев и изменение attachments. Запуск:
`.venv/bin/python tools/run_native_tests.py --owui-version 0.12.3`.

## Текстовые Skills OWUI 0.11.1

В 0.11.1 Skill хранит текст `content`, а native reader — `view_skill(id)`.
Создайте `route-a` с описанием условий передачи и инструкцией
`lite_delegate(agent_id="agent-a")`; задайте `AGENTS = {"agent-a": "route-a"}`.
Рабочий `a-working-guide` с инструкциями решения прикрепите к
`agent-a.info.meta.skillIds`. `base_skill_ids` Router хранит дополнительные
общие инструкции, routing Skill из `AGENTS` дублировать в нём не нужно.

Каталог и read scope сохраняют те же границы владельцев и моделей. Только
`view_skill` получает owner authority; локальный Tool получает actor и его
UserValves. Native refresh не снимает guard; отключённый/отсоединённый Skill
не читается. Имена всех трёх readers остаются зарезервированы, но
`read_skill_file` и `grep_skill_files` в legacy-комплекте отсутствуют.
Файловые страницы/версии из раздела выше относятся к 0.12.3. В 0.11.1
параллельные задания недоступны независимо от текста Skill.

Roundtrip текстовых Skills/моделей, два actor без прямых grants, отдельные
каталоги, refresh, изменения attachments, неактивность и inlet-подмена
проверяются `tests/native_0111/test_resources_0111.py`. Запуск legacy suite —
по команде в [development.md](development.md). Для current suite используйте
`.venv/bin/python tools/run_native_tests.py --owui-version 0.12.3`.
