# Диагностика реального LLM-прогона 2026-11-10

Источник: `real-llm-context-acceptance.json`. Новые внешние LLM-запросы,
credentials, изменения production runtime и промптов не использовались.

## Воспроизведение

```sh
.venv/bin/python tools/diagnose_sequential_delegation.py
.venv/bin/python tools/diagnose_sequential_delegation.py --batch
```

До исправления первый режим был красным: реальный порядок вызовов воспроизводится
через production `parallel_tool`, `delegate_tool`, `downstream_data` с
изолированным GroupAdapter вместо native worker transport. Результат за
доли секунды: один worker, отказ второго вызова, `completed`, handoff принят,
ошибки второй попытки в downstream-пакете нет. Повторный запуск дал тот же исход.

Контроль меняет одну переменную: два вызова находятся в одной наблюдаемой
генерации. Два callable исполняются через gather; два worker запускаются,
проверка проходит. Native transport и реальная модель этим replay не проверяются;
они уже наблюдались в записанном live trace. Это диагностический replay,
а не регрессия нового требования запрещать handoff после любой отклонённой попытки.

## Проверенные гипотезы

1. Ответ провайдера уже содержит по одному delegate_task (outputs 2 и 7).
   Runner передаёт каждый полученный список tool_calls целиком в SSE. Наш
   streaming/native loop не разделяет исходный multi-call на два вызова.
   Почему провайдер выдал такой ответ — ограничение модели, её инструкции
   или provider routing/defaults — не установлено без нового live A/B.
   Runner не задаёт `parallel_tool_calls`; отсутствие поля само по себе
   не доказывает запрет параллельных вызовов.
2. `parallel_tool` отклоняет вызов из следующей генерации до изменения состояния
   ранее завершённой группы. `handoff_barrier` проверяет только idle/completed.
   Поэтому успешная группа из одного задания разрешает handoff после отказа
   дополнительного запуска. Это соответствует текущей механике одной группы,
   но не доказывает выполнение пользовательского требования о двух заданиях.
3. `agent_projection` исключает чужую Router Tool-историю. `downstream_data`
   добавляет только подтверждённые результаты принятой группы, без отклонённых
   попыток. В outputs 9–12 у финального агента есть один результат и память,
   но нет ошибки второго delegate_task. Исходный пользовательский запрос
   по-прежнему просит два запуска.
4. В тестовом worker-промпте есть утверждение `report the two supplied outcomes`,
   хотя фактически supplied outcome один. Это подтверждённый дефект стенда,
   способный подталкивать к двум строкам. Его причинный вклад в конкретный
   ответ остаётся гипотезой до live A/B с изменением только этого текста.
5. Три worker_lookup финального этапа имеют разные call IDs. В следующих
   inputs сохранены соответственно 1, 2 и 3 собственные завершённые пары.
   Потеря Tool-истории и автоматический retry одного вызова этим trace опровергнуты.
   Повторные запросы выдаёт провайдер вопреки `exactly ONCE`. Сам fixture Tool
   возвращает лишь WORKER_LOOKUP_RESULT, без предметного результата/описания,
   поэтому стенд не является полноценной моделью прикладного forecasting Tool.

## Причина ложной итоговой сводки

Сошлись три условия: провайдер выдал последовательные вызовы; runtime считает
первую одноэлементную группу успешно завершённой и не учитывает в барьере отказ
следующего запуска; финальный агент не видит этот отказ, а тестовый промпт заранее
предполагает два результата. В итоге один task_id появился в ответе дважды.
Система не создала второго child и не повторила первый worker автоматически.

Метка native-памяти дошла. У этого прогона нет признака потери памяти,
потери параметров FTP-42/дат или утечки родительской оркестрации работнику.

## Отдельная найденная несогласованность

`docs/templates/router-system-prompt.md` и
`docs/templates/routing-skill/SKILL.md` всё ещё описывают lite_parallel/tasks,
хотя текущий контракт — delegate_task на одно задание. Эти шаблоны не применялись
в данном runner, поэтому не являются причиной записанного live failure.

## Изменения по результатам диагноза

- Исправить стенд: не предписывать число результатов финальному агенту заранее;
  разделить инструкции работника и синтезатора; дать Tool предметный результат
  и проверять вызовы по исполнению. Сохранить исходный failed trace.
- Отдельно согласовать runtime-политику отказа дополнительного запуска:
  блокировать handoff либо передавать адресату server-owned сведения об отказе
  и фактическом числе заданий. Не подменять одним completed доказательство
  выполнения семантического количества из запроса пользователя.
- Провести live A/B поддержки multi-call на одном и том же запросе с явным
  parallel_tool_calls, если он поддерживается endpoint, и с другой моделью.
  Не объявлять эту модель принципиально неспособной по одному прогону.
- Обновить два устаревших шаблона под текущий контракт.

Обе live-приёмочные задачи остаются открытыми. Исправление политики handoff
меняет observable behavior и требует согласования; диагноз сам по себе
не доказывает прохождение исходного реального LLM-сценария после исправления.


## Исправление после согласования

Пользователь согласовал исправление. Дополнительная попытка теперь блокирует
handoff по серверному аудиту, включая ошибку аргументов до callable. Результаты
первой группы сохранены. Default replay теперь проверяет блокировку и проходит;
`--batch` проверяет прежний успешный путь двух вызовов. Исправлены промпты и
валидатор live-стенда, а также оба устаревших шаблона. Исходный failed trace
сохранён без переписывания. Повторная real-LLM приёмка остаётся отдельной работой.
