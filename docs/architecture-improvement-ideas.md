# Идеи улучшения архитектуры Router и Filter

Дата: 2026-11-05. Статус: **отложено по решению пользователя**.

Это заметки архитектурного разбора, а не согласованный план реализации.
Рефакторинг не начат, новые OpenSpec changes не созданы. Конкретные interfaces
и ответы на открытые вопросы ещё не выбраны.

Область разбора — текущие Router и Filter для единственной поддерживаемой
версии **Open WebUI 0.12.5**. Основной пользовательский сценарий — MCP через
StreamableHTTP. Существующие local Tools, OpenAPI и terminal остаются частью
поддерживаемого исполнения.

## Кандидаты и приоритеты

| № | Идея | Оценка | Ожидаемый результат |
|---|---|---|---|
| 1 | Сосредоточить владение MCP-сессиями и rollback подготовки | Strong; рекомендованный первый шаг | Pipe и parallel меньше знают о внутреннем реестре |
| 2 | Собрать правила исполняемого набора Tools вместе | Worth exploring; оценить после первого шага | Имена, schema, callable и защита после inlet согласуются в одном месте |
| 3 | Исследовать повторные проверки MCP-подключения | Speculative; сначала измерить затраты | Возможное сокращение повторного чтения политики при сохранении её актуальности |

Термины разбора: **module** скрывает поведение за **interface**;
**depth** — объём поведения, доступный через этот interface; **seam** — место
его применения; **adapter** — конкретная реализация на seam. Ожидаемый
**leverage** — меньше знаний у callers; **locality** — сосредоточение изменений
и проверки поведения в одном месте. Число файлов само по себе не критерий.

## 1. Владение MCP-сессиями и rollback подготовки

### Наблюдаемая сложность

- [capabilities.py](../src/lite_handoff_router/capabilities.py) создаёт реестр
  `request.scope["lite_handoff_mcp"]`, формирует ключ actor/owner/model/server,
  переиспользует сессии и очищает созданные ресурсы при собственной ошибке.
- [Pipe](../src/lite_handoff_router/entrypoints/lite_handoff_router.py)
  запоминает ключи до подготовки. Если последующая подготовка завершается
  ошибкой, он сам находит новые ключи, удаляет их и ожидает закрытия сессий.
- [parallel.py](../src/lite_handoff_router/parallel.py) извлекает сессии из
  дочернего scope и ожидает их закрытия при завершении работника.

Таким образом, interface владения включает устройство словаря, момент создания
ресурсов и правила нескольких путей cleanup. Эти знания распределены между
callers.

### Направление углубления

Сосредоточить реестр, reuse, принадлежность новых ресурсов конкретной подготовке
и её rollback в одном module. Pipe и parallel должны выражать lifecycle своей
работы, а учёт сессий становится внутренней implementation этого module.
Существующий OWUIAdapter сохраняется как adapter к штатному MCP.

Нужно различать два времени жизни:

| Что | Когда заканчивается |
|---|---|
| Подготовка очередной генерации | Успешная подготовка либо её ошибка |
| MCP-сессии полного запроса | Окончательное завершение запроса, ошибка или Stop |

Возврат Pipe и завершение отдельного provider stream — промежуточные этапы:
пригодное соединение должно оставаться доступным продолжениям.

Ключевой пример: Router уже использует соединение A; подготовка агента создаёт
B, после чего inlet агента падает. Требуемый исход — закрыть B, сохранить A
и прежний опубликованный набор Tools, не переключать активного агента.

**Deletion test:** удаление `McpSession` разнесёт очередь, ожидающие вызовы,
отмену и deadline по callers — этот module уже оправдан. Углублять предлагается
владение вокруг него. Ожидаемые locality и leverage — одно место для правил
rollback и меньше зависимости Pipe/parallel от ASGI scope.

### Поведенческие проверки при возвращении к идее

- Новое MCP-подключение успешно открыто, затем destination inlet падает:
  новые ресурсы закрыты, прежние сессии и опубликованные Tools сохранены.
- Несколько Tool-продолжений используют пригодную сессию без переподключения.
- Stop во время открытия, активного вызова и ожидания в очереди завершает
  локальную работу в пределах общего бюджета 5 секунд.
- Автоматический cleanup полного запроса и явный cleanup работника безопасны
  при повторном или одновременном вызове; пользователи и работники изолированы.

Опора: [test_atomic.py](../tests/test_atomic.py),
[test_capabilities.py](../tests/test_capabilities.py),
[test_mcp_cleanup.py](../tests/native/test_mcp_cleanup.py),
[test_mcp_transport.py](../tests/native_common/test_mcp_transport.py).
Сценарий «новый MCP + поздняя ошибка inlet» стоит проверить совместно:
существующие проверки загрузки MCP и атомарности в основном раздельные.
Interface должен быть test surface для наблюдаемого результата.

### Открытые вопросы — ответы пользователя пока не получены

1. Ограничить объём реестром, rollback и изменениями callers или также
   пересматривать внутреннее устройство `McpSession`?
   Рекомендация: первый объём, с сохранением нынешнего lifecycle сессии.
2. Допустим ли небольшой рост внутреннего кода ради сокращения знаний
   Pipe/parallel о словаре, ключах и новых сессиях?
   Рекомендация: приоритет меньшей связности при минимальном росте кода.

До выбора конкретного interface также проверить:

- Учёт новых объектов при замене завершённой сессии по прежнему ключу:
  текущий внешний rollback сравнивает ключи. Это наблюдение по коду,
  а не воспроизведённый runtime-дефект.
- Нужные гарантии одновременной подготовки на одном scope. Параллельные
  работники используют отдельные scope; поддержка multi-model fan-out
  самого Router в текущей матрице не заявлена и не проверена.

## 2. Правила исполняемого набора Tools

Затронутые места: [model_execution.py](../src/lite_handoff_router/model_execution.py),
[owui_adapter.py](../src/lite_handoff_router/owui_adapter.py),
[capabilities.py](../src/lite_handoff_router/capabilities.py),
[binding.py](../src/lite_handoff_router/binding.py),
[skills.py](../src/lite_handoff_router/skills.py).

`prepare_model` знает сборку Tools, reserved names, terminal collisions,
protected snapshot, проверку после destination inlet и финальный binding.
При этом alias, исходная операция и pinning пользователя согласуются
в других местах.

Идея — углубить module исполняемого набора Tools: сосредоточить согласованность
«публичное имя — schema — callable — ресурс», защиту после inlet и привязку
контекста. Порядок prompt/history/inlet/publication остаётся явным.
Seam проходит через подготовку и проверку набора; используется существующий
adapter OWUI. Точный interface ещё не проектировался.

Различия правил необходимо сохранить: local/OpenAPI разрешают коллизии через
alias; MCP, terminal и reserved names имеют собственные правила отказа.

**Deletion test:** удаление проверок переносит ошибки к исполнению, а удаление
общей регистрации возвращает дублирование alias/schema. Цель — locality
правил и leverage для подготовок, а не удаление защиты или универсальный
framework. Tests должны проверять native dispatch, исходную операцию,
actor/owner и отказ подменённых Tools через interface.

## 3. Повторные проверки MCP-подключения

Затронутые места: [resources.py](../src/lite_handoff_router/resources.py),
`mcp_invoker` в [capabilities.py](../src/lite_handoff_router/capabilities.py),
`tool_access`, `mcp_specs` и `mcp_connection` в
[owui_adapter.py](../src/lite_handoff_router/owui_adapter.py).

Изолированный probe одного вызова показал:

| Операция | Количество |
|---|---:|
| Проверка модели | 1 |
| Определение owner | 1 |
| Обращение к `mcp_connection` | 2 |
| Отправка в transport | 1 |

Общий ResourceScope проверяет подключение до очереди; queued проверка
function filter повторно проверяет подключение и ACL перед отправкой.
Probe использовал действительные ResourceScope/binding/invoker и OWUIAdapter
с локальными stand-in. Это счётчик вызовов, не измерение latency рабочей установки.

После профилирования можно рассмотреть более глубокий module допуска
MCP-операции: свежее решение о модели, owner, attachment, подключении и filter
перед dispatch. Seam — отправка операции через существующий adapter;
конкретный interface пока не выбран.

**Deletion test:** простое удаление проверки не учитывает ожидание в очереди
и отзыв разрешений. Возможные locality и leverage имеют смысл, только если
повторная работа сокращается с сохранением актуальности политики.
Нужны проверки отзыва доступа, смены owner и отмены во время проверки.
Измеренного основания обещать ускорение пока нет; TTL-кэш разрешений между
вызовами изменил бы текущий контракт.

## Что сохранить

- Два entrypoints: Filter создаёт trusted scope, receipt и общий
  `metadata.tools` до native копирования; Pipe готовит каждую генерацию
  и обновляет общий словарь in-place.
- Раздельные роли execution actor и model owner.
- Текущую отмену `McpSession`: очередь, worker/supervisor, параллельный
  disconnect, общий deadline и идемпотентное закрытие.
- Свежие проверки прав и MCP function filter, атомарную публикацию Tools
  и изоляцию пользователей/работников.
- Единственный релиз 0.12.5, две standalone Functions и существующий
  adapter к OWUI.

## Когда вернуться

Сначала согласовать объём варианта 1 и критерий упрощения. Затем сравнить
варианты interface, проверить сценарии владения и оформить отдельный
OpenSpec change, если пользователь решит начать работу. Вариант 2 оценить
после первого шага; вариант 3 — после измерения затрат.

Текущие основные контракты:
[model-bound-resource-access](../openspec/specs/model-bound-resource-access/spec.md)
и [workspace-model-execution](../openspec/specs/workspace-model-execution/spec.md).
