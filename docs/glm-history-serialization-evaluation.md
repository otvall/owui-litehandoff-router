# JSON, Markdown и XML в истории GLM‑5.3‑Flash

## Метод

26 ноября 2026 года. GLM‑5.3‑Flash на подключении Z.ai через Chat Completions в Open WebUI 0.13.3-slim. В каждом сравнении одинаковы системный промпт агента с общей инструкцией теста, роль и позиция блока, вопрос, порядок фактов, схемы инструментов и параметры: `temperature=0`, `reasoning_effort=low`, `max_tokens=280`, `stream=false`. Менялась строка после `[Conversation history]` в сообщении `user` перед текущим вопросом.

Каждую из семи задач проверили с двумя наборами значений и тремя форматами. В JSON использовались компактные объекты. Markdown использовал заголовки ходов, списки и явно подписанные поля. XML использовал теги полей с экранированием текстовых значений. Во всех вариантах сводка стояла перед ходами. Тестовая история была синтетической. Схемы рабочих инструментов были одинаковыми, ответы проверялись по имени и аргументам, сами инструменты тест не запускал. В задаче со свежим результатом готовая рабочая пара `assistant` / `tool` добавлялась после текущего вопроса. [Текущая упаковка агента](../src/lite_handoff_router/agent_history_block.py#L111-L121) · [Промпт агента](../src/lite_handoff_router/model_execution.py#L38-L48)

Критерий понимания для ответов — правильные факты и типы значений без лишнего вызова инструмента. Корректные ответы списком оценивались по содержанию вручную. Для действий требовался ровно один вызов с правильным именем и аргументами. Соблюдение просьбы вернуть один JSON-объект учитывалось отдельно. Входные токены взяты из `usage.prompt_tokens` по полному запросу.

## Что говорят официальные источники

Z.ai документирует JSON для структурированного **вывода** и для аргументов вызовов инструментов. Документированной рекомендации по формату текстового блока истории нет. Публичный шаблон передаёт строковый `content` в модель как текст. Служебные теги протокола инструментов относятся к обёртке вызовов и результатов. [Модель GLM‑5.3‑Flash](https://docs.z.ai/guides/vlm/glm-5.3-flash) · [Structured Output](https://docs.z.ai/guides/capabilities/struct-output) · [Шаблон чата GLM](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/b98f72538870b0dbf6b796581c19b99527eb6089/chat_template.jinja#L49-L94)

Предыдущий прогон проекта сравнивал роли сообщений при одинаковом JSON в блочных вариантах. Замер в 11 токенов относился к служебной Tool-паре и тому же тексту в `user`. [Предыдущий прогон](glm-history-format-evaluation.md#проверка-на-реальной-модели)

Все 42 запроса основного прогона получили HTTP 200.

В ошибочном XML-ответе модель записала старые 15 единиц в `units`, а после объекта указала свежие 11 единиц. Это противоречие засчитано как ошибка. В длинном кейсе во всех шести ответах правильно определены номер, дата, количество и агент. Пять ответов дали эти факты списком. В одном XML-ответе автор был назван в тексте как агент `stock` без отдельного поля `author`.

Компактный JSON потребовал на 11,9% меньше входных токенов, чем испытанный Markdown, и на 10,2% меньше, чем испытанный XML. Суммарно основной прогон использовал 56 440 входных и 2 521 выходной токен. Это замеры полных запросов для данных рендереров, промптов и подключения.

## Решение для проекта

Оставить `turns` в компактном JSON. Markdown дал ту же точность в этой выборке при большем входе. Текст внутри `summary` может использовать Markdown-заголовки и короткие списки. Отдельного сравнения качества генерации Markdown-сводки здесь не было.

Сценарий с графиком прошёл во всех трёх вариантах. Тест проверял чтение авторства готового артефакта и выбор Tool-вызова. Он не проверял сохранение истории, работу фильтров, реальный handoff и перерисовку графика. Один ошибочный XML-ответ не устанавливает устойчивую разницу в качестве. Для собственного SGLang и другого шаблона разметки цифры нужно проверять отдельно.
