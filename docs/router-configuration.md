# Промпт Router, routing Skills и общие ресурсы

Инструкция для **Open WebUI 0.13.3**. Базовая установка двух Functions описана
в [setup.md](setup.md).

Готовые тексты:

- [Системный промпт Router](templates/router-system-prompt.md) — скопировать
  целиком в системный промпт публичной Workspace Model Router.
- [Шаблон routing Skill](templates/routing-skill/SKILL.md) — заменить
  `{{...}}` и сохранить как `SKILL.md` в Skill OWUI.

Шаблоны применяются вручную. Обновление файлов в Git не изменяет сохранённые
промпты и Skills работающей установки. Для изменения только этих текстов новая
сборка Functions не требуется. При обновлении Functions на самодостаточные
параллельные поручения обновите также установленный промпт Router и его routing
Skills: работники больше не получают родительскую переписку автоматически.

## 1. Где хранить настройки

| Что добавляем | Где настраиваем |
|---|---|
| Общий Tool, которым пользуется сам Router | Административный `base_tool_ids` в Filter Router Preparation |
| Общий рабочий Skill самого Router | `base_skill_ids` в том же Filter |
| Агента и его routing Skill | `AGENTS` в коде установленного Filter |
| Рабочие Tools/Skills агента | В карточке Workspace Model этого агента |
| Правило, когда Router использует ресурс | В отдельном блоке системного промпта Router; подробности — в базовом Skill |

**Базовый ресурс Router не наследуется агентами при handoff или параллельном
запуске.** Если один MCP-сервер или Skill нужен и Router, и агентам, добавьте
его в базовый набор Router и отдельно в каждую нужную модель агента. Для
каждой модели права на ресурс проверяются от её владельца.

Поля Tools и Skills в карточке самого Router остаются пустыми: его базовый
набор определяется Valves Filter. Текст системного промпта объясняет способ
использования ресурса, а подключение ресурса выполняется настройками OWUI.

## 2. Как создать routing Skill

Routing Skill описывает **когда выбрать агента**. Рабочие инструкции агента
описывают **как выполнить задачу** и задаются в его модели и рабочих Skills.

1. Создайте и активируйте Skill в OWUI. Задайте понятное имя и описание:
   они попадут в каталог Router до чтения полного текста Skill.
2. Скопируйте [шаблон](templates/routing-skill/SKILL.md) в его `SKILL.md`.
3. Замените все поля:

   | Поле | Что указать |
   |---|---|
   | `{{AGENT_NAME}}` | Понятное имя агента |
   | `{{AGENT_MODEL_ID}}` | Точный Workspace Model ID агента, одинаковый во всём тексте |
   | `{{ROUTING_CRITERIA}}` | Типы запросов, признаки выбора и несколько положительных примеров |
   | `{{OTHER_ROUTE_CRITERIA}}` | Похожие запросы, которые остаются Router или относятся к другому агенту |
   | `{{EXPECTED_RESULT}}` | Результат, ради которого выбирается агент |

4. Скопируйте фактический ID созданного Skill. Владелец публичной модели
   Router должен иметь к нему доступ.
5. Добавьте пару в `AGENTS` установленного Router Preparation. Например:

   ```python
   AGENTS: dict[str, str] = {
       "analyst": "route-analyst",
       "writer": "route-writer",
   }
   ```

Здесь все IDs — примеры: замените их реальными значениями, включая ID Skill,
если OWUI создал его автоматически. Routing Skill не требуется дублировать
в `base_skill_ids` или прикреплять к рабочим Skills агента.

Пример метаданных routing Skill аналитика:

- Имя: `Аналитик данных`.
- Описание: `Анализ таблиц и показателей, сравнение периодов, поиск причин
  отклонений и подготовка выводов по данным.`
- Условия выбора: пользователь просит сравнить показатели, проверить гипотезу
  по таблице или объяснить изменение метрики.
- Другой путь: простое объяснение термина остаётся Router; стилистическая
  переработка готового текста относится к редактору.
- Ожидаемый результат: выводы с расчётами, допущениями и ссылками на данные.

## 3. Как поддерживать системный промпт

Используйте [рекомендуемый промпт](templates/router-system-prompt.md) как
постоянную основу. Он описывает выбор пути и правила управляющих Tools.
Каталог агентов, IDs Skills и схемы Tools Router получает из текущего запроса.

При добавлении агента обновляйте `AGENTS`, его routing Skill и права доступа.
Перечень всех агентов и их специализаций в системном промпте дублировать
не требуется.

Для общего ресурса добавляйте в конец промпта короткий блок:

```text
## Общие ресурсы Router

Когда [конкретный тип запроса], прочти Skill [фактический skill_id]
через view_skill и примени его инструкции.
```

Укажите условие, по которому Router должен обратиться к ресурсу, и оставьте
подробную процедуру в Skill. Если Tool используется без Skill, в блоке
промпта опишите, когда его вызывать и как использовать результат.

При переименовании или удалении ресурса обновляйте одновременно его IDs
в Valves, связанные Skills и этот блок промпта. Основные правила
`lite_delegate` и `delegate_task` сохраняйте: это ограничения исполнения.

## 4. Пример: общий поиск через MCP и базовый Skill

Предположим, в OWUI настроен MCP-сервер через StreamableHTTP:

- `info.id` подключения — `shared`;
- сервер предоставляет функцию `search_documents`;
- рабочий Skill с инструкциями поиска имеет ID `common-search-guide`.

### Подключение

В административных Valves Router Preparation добавьте ресурсы к существующим
спискам:

```json
{
  "base_tool_ids": ["server:mcp:shared"],
  "base_skill_ids": ["common-search-guide"]
}
```

Это пример полного значения двух полей. Сохраните уже настроенные IDs при
редактировании. Владельцу публичной модели Router должны быть доступны
подключение и Skill. При пользовательском OAuth/session auth используется
авторизация пользователя чата.

ID сервера подключает его разрешённые функции. Для ограничения набора
используйте `function_name_filter_list` подключения OWUI.

В этом примере ожидаемое публичное имя функции — `shared_search_documents`.
Проверьте фактически опубликованное имя по доступной схеме Tools: namespace,
переименование и сокращение длинных имён могут изменить его. В инструкции
вписывается публичное имя, а не ID `server:mcp:shared`.

### Содержимое базового Skill `common-search-guide`

```markdown
# Поиск в общей базе документов

Используй для вопросов о внутренних документах, правилах и регламентах.

1. Сформулируй запрос по вопросу пользователя и вызови
   shared_search_documents с аргументами опубликованной схемы.
2. Используй найденные документы для ответа, сохраняя ссылки на источники.
   Если данных недостаточно, обозначь, чего не удалось установить.
3. Если дальнейшая задача требует профильного агента, сначала получи результат
   поиска, затем выбери агента по routing Skill и отдельно передай исходный
   запрос через lite_delegate. Сохрани полезные результаты в текущем чате.
```

### Блок для добавления к системному промпту Router

```text
## Общая база документов

Для вопросов о внутренних документах, правилах и регламентах сначала прочти
Skill common-search-guide через view_skill(id="common-search-guide").
Следуй его инструкции поиска и сохраняй ссылки на найденные источники.
Простой вопрос закрой самостоятельно; профильную обработку передай
подходящему агенту после получения результатов поиска отдельным lite_delegate.
```

Общий Tool принадлежит текущему набору Router. Если агенту потребуется
самостоятельно повторить поиск, прикрепите `server:mcp:shared` к его модели
и разрешите подключение владельцу этой модели. Агент использует собственный
промпт; добавленный блок Router автоматически к нему не переносится.

## 5. Если нужен только общий Tool

Добавьте его ID в `base_tool_ids`. `base_skill_ids` может остаться пустым.
Для локального Tool указывается ID записи Tool; для MCP — ID вида
`server:mcp:shared`. Один Tool или сервер может публиковать несколько функций.

Пример короткого блока промпта для того же MCP-поиска без базового Skill:

```text
## Общая база документов

Для вопросов о внутренних документах, правилах и регламентах используй
доступную функцию shared_search_documents с аргументами её схемы.
Основывай ответ на найденных данных и сохраняй ссылки на источники.
Если затем нужна профильная обработка, дождись поиска и передай запрос
выбранному агенту отдельным lite_delegate.
```

Выберите один из двух вариантов инструкции поиска — через Skill либо
непосредственно в промпте. Используйте в тексте проверенное публичное имя.

## 6. Если нужен только базовый Skill

Добавьте его фактический ID в `base_skill_ids`; набор Tools меняйте только
при необходимости. Например, Skill `common-answer-format` может задавать
порядок краткого ответа, определения терминов и оформления источников.

```text
## Общий формат самостоятельного ответа

Перед самостоятельной подготовкой краткой справки прочти
view_skill(id="common-answer-format") и примени его правила оформления.
```

Содержимое Skill должно соответствовать задаче и доступным возможностям
Router. Для применения тех же правил агентом прикрепите Skill к его модели
и задайте условие чтения в собственных инструкциях агента.

## 7. Как проверить обновление

### Самодостаточные параллельные поручения

Для `delegate_task` каждый `task` должен быть понятен без истории основного
чата. Router включает действие, необходимые факты, точные даты, значения и IDs,
ограничения и ожидаемый результат. Если ранее пользователь указал ФТП
`FTP-42`, период `2026-11-01`–`2026-11-30` и формат «краткая таблица», то
просьба «сделай два параллельных вызова в этот агент, покажи прогноз ФТП»
может дать такую группу (IDs агента и данные здесь — пример):

```text
delegate_task(agent_id="forecast-agent", task="Покажи прогноз ФТП FTP-42 за период 2026-11-01–2026-11-30. Верни краткую таблицу.")
delegate_task(agent_id="forecast-agent", task="Покажи прогноз ФТП FTP-42 за период 2026-11-01–2026-11-30. Верни краткую таблицу.")
```

Это два отдельных исполнения одной модели, каждое выполняет своё поручение.
Фразы «вызови двух агентов», «выполни дважды» и «см. предыдущие сообщения»
не нужны в этих поручениях. Количество запусков задаётся числом Tool calls.
Исходные значения берутся из реального запроса; пример не задаёт значения
по умолчанию для отсутствующих параметров.

Если требуется полный документ из входных вложений, укажите его фактический
ID в `file_ids` соответствующего элемента и объясните в `task`, как его
использовать. Вложения проверяются на доступность. Не заменяйте обязательное
полное содержание приблизительным пересказом. Если необходимых данных нет,
Router уточняет их до запуска либо явно описывает ограничение поручения;
работник сообщает об обнаруженном недостатке данных.

При установке новой пары Functions перенесите эти правила из
[актуального шаблона](templates/router-system-prompt.md) в сохранённый системный
промпт публичной модели Router, сохранив свои общие ресурсы. Обновите связанные
routing Skills по [шаблону](templates/routing-skill/SKILL.md). Запись в Git
не обновляет их в OWUI. Обычный `lite_delegate` продолжает передавать переписку.

### Проверочные запросы

Сохраните предыдущие Valves и текст промпта, примените настройки и откройте
новый запрос через публичную модель Router. Проверьте такие случаи:

| Запрос | Ожидаемое поведение |
|---|---|
| Общий вопрос без нужды в ресурсах | Самостоятельный ответ |
| Вопрос по общей базе документов | Чтение базового Skill, если он настроен, затем вызов общего Tool |
| Профильный вопрос | Чтение подходящего routing Skill и отдельный `lite_delegate` |
| Поиск с последующей профильной обработкой | Поиск завершается перед handoff; полезные результаты доступны как данные |
| Две независимые задачи при доступном parallel | Два отдельных delegate_task в одной генерации, затем итог или handoff после полного успеха |
| Два параллельных вызова одного агента | Два элемента с одним `agent_id`, каждый работник выполняет поручение один раз |
| Параллельное поручение со ссылкой на ранние параметры | В `task` переданы сами даты, значения и IDs; работнику не нужна переписка |
| Та же задача от обычного пользователя | Учитывается его доступ к моделям и пользовательская авторизация MCP |

Раскройте реальные вызовы Tools в истории. Для управляющего вызова должны
быть отдельные генерации: один `lite_delegate` либо несколько `delegate_task`.
Обычный текст «передаю агенту» сам по себе передачу не выполняет.

При проблеме верните предыдущие списки Valves и связанный с ними блок промпта.
Проверьте точные IDs, активность Skill, права владельца модели и опубликованные
имена функций. Результаты проверки шаблонов не заменяют проверку поведения
выбранной LLM в вашей установке.
