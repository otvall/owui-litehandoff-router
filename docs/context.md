# Контекст разговора

Один чат сохраняет общую переписку при смене исполнителя. Например:

| Новое сообщение пользователя | Кто начинает | Кто завершает |
| --- | --- | --- |
| Вопрос профиля A | Router | A после `lite_delegate` |
| Вопрос профиля B | Router | B после нового `lite_delegate` |
| Общий вопрос | Router | Router самостоятельно |

Выбор действует только до конца текущего пользовательского запроса. Продолжение
после Tool, включая служебное `user`-сообщение OWUI с изображением результата,
остаётся у выбранного агента. Новый HTTP-запрос с сообщением пользователя проходит
обязательный Preparation заново: новый персональный реестр и базовые Valves,
пустое состояние handoff. Старый receipt клиента не восстанавливает исполнителя.

## Исходная история и представления

Preparation сохраняет копию текущей ветки, полученной от OWUI. На native
продолжениях обновляется хвост текущего запроса, а исходный префикс сохраняется.
Комплект не удаляет сообщения или Tool results из БД. Обычный handoff
продолжает основной чат; только `lite_parallel` создаёт внутренние дочерние чаты.
Каждой модели готовится отдельное представление этой ветки.

Router получает пользовательские сообщения, видимые ответы всех исполнителей
и справку о завершённых Tool exchanges за всю доступную ветку. Справка содержит
исполнителя, Tool, аргументы и результат как исторические данные. Она не
публикует schemas или callables чужих Tools. Чтения Skills представлены только
операцией, ID и статусом, без старого текста инструкций, файлов или поисковых
фрагментов. Собственные допустимые чтения Router в текущем запросе остаются
в его нативной Tool-цепочке.

Агент получает ту же видимую переписку и собственный системный промпт. Из
служебной истории ему передаются только завершённые exchanges, однозначно
принадлежащие этому Model ID и допустимые в его текущем наборе Tools. Трасса
Router, передача, системные инструкции и рабочие Skill-загрузки других агентов
исключаются. Одинаковое имя `lookup` у A и B не делает результаты общими.
После отключения Tool от карточки его старые exchanges также исключаются
из представления агента; исходная история и справка Router их сохраняют.

Общие пользовательские файлы, изображения и видимые ответы доступны по обычным
правилам OWUI. Если A нужен сырой результат B, отсутствующий в общем ответе
или доступном файле, комплект не подставляет его как собственный Tool result A.
Для обмена результатами независимых заданий используется `lite_parallel`.

## Данные параллельных заданий

Router передаёт работнику конкретное задание, исходный вопрос и видимую
переписку текущей ветки как данные. Системные промпты, Tool chains и прочитанные
рабочие инструкции Router/других работников туда не входят. Файлы задания
выбираются из доступных вложений родителя через `file_ids` и проверяются перед
запуском. У каждого задания отдельные история, Skill state, callable и MCP.

После ожидания всей группы Router получает упорядоченные полные результаты
с авторами, исходами, файлами и ссылками. Сборщик читает сохранённый дочерний
ответ, а не усечённый native summary. Незавершённый ответ, ошибка, пауза или
`finish_reason=length` не подтверждают успех. Сырые Tool traces остаются
в дочернем чате. Публичный результат не содержит tickets и credentials.

При полном успехе отдельный `lite_delegate` передаёт итоговую задачу C в
основном чате. Подготовка C добавляет проверенный пакет A/B сообщением с ролью
`user`, явно обозначенным как входные данные с авторами. Чужой результат не
становится собственным Tool result C. Переданные файловые ссылки повторно
авторизуются и добавляются к эффективным вложениям C; исходные вложения
пользователя сохраняются. При удалённом или недоступном файле подготовка
возвращает ошибку. Пути вроде `/tmp/forecast.csv` переносимыми файлами не считаются.

Переполнение контекста остаётся явной ошибкой провайдера. Автоматического
усечения, пересказа или повторного запуска работников нет. После неполной
группы финальная передача блокируется, Router может сообщить частичные результаты.
Новое пользовательское сообщение создаёт пустое состояние группы. Сохранённый
Tool result с результатами и ссылками остаётся историческими данными Router.

## Авторство и целостность цепочки

Совпадение `tool_call_id` само по себе недостаточно: пары сопоставляются внутри
конкретного пользовательского запроса и группы вызовов. Неполные и
противоречивые пары исключаются из нативной истории. Если завершённая пара есть,
но авторство не подтверждено, Router видит её с неизвестным исполнителем,
а агент её не получает.

Текущее авторство фиксируется по фактическим вызовам провайдера. Завершённый
настоящий вызов `lite_delegate` сохраняет сведения о Router в своём Tool result;
дальнейшая история связывается с выбранным Model ID. Это не зависит от
сегодняшнего состава реестра. Marker-подобный текст ответа или другого Tool
не переключает текущего исполнителя: нужны server-side pending и завершённая
соответствующая пара. Для старых чатов без достаточной информации авторство
не угадывается по имени Tool.

Tools получают `__messages__` своего подготовленного представления после
допустимых destination inlets. Штатный callable refresh не заменяет его внешней
историей Router. Обновления `__files__` при этом сохраняются. Две последовательные
операции агента видят собственную текущую цепочку, включая результаты-изображения.

## Свежие Skills и ограничения

Загрузка настроенных ресурсов использует владельца выбранной Workspace Model;
у Router — владельца публичной Router-модели. Это позволяет работать без
отдельных grants пользователя на Tools/Skills/MCP и не расширяет их набор.
Локальные Tools получают пользователя чата и его UserValves, внешние вызовы —
его пользовательскую авторизацию. Только ограниченные Skill readers используют
контекст владельца. Родительский транспорт Router не становится владельцем
ресурсов параллельного работника. При смене владельца, отзыве прав или отсоединении
ресурса старый callable не продолжает работу с прежними возможностями.
Доступ к чатам и обычным файлам по-прежнему проверяется от пользователя чата.

На каждом вызове актуальны карточка модели, её параметры, Tools и Skills.
При новом сообщении полные старые результаты Skill readers не воспроизводятся
даже тому же агенту. Модель получает актуальный каталог и при необходимости
читает инструкции заново. В пределах текущего запроса допустимое собственное
чтение сохраняется; scope и штатные права проверяются независимо. Подробности —
в [Skills](skills.md).

Автоматического пересказа, усечения, повторного исполнения Tools для
восстановления данных или переноса сырых чужих результатов в MVP нет.
В OWUI требуется `chat.context_compaction.enable=false`; если сжатие включено,
Pipe прекращает генерацию с явной ошибкой настройки. Комплект не восстанавливает
ветку, уже пересказанную внешним механизмом до Preparation. Ошибка ограничения
контекста от провайдера передаётся без fallback и повторного запуска действий.

Текущая версия допускает одну передачу одному агенту за запрос, без вложенных
или конкурирующих передач. Она не обеспечивает отдельную долговременную память,
произвольный обмен файловыми системами агентов или поддержку других версий OWUI.

## Проверки

`tests/test_preparation.py` проверяет новое состояние на следующем сообщении.
`tests/test_history.py` проверяет несколько прошлых запросов,
повторный выбор A, одинаковые имена Tools, повторяющиеся IDs, неоднозначность,
отключённые attachments и подавление старых Skill-инструкций.
`tests/native/test_history.py` сверяет fixture со штатной группировкой v0.12.3.
`tests/native/test_chain.py` проходит настоящий streaming Tool loop с двумя
последовательными Tools, изменением inlet, пользовательским вложением,
служебным изображением и обновлением файлов, затем переключение A → B → Router
в том же чате. Он проверяет ошибки провайдера и переполнение, а также ошибку
после выполненного Tool без повторного исполнения. Транспорт генерации в этом тесте
заменяет тестовый провайдер; это не браузерная проверка.
Фактические результаты и оставшиеся проверки — в [приёмке](acceptance.md).
