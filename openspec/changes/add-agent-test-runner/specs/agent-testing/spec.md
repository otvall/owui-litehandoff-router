# Spec Delta

## Purpose

Позволяет проверять Router и зарегистрированные Workspace Models на воспроизводимых пользовательских сценариях. Отчёт связывает решение о маршруте, фактическое исполнение и отображение результата с конкретной конфигурацией стенда.

## ADDED Requirements

### Requirement: Cases declare inputs and expected behavior

Инструмент SHALL принимать версионированный набор кейсов с уникальными ID, ролью тестового пользователя, маршрутом запуска, репликами, ссылками на фикстуры и ожидаемыми проверками. Кейсы через Router SHALL допускать явно заданные альтернативы решения. Ссылки на фикстуры и структуру выбранного набора SHALL проверять до запросов к модели.

#### Scenario: Boundary request has multiple accepted routes

- **WHEN** кейс разрешает два конкретных маршрута или уточнение с заданным критерием
- **THEN** инструмент оценивает фактическое решение по указанным альтернативам
- **AND** случайное делегирование другому агенту не засчитывается

#### Scenario: Fixture or case definition is invalid

- **WHEN** в выбранном наборе есть повторяющийся ID, неизвестная роль, недопустимая проверка или отсутствующий файл
- **THEN** инструмент сообщает, какой кейс и поле требуют исправления, до вызовов модели

### Requirement: Coverage accounts for the configured registry and user roles

Инструмент SHALL сопоставлять кейсы с ожидаемым `AGENTS` установленной тестовой конфигурации и учитывать персональную доступность модели. Покрытие SHALL показываться по каждой зарегистрированной модели, включая модели без кейсов, недоступные модели и проверки, отфильтрованные при запуске.

#### Scenario: A hidden model and an inaccessible model are registered

- **WHEN** A скрыта в селекторе и разрешена обычному пользователю, а B зарегистрирована и этому пользователю запрещена
- **THEN** A остаётся кандидатом на положительную проверку, а B отражается как недоступная для этой роли
- **AND** запрет доступа, ожидаемый негативным кейсом, оценивается отдельно от недостающего положительного покрытия B

#### Scenario: A registered model has no positive case

- **WHEN** ни один кейс набора не ожидает успешного запуска зарегистрированной модели C
- **THEN** отчёт показывает пробел по C, даже если все выполненные кейсы прошли

### Requirement: Execution uses an isolated Open WebUI test deployment

Инструмент SHALL запускать запросы штатным путём OWUI 0.13.3 под заданным тестовым пользователем. Режим с управляемым провайдером SHALL поддерживать локальный прогон. Режим реальных LLM SHALL запускаться явно и сохранять промпты, Skills и параметры тестируемой конфигурации.

#### Scenario: Same scenario is executed in both modes

- **WHEN** оператор запускает выбранный кейс с управляемым провайдером и затем с реальными LLM
- **THEN** оба прогона сохраняют результаты отдельно и указывают режим, конфигурацию и фактические модели

#### Scenario: Direct control uses the same actor

- **WHEN** кейс предусматривает прямой запуск агента и тестовому пользователю разрешён этот путь
- **THEN** инструмент выполняет прямой запрос под тем же пользователем и отмечает способ запуска в отчёте

#### Scenario: Target environment cannot be verified

- **WHEN** конфигурация целевого стенда не подтверждена или обнаружено несовпадение с ожидаемой версией OWUI либо выбранной сборкой Functions
- **THEN** инструмент сообщает причину и не начинает прогон

### Requirement: Route is scored from calls and executed outcomes

Инструмент SHALL проверять форму маршрута, точные Workspace Model IDs, успешное чтение routing Skill в текущем ходе и фактическое исполнение. Для параллельного кейса инструмент SHALL сверять границы генераций `delegate_task` и связь каждого call ID с его терминальным результатом.

#### Scenario: Router claims handoff in prose

- **WHEN** Router пишет, что передал запрос, но исполнение ожидаемого агента не подтверждено
- **THEN** проверка handoff завершается ошибкой

#### Scenario: Two assignments reach the same agent

- **WHEN** разметка требует два параллельных задания одному Workspace Model ID
- **THEN** успех засчитывается при двух вызовах в одной генерации и двух отдельных подтверждённых выполнениях
- **AND** повтор одного результата и отправка заданий отдельными генерациями считаются ошибкой

#### Scenario: One member of the group fails

- **WHEN** в кейсе ожидается частичный результат и один исполнитель завершается ошибкой
- **THEN** инструмент проверяет реальные исходы заданий, отсутствие финального handoff и критерий сообщения пользователю, заданный кейсом

### Requirement: Agent skills and outputs have their own checks

Кейс SHALL позволять оценить чтение рабочего Skill, фактический вызов Tool, данные или артефакт результата отдельно от выбора маршрута. Проверка, которой требуется оценка смысла, SHALL оставаться на ручной проверке до появления подтверждённого результата по критерию кейса.

#### Scenario: Correct agent calls the wrong Tool

- **WHEN** Router правильно выбирает агента, но тот пропускает обязательный рабочий Skill или Tool
- **THEN** отчёт показывает успешный выбор маршрута и провал проверки агента

#### Scenario: Clarification requires a meaningful question

- **WHEN** кейс требует вопроса о цели пользователя, а структура вызовов подтверждает отсутствие делегирования
- **THEN** отсутствие делегирования оценивается автоматически, а смысл вопроса помечается для проверки по указанному критерию

### Requirement: Inline Visualizer validates the agent tool chain

Инструмент SHALL поддерживать закреплённую пару Inline Visualizer Tool и рабочего Skill 2.2.3. Проверки SHALL различать чтение routing Skill Router и чтение рабочего Skill агентом, проверять вызов `visualize`, блок ответа с маркерами и принадлежность сохранённого embed ожидаемому сообщению.

#### Scenario: Similar requests differ in whether a visual was requested

- **WHEN** один кейс прямо просит визуализацию, а второй просит объяснить те же данные
- **THEN** для первого проверяется чтение рабочего Skill по его фактическому ID, вызов `visualize` и завершённый блок `@@@VIZ-START` / `@@@VIZ-END`
- **AND** для второго проверяется отсутствие вызова `visualize`

#### Scenario: Another agent receives history after visualization

- **WHEN** проверяемая конфигурация поддерживает фильтрацию истории Visualizer и в последовательности A → B → A агент A ранее создал визуализацию
- **THEN** инструмент проверяет заглушку у B и исходный блок при возврате к A по контракту проверяемой конфигурации
- **AND** сохранённый исходный ответ остаётся доступен для отрисовки

### Requirement: Browser checks prove rendering and interaction

Для браузерного кейса инструмент SHALL проверять видимый результат в iframe и эффект действия пользователя. Он SHALL различать основное и дочернее сообщения, фиксировать восстановление после перезагрузки без нового Tool или LLM вызова и сохранять свидетельства при провале.

#### Scenario: Worker renders while the viewer stays in the main chat

- **WHEN** пользователь ждёт завершения локального параллельного кейса в основном чате без browser callback дочернего Tool
- **THEN** проверка фиксирует завершение Tool в контрольных восьми секундах и отсутствие embed работника в основном сообщении
- **AND** переход по «Открыть выполнение» показывает SVG и кнопку, меняющую видимое состояние

#### Scenario: Child executions render independently

- **WHEN** в A+B или A+A созданы две визуализации
- **THEN** каждый дочерний чат показывает свой маркер и интерактивное состояние
- **AND** перезагрузка или открытие ссылки в новой сессии владельца восстанавливает визуализацию без новой генерации
- **AND** пользователь без доступа не получает содержимое дочернего чата

#### Scenario: Ordinary handoff saves rendering in the main chat

- **WHEN** обычный handoff создаёт визуализацию в основном чате
- **THEN** браузерная проверка подтверждает видимый интерактивный результат в сохранённом основном сообщении

### Requirement: Reports distinguish failures from unverified outcomes

Инструмент SHALL сохранять машиночитаемый отчёт по всему выбранному набору с покрытием, идентификаторами конфигурации, наблюдениями по проверкам и исходами `passed`, `failed`, `blocked` или `needs_review`. Отчёт и артефакты SHALL исключать учётные данные.

#### Scenario: Provider is unavailable for one case

- **WHEN** провайдер недоступен до получения решения по одному кейсу
- **THEN** кейс отмечается как `blocked` с причиной, соседние независимые кейсы продолжаются

#### Scenario: Backend passes while browser check fails

- **WHEN** Tool успешно сохранил embed, но iframe остался пустым или клик не изменил состояние
- **THEN** отчёт сохраняет оба результата, указывает провал браузерной проверки и прикладывает доступное свидетельство
- **AND** выбранный набор считается пройденным только при успешном прохождении всех обязательных проверок
