# Design

## Context

Штатный HTTP-путь OWUI 0.13.3 уже использован в `tools/native_context_http.py`. `tools/real_llm_context_acceptance.py` показывает, как записывать вызовы модели, но задаёт специальные промпты стенда. Браузерный gate Visualizer содержит закреплённые Tool/Skill и готовый SVG, а его провайдер и проверки всё ещё опираются на один вызов `lite_parallel`. Текущий контракт связывает вызовы `delegate_task` с результатами по отдельным call IDs.

## Goals / Non-Goals

CLI пригоден для ручных прогонов нужного агента и автоматических прогонов всей тестовой конфигурации. Обязательный браузерный контроль воспроизводим локально. Область изменения ограничена стендом, инструментами и отчётностью. Запускать средство из чата в роли Workspace Tool или вводить новый runtime API в этом изменении не требуется.

## Decisions

### Профиль стенда и каталог

CLI принимает локальный профиль заранее подготовленного стенда и каталог кейсов. Для эталонного профиля тестовый bootstrap поднимает конфигурацию на чистом OWUI 0.13.3 из согласованной пары standalone Functions и тестовых ресурсов. Настройки проверяемой конфигурации импортируются из явного снимка. Профиль указывает URL и идентификатор стенда, Router Workspace Model ID, ожидаемый `AGENTS`, базовые модели, привязки ресурсов и роли. Учётные данные передаются отдельно и не входят в профиль.

Перед первым чатом CLI сверяет идентификатор стенда, версию OWUI, хеши установленных Functions и установленный реестр со снимком. Для литерального `AGENTS` достаточно разобрать присваивание из административного экспорта без исполнения кода. Если снимок нельзя подтвердить, прогон останавливается. Роли в локальной фикстуре включают владельца ресурсов, обычного пользователя с доступом к моделям и обычного пользователя без нужного доступа. Владельца используют для подготовки и сверки конфигурации, а диалоги идут с полномочиями роли из кейса. Одна выгрузка списка моделей от администратора не отражает персональный каталог Router.

### Формат кейсов и покрытие

Версионированный JSON позволяет обойтись стандартной библиотекой Python при загрузке. Кейс задаёт `id`, роль, входной путь (Router или конкретная модель), реплики и относительные пути к фикстурам, допустимые решения, проверки и критерии ручной оценки. Для обязательных проверок используются известные типы с параметрами. Отдельная декларация вида `expected.agent_id` привязывает положительный кейс к Workspace Model ID даже при запуске через Router. Отрицательный кейс может назвать модель, ошибочный вызов которой он ловит.

Отчёт сверяет зарегистрированные модели с полным набором размеченных кейсов и отдельно показывает, какие из них выбраны и выполнены в данном запуске. Для каждой модели отмечаются профильный запрос, пограничный или негативный пример и проверка ключевого ресурса, когда ресурс есть. Начальный набор поставляется на синтетическом каталоге. Кейсы конкретной установки добавляются после сверки её реестра и ресурсов.

### Режимы запуска и доказательства

Оба режима используют штатный HTTP или браузерный чат OWUI. Каждый независимый кейс начинает новый чат, а реплики одного кейса используют его историю. Пользовательские формулировки и ожидания общие. Управляемый локальный провайдер отвечает по сценарию, поэтому подходит для регрессий и CI. Режим реальных LLM явно выбирается при запуске и использует реальные привязки базовых моделей и рабочие параметры тестового профиля. Для интеграций с внешними данными применяются тестовые учётные записи, данные и подключения.

Запись на стороне управляемого провайдера или наблюдение на границе провайдера в изолированном стенде дают фактический номер генерации, модель и Tool calls. Сохранённые `output` и записи дочерних чатов подтверждают результаты, статусы и связи. Для `delegate_task` проверяется соответствие call ID → Tool result → дочерний чат. История OWUI может объединять вывод нескольких продолжений, поэтому по ней одной нельзя определять границу генерации. Отсутствующую обязательную трассировку отмечаем как блокировку проверки с причиной.

Для проверки маршрута, ресурсов агента и браузера храним отдельные результаты. Смысловые критерии можно проверять по результатам вручную. До оценки они имеют статус `needs_review`. JSON содержит матрицу, результаты по кейсам, ссылки на очищенные свидетельства, ревизию, версии и хеши конфигурации, режим и ID моделей. Достаточно одного машинного формата и короткой сводки в терминале. CLI возвращает успешный код только когда выбранные обязательные проверки пройдены. Фильтры и пробелы покрытия отражаются в явном виде.

### Браузерная проверка

Используем Python Playwright и headless Chromium отдельной зависимостью стенда. Установка браузера и системных зависимостей выполняется при подготовке окружения. Для локального кейса отключён внешний сетевой доступ к страницам и оставлен штатный HTTP/WebSocket OWUI. Scripts и Same Origin включаются в профиле синтетического пользователя. Tool/Skill проверяются по существующему manifest, используются `security_level=offline` и `chime=false`.

Переиспользуем локальный SVG, его маркер и стабильные ID из `tools/visualizer_gate_provider.py`. Обновляем провайдер и проверку backend gate под `delegate_task`. Playwright открывает iframe, ждёт видимый SVG и проверяет клик по `#vg-toggle` с изменением `#vg-state`. Reload и новая сессия проверяются через сохранённую ссылку и счётчики вызовов. Для обычного handoff проверяется сохранённое основное сообщение. Для A+B и A+A браузер открывает два выполнения и проверяет разные маркеры и независимое состояние. Свидетельства при провале сохраняются из синтетического профиля с исключением секретов.

У реальной модели разметка графика меняется. Для таких кейсов используем критерии содержимого и взаимодействия из самого кейса, без привязки к ID синтетической фикстуры. Проверка A → B → A активируется в профиле, где заявлена фильтрация чужих блоков Visualizer, и использует контракт ветки `add-context-overflow-prevention`.

## Risks / Trade-offs

- Изменение сборки или провайдера между прогонами затрудняет сравнение. Отчёт фиксирует режим, образ, хеши и фактические модели.
- Браузерная фикстура зависит от готовности дочернего ответа и загрузки iframe. Проверки ждут целевое состояние в пределах таймаута, а при сбое сохраняют контекст наблюдения.
- Доступность провайдера и ручная проверка ограничивают автоматический вывод о качестве. Эти причины имеют отдельные статусы, независимые кейсы продолжаются.
- Локальный SVG подтверждает работу без CDN. Для Skill, реально требующего библиотеку или внешний ресурс, нужен свой кейс с явно объявленной зависимостью.

## Migration Plan

Развернуть новый тестовый профиль, запустить native и управляемую HTTP-проверку, затем Chromium gate. После подтверждения фикстур загрузить снимок проверяемой конфигурации и добавить кейсы по её моделям. Удаление одноразовой среды освобождает её БД и тестовые ресурсы. Изменения рабочих установок для перехода не нужны.
