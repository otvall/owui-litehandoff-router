# Design

## Context

См. proposal.md. Сейчас parallel.py формирует entry.input из видимой родительской переписки до user_boundary и дополнительного user-сообщения Assigned task. prepare_worker подставляет input в body.messages, создаёт состояние worker=True и выбирает агента. prepare_model строит контекст из state.source; refresh_source обновляет хвост на продолжениях.

Пользователь сообщил конкретный случай: общий запрос требует двух параллельных вызовов одного агента, сохранённое поручение содержит «[Задание UID] покажи прогноз ФТП», а работник обещает выполнить прогноз дважды последовательно. Поручение присутствует в сохранённом дочернем сообщении; точный payload сбойной модели ещё не получен. Принято изменить границу входных данных независимо от того, насколько конкретная модель соблюдает пояснение о справочной переписке.

Действующий Worker inputs and runtime remain isolated требует всей видимой переписки. Shared dialogue follows the selected agent сформулирован для агента без исключения работников. Обе нормы согласуются delta-спецификациями; исходные сообщения в БД сохраняются.

## Goals / Non-Goals

**Goals:** единая граница контекста задания от первого вызова работника до завершения его собственной Tool-цепочки; два независимых запуска одной модели выполняют по одному поручению.

**Non-Goals:** вложенная оркестрация, новые поля API, отдельная LLM для пересказа, автоматический доступ к родительской истории, изменение обычного handoff или передачи полных результатов группы.

## Decisions

### 1. Router формирует самодостаточное поручение в существующем task

Router использует доступную ему историю при обычной генерации lite_parallel и включает действие, необходимые факты, точные даты/значения/IDs, ограничения и ожидаемый результат. Просьба об организации группы не копируется как действие работника. Обновляются описание task, рекомендованный Router-промпт, routing Skill и руководство. Если фактов не хватает, Router уточняет их до запуска либо явно передаёт ограничение; работник сообщает об обнаруженном недостатке данных.

Отдельное поле context пока не вводится: структурированные разделы в task достаточны и сохраняют текущую схему. Отдельный вызов модели для подготовки контекста добавил бы стоимость и второй источник искажений без необходимости.

### 2. Родительская переписка не добавляется в input работника

Дочерний исходный контекст содержит назначенное user-поручение и выбранные file_ids. prepare_worker и begin используют этот контекст как source/original_source. На дальнейших вызовах сохраняются только он и собственные допустимые продолжения работника. Не допускается восстановление родительской истории из body, metadata, chat_context или через Tool callable refresh. Проверяется фактический payload после Filter и подготовки агента, а не только запись дочернего чата.

Нужные выдержки Router может включить в task как данные. Полные документы передаются доступными вложениями; обязательное полное содержание и точные значения не заменяются приблизительным пересказом. Поручение — заранее определённый вход отдельной задачи, а не скрытое усечение истории после ошибки лимита.

Альтернатива с полной перепиской и одним системным пояснением оставляет рядом конкурирующие цели и расходует контекст на ненужную историю; она не выбрана.

### 3. Короткое системное пояснение роли дополняет промпт агента

По подтверждённому внутреннему worker-состоянию добавляется указание выполнять своё поручение; Router уже управляет группой и числом запусков. Оно не обещает недоступных возможностей. Динамический task остаётся user-сообщением, не становится системной инструкцией. Собственный системный промпт модели сохраняется. Указание не дублируется при повторной подготовке.

Формулировка не запрещает несколько действий, если их явно требует само поручение. Запрещено повторять всю задачу только из-за родительского количества запусков. lite_parallel, lite_delegate и delegate_task работнику по-прежнему не выдаются.

### 4. Обычный handoff и каноническая история сохраняются

Для lite_delegate сохраняется видимая переписка, в том числе когда финальный агент получает полные результаты успешной группы. Изменяется только контекст параллельных работников. Исходная история основного чата не переписывается, а полные подтверждённые результаты работников собираются прежним способом.

## Risks / Trade-offs

- Router может опустить важные ограничения → явный контракт task, примеры переноса точных параметров и проверка случаев со ссылкой на раннюю реплику.
- Неполное поручение нельзя достоверно определить проверкой непустой строки → структурные проверки не заявляются как гарантия смысловой полноты; отдельно проверяется реальная модель, при недостатке данных нужен явный ответ.
- Старый пользовательский Router-промпт рассчитывает на доступ работника к переписке → обновить опубликованные рекомендации и описать необходимость обновления установленного системного промпта.
- Native продолжение или destination inlet восстановит внешний контекст → регрессии первого payload, Skill/Tool-продолжений, callable refresh и изоляции двух запусков одной модели.
- Детерминированный провайдер скрывает смысловую ошибку → отдельно провести реальный сценарий пользователя; заглушка проверяет только транспорт и состав контекста.
- Подготовленное поручение не помещается в окно → явная ошибка без скрытого сокращения или повторного запуска действий.

## Migration Plan

Обновить документацию и установленный пользователем Router-промпт под самодостаточные task, пересобрать согласованную пару Functions и проверить их в изолированной OWUI 0.12.5. Данные и форма аргументов не мигрируют. Поведение контекста несовместимо с прежним ожиданием доступа к переписке; обновление промпта должно сопровождать установку экспортов. Откат — предыдущая согласованная пара Functions и соответствующие инструкции Router.
