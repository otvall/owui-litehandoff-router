# Design

## Context

Мотивация и согласованная граница находятся в [proposal.md](proposal.md), наблюдаемое поведение — в [agent-task-visualizations](specs/agent-task-visualizations/spec.md). Design нужен из-за миграции внешнего плагина и взаимодействия браузерных событий с изолированным исполнением.

Наблюдения по проекту:

- `parallel.py` запускает `subagents.delegate` через публичную Router-модель; `prepare_worker` связывает новый scope с дочерним chat/message и выбранным агентом. В дочерней задаче Router LLM не вызывается.
- `model_execution.py` передаёт события текущего дочернего запроса в загрузчик Tools. `owui_adapter.py` загружает ресурсы с правами владельца модели, сохраняет пользователя исполнения и использует native binder. `binding.py` сохраняет привязку при обновлении callable.
- `collect_result` собирает текст и файлы. Перенос `embeds` в основной чат отсутствует; это соответствует выбранной границе. Текстовый результат группы по-прежнему может содержать HTML как данные, но не должен автоматически становиться embed основного сообщения.
- Текущая приёмка в `tools/parallel_acceptance.py` доказывает native цепочки, файлы и доступ к дочерним чатам. Проверки исполнения настоящего Inline Visualizer и его DOM пока нет. HTTP-проба со случайным `session_id` не воспроизводит ожидание активной браузерной сессии.

Что установлено во время исследования:

- В [Inline Visualizer 2.1.1](https://github.com/Classic298/open-webui-plugins/blob/5f549492316505af4ec6f2de0bdee781b1e778a5/inline-visualizer-v2/tool.py) `render_visualization` ожидает браузерное определение языка без собственного таймаута. Изолированный запуск оставался pending после шести секунд; ответ браузера немедленно освобождал вызов.
- В [OWUI 0.12.3](https://github.com/open-webui/open-webui/blob/v0.12.3/src/lib/components/chat/Chat.svelte#L1440) `execute` обрабатывается для открытого чата. Вызов из другого дочернего чата на исходной сессии основного чата не получает этот callback. Серверный caller передаёт дочерние chat/message IDs; при настройке socket timeout по умолчанию ожидание не ограничено самим caller. Общий deadline группы остаётся внешней границей.
- В исследованном Tool 2.2.3 ожидание определения языка ограничено пятью секундами, оболочка публикуется событием `embeds` уровня сообщения. Изолированный вызов завершился за пять секунд без ответа браузера. [Исправление native embeds](https://github.com/Classic298/open-webui-plugins/commit/f7aa83c77f7355da94537c08f141c70be00208b5) появилось после 2.1.1.

Это объясняет воспроизводимую причину зависания, но не является пройденной сквозной проверкой 2.2.3 с продуктовым Router и браузером. Такой gate обязателен в реализации.

## Goals / Non-Goals

**Goals:**

- Доказать совместимость через существующий native путь, включая неотвечающий браузер, сохранение сообщения и настоящее взаимодействие с iframe.
- Зафиксировать минимальное обновление установленного визуализатора; исправлять Router только при отдельном воспроизведённом дефекте интеграции.
- Сохранить идентичность каждого дочернего исполнения при одновременной работе и просмотре.

**Non-Goals:**

- Поддерживать неизменённый Visualizer 2.1.1 или форкать его ради обратной совместимости.
- Создавать общий механизм перенаправления browser RPC всех Tools, собственный renderer, автоматическую миграцию стороннего плагина или патч frontend OWUI.
- Гарантировать работу произвольных CDN-библиотек, сетевых данных и браузерных возможностей, не участвующих в контрольном сценарии.

## Decisions

### 1. Согласованный upstream-комплект и проверка до изменения runtime

Базовая проверяемая конфигурация — Tool 2.2.3 и `SKILL.md` из того же upstream snapshot. Обозначение комплекта 2.2.3 в proposal/spec относится к версии Tool и согласованному с ним Skill; у самого Skill не требуется отдельное совпадающее поле версии.

Для положительного gate использовать snapshot `bcc224db138b6901a8d4b99e7f8a8859bea5629b` репозитория Classic298/open-webui-plugins, предварительно сверив версию и наличие обоих файлов. Для отрицательного контроля — snapshot 2.1.1 `5f549492316505af4ec6f2de0bdee781b1e778a5`. Сохранить ссылки и SHA-256 фактически использованных файлов в manifest приёмки; не получать плавающий `main` во время исполнения. Тестовый установщик принимает заранее подготовленные локальные файлы, сверяет manifest и работает без загрузок в runtime.

Первый положительный прогон выполняется на текущих двух exports и немодифицированном upstream Tool. При успехе change ограничивается проверками, manifest и документацией; дополнительная логика Router не нужна. Старый Tool используется только как отрицательный контроль с ограниченным временем и обязательной отменой, а не как зависшая бесконтрольная фоновая задача.

Альтернатива — сразу менять обработку browser RPC в Router. Она затронула бы все Tools и скрыла бы, достаточно ли уже сделанных upstream-исправлений, поэтому не выбрана.

### 2. События и DOM остаются привязанными к дочернему сообщению

Сохранить дочерние `chat_id`/`message_id`, native emitter/caller и текущую модель загрузки ресурсов. Не подставлять родительские IDs для получения browser callback. Visualizer сам завершает необязательное определение языка по своему таймауту; отсутствие callback не должно требовать открытия дочернего чата заранее.

Оболочка сохраняется native событием `embeds` дочернего сообщения; HTML/SVG в маркерах остаётся в ответе того же работника. При открытии выполнения observer плагина читает окружающий ответ в этом дочернем чате. Привязка не зависит от того, открыт ли дочерний чат в исходной вкладке, другой вкладке или позднее в новой сессии пользователя.

```text
Main chat --> lite_parallel --> child A --> Tool + marked HTML --> embed A
                          +--> child B --> Tool + marked HTML --> embed B
          <-- statuses, results and child links ----------------------+
```

Не добавлять Visualizer в `base_tool_ids`/`base_skill_ids` Router и не менять `collect_result` ради публикации embeds. Same-origin — явная настройка пользователя, необходимая плагину; продукт не включает её автоматически. Для подготовленного тестового пользователя настройка является заявленным условием стенда.

### 3. Детерминированный gate достигает настоящей границы сбоя

Добавить отдельный `tools/visualizer_acceptance.py` по устройству существующей приёмки, повторно используя подходящие helpers и расширяя детерминированный провайдер отдельным сценарием. Работа допускается только в одноразовом OWUI 0.12.3 с отдельными fixture IDs и восстановлением изменённых настроек. Product code, native Tool loop и загруженные Tool/Skill не заменяются заглушками; детерминированным является ответ тестового провайдера.

Минимальный основной сценарий использует одного работника с Visualizer и второго простого работника, поскольку `lite_parallel` принимает минимум два задания. Далее проверить пару разных визуализирующих агентов и два задания одной модели.

Граница отрицательного контроля: живая сессия действительно зарегистрирована в OWUI, открыта на основном чате, передана в запрос, дочерний чат ещё не открыт. Вызов 2.1.1 должен оставаться в ожидании `execute` до ограниченного прерывания проверки. Несуществующий session ID, немедленно получающий ошибку disconnected, не заменяет этот контроль. Отдельная положительная проверка моделирует отключение исходной socket-сессии без нажатия Stop.

Граница положительного контроля: Tool 2.2.3 вызывается один раз, возвращается не позднее восьми секунд от входа в локальном стенде, после него приходит следующий запрос к провайдеру и сохраняется полный ответ с реальным HTML/SVG. Пять секунд — таймаут upstream; три секунды — допуск локального сценария на построение оболочки и native обработку. Измерять Tool отдельно от очереди LLM и времени выполнения всей группы. Метрики и счётчики добавляются на тестовой границе, оригинальная реализация Tool вызывается один раз.

Контрольный фрагмент содержит уникальную метку задания, SVG и локальную кнопку/переключатель с проверяемым изменением DOM. В нём нет CDN, fetch и внешних изображений. Провайдер использует фактическое опубликованное имя функции: в исследованных snapshot это `render_visualization` для 2.1.1 и `visualize` для 2.2.3. Skill читается по настоящему разрешённому ID до вызова Tool.

### 4. Сохранённый embed и отрисовка проверяются раздельно

Backend-проверка подтверждает terminal-ответ без ошибки, завершённый Tool call, сохранённый `embeds` дочернего сообщения, ожидаемое содержимое ответа, корреляцию с заданием и отсутствие новых embeds работника у родителя. Готовность группы сама по себе не означает, что браузер отрисовал SVG.

Браузерная проверка обязательна для следующих действий:

1. Оставаться на основном чате до завершения Tool и всей группы; затем открыть выполнение по штатной ссылке. В iframe найти ожидаемые элементы, дождаться исчезновения loader и проверить локальное взаимодействие.
2. В отдельном прогоне открыть дочерний чат во время контролируемой генерации после Tool и дождаться законченной визуализации.
3. Перезагрузить завершённый дочерний чат и открыть ту же ссылку в другой сессии того же пользователя. Повторно проверить DOM/взаимодействие; число вызовов модели и Tool не увеличивается.
4. Сопоставить уникальные метки A/B и двух A с правильными дочерними чатами. Обычный пользователь без grants на ресурсы агента может смотреть своё выполнение; другой пользователь без доступа не получает историю или embed. Внутренние чаты остаются скрытыми из обычной истории.

Сохранить команды, версии, длительности, IDs проверенных чатов, снимки DOM/экрана и результаты взаимодействия без токенов и приватного содержимого. Проверка может управляться доступным browser/computer-use инструментом; создание нового frontend или обязательной runtime-зависимости для браузера не требуется.

### 5. Остаточный дефект исправляется только в подтверждённой точке интеграции

Если положительный gate проходит, явно записать, что исправление состоит в обновлении внешнего Tool/Skill и runtime Router не менялся.

Если остаётся воспроизводимый дефект Router, превратить конкретную границу в regression test до исправления. Допустимые точки — передача дочерних событий из `model_execution.py` и сохранение контекста при загрузке/refresh в `owui_adapter.py`/`binding.py`. Исправление должно сохранять native обработку embeds и chat identity; внутренние импорты OWUI остаются в адаптере. После него пересобрать два exports и повторить исходный gate.

Не отключать `__event_call__` глобально и не выдавать фиктивные успешные ответы browser RPC. Не менять глобальные каталоги моделей, `CHAT_COMPLETION_HANDLER`, чужие сессии или пользовательские grants. Если для прохождения нужен форк JS плагина либо патч OWUI, зафиксировать конкретный сбой и пересмотреть этот design до расширения реализации; не объявлять совместимость по одному backend-результату.

## Risks / Trade-offs

- Изолированная проверка пятисекундного таймаута не доказывает сквозную отрисовку -> завершение gate требует native запроса и браузерной проверки готового iframe.
- HTTP-фикстура с несуществующей сессией пропускает исходный баг -> отрицательный контроль выполняется с настоящей активной сессией основного чата.
- Upstream Tool и Skill расходятся по именам функций или инструкции устаревают -> фиксировать общий snapshot, hashes и фактические specs загруженного Tool.
- Открытие дочернего чата может совпасть с уже прошедшим событием -> проверять сохранённые поля, reload и другую сессию, а не только live-доставку события.
- Результаты разных работников смешиваются при общей привязке -> две модели и повторение одной модели проверяются с разными уникальными метками.
- Same-origin выключен или внешняя библиотека недоступна в закрытом контуре -> описать настройку, использовать локальный HTML/SVG-контроль; доступность CDN не считать доказанной.
- Обновление внешнего Tool влияет и на его обычное использование -> перед миграцией сохранить прежние Tool/Skill/Valves и проверить прямое использование или обычный handoff дополнительно к параллельному сценарию.

## Migration Plan

1. Подготовить два snapshot локально и manifest. В одноразовом стенде сохранить исходные fixture настройки и выполнить отрицательный контроль 2.1.1 с последующей остановкой и cleanup.
2. Установить согласованные Tool 2.2.3 и Skill в выделенные test IDs, прикрепить только нужным агентам и выполнить положительный gate. Это не обновляет production-ресурсы пользователя.
3. При необходимости внести только доказанное исправление адаптации, пересобрать exports и повторить проверки. Если обновления плагина достаточно, зафиксировать это без искусственного изменения Router.
4. После приёмки описать ручное обновление установленного Tool и связанного Skill с сохранением их IDs/attachments и проверкой заново сформированных specs. Пользовательские Valves и настройку same-origin проверять отдельно.
5. Rollback восстанавливает сохранённые Tool/Skill/Valves и, только если менялись Functions, предыдущую согласованную пару exports. Возврат к 2.1.1 возвращает известное ограничение параллельного вызова; это не совместимый обходной путь. Сохранённые дочерние чаты и их связи не удаляются.
