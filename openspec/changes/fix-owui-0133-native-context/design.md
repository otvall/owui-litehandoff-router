# Design

## Context

Мотивация и границы — в proposal.md. Изменение затрагивает жизненный цикл, проекции истории и проверки доступа, поэтому design обязателен.

Preparation создаёт request-local state и общий registry Tools до вызова Pipe. Pipe обновляет canonical source, готовит модель и публикует registry для штатного Tool loop. `observation.py` подтверждает вызовы провайдера; `history.py` разрешает агенту exchanges с подтверждённым Model ID. Native-контекст OWUI создаётся вне провайдера и сейчас получает executor=unknown.

На OWUI 0.13.3 проверены 79 unit и 55 native тестов; отдельная проба native hidden-result формата воспроизводит потерю памяти после handoff. Минимум: вопрос пользователя, служебный assistant call `recall_memories`, связанный tool result. Router сохраняет результат как historical reference, агент исключает его даже при наличии одноимённого Tool. Это проверка формата и проекций, а не настоящего memory retrieval или решений живой LLM.

Исходники тега 0.13.3 показывают две важные границы: основной endpoint заново собирает metadata; native preprocessing формирует initial_output и добавляет его преобразованные сообщения перед Pipe. Эти сведения дают точку получения серверного контекста, но не разрешают доверять одноимённому полю произвольного клиента или прямого вызова Pipe.

## Goals / Non-Goals

**Goals:** отдельное серверное происхождение служебных данных, сохранение допустимой памяти на handoff, проверяемые границы пользователя и ресурсов, повторяемые регрессии без изменения Tool loop.

**Non-Goals:** новая оркестрация, долговременная память Router, собственный retrieval engine, новые knowledge Tools, перенос Skills-манифеста в другой формат, изменение native approvals, UI-панель и исправление наблюдаемого live-rendering.

## Decisions

### 1. Отдельный адаптер native-контекста

Преобразование формата OWUI и проверки серверного источника разместить за узкой границей `owui_adapter.py`, при необходимости в отдельном `native_context.py`. История получает нормализованные записи, а не знания о внутренних форматах разных релизов. Проверяется наличие API и данных, номер установленной версии не читается.

Запись содержит вид контекста, связанную пару вызов/результат, область actor/chat/message/server request, исходную область attachments и fingerprint содержимого. Состояние хранится в ASGI scope вместе с существующим trusted lifecycle state; в клиентский receipt и переносимый chat_context оно не включается.

Альтернативы: разрешить все unknown exchanges или распознавать только имя/hidden-флаг. Они отвергнуты: пользовательская история и модель могут воспроизвести эти признаки; это также ослабило бы проверку настоящего handoff.

### 2. Получение после native preprocessing, до проекции

На первой подготовке Pipe после `require()` адаптер читает результаты текущего серверного preprocessing, сопоставляет полные пары с текущими сообщениями и фиксирует независимое подтверждение. Проверяются область запроса и однозначность пары, включая аргументы и содержимое результата. Одного совпадения call_id недостаточно. Входные messages и canonical source не переписываются.

Доверенный путь — metadata, заново созданная штатным endpoint и наполненная native preprocessing; прямая передача клиентского initial_output не является таким путём. HTTP-проверки должны подтвердить эту границу для установленного OWUI, включая поддельные metadata, hidden results и internal-признаки. Если путь не подтверждён, записи остаются неподтверждёнными, действует прежняя политика unknown и безопасная диагностика.

На native продолжениях сохранённая request-local запись используется повторно без накопления копий. Изменения, внесённые destination inlet, не могут переписать подтверждение происхождения или расширить область ресурсов.

Для нового HTTP-запроса прежнее подтверждение не восстанавливается из истории. При штатном approval resume сначала требуется серверное подтверждение самого resume; если preprocessing не создал свежие записи, допустимая память заново получается через штатное серверное чтение OWUI с пользователем исполнения и действующими настройками. Это чтение контекста, а не повтор Tools агента. Сохранённые hidden-флаги не используются вместо проверки. Политика разрешения/запрета approvals остаётся существующей.

### 3. Проекции различают контекст OWUI и действия модели

`history.py` сохраняет существующие правила provider audit для обычных Tools. Допустимые подтверждённые native-пары выбираются отдельным правилом и сохраняются как текущий служебный контекст, независимо от наличия одноимённого callable. Они не становятся ни historical reference, ни доказательством, что агент выполнил Tool.

Проекция включает пару целиком и единожды, сохраняет текущий вопрос и его границу. Canonical source остаётся полным. `model_execution.py` применяет политику выбранного адресата до сборки его проекции; Tools получают уже итоговые сообщения через существующий context binder.

Альтернатива — пометить native-записи как вызовы Router или агента в provider-аудите. Она отвергнута: это выдуманное авторство и смешение с доказательством handoff.

### 4. Политика зависит от вида данных

| Вид | Политика |
| --- | --- |
| recall_memories | Пользователь исполнения, текущие разрешения OWUI и политика выбранной модели. Передаётся при обычном/финальном handoff, пока разрешена. Память владельца не читается. |
| list_attached_knowledge | Только подтверждённые актуальные пользовательские attachments либо разрешённая область выбранной модели. Native-проверки knowledge/files выполняются от actor; owner authority Tools/Skills сюда не расширяется. |
| list_available_skills | Родительский каталог не переносится целиком. Существующий scoped-манифест выбранной модели остаётся источником доступных Skills; readers и owner/actor разделение сохраняются. |

Для knowledge адаптер сопоставляет IDs со штатными серверными attachments и актуальными правами. Неоднозначный смешанный список не копируется как свободный текст: неподтверждённые записи исключаются, публикуются только разрешённые данные. Это обработка уже доступного контекста, без автоматического подключения retrieval Tools или новых приватных knowledge-источников адресата.

Политика пересчитывается на каждой подготовке: отзыв доступа, отключение памяти или изменение набора Skills не обходятся кешем контекста. Содержимое исключённых записей в диагностику не попадает.

### 5. Работник начинает с собственной области

`prepare_worker()` сохраняет task-only вход и отдельный lifecycle state. Родительские native-записи и подтверждения не включаются в ticket/input/chat_context. Если штатный child preprocessing создаёт собственные допустимые записи, они подтверждаются для child, его task и файлов. A+A также означает две независимые области.

После группы финальный агент C использует область основного запроса: разрешённую память родителя и полные подтверждённые результаты, а не служебную историю работников.

### 6. Приёмка проверяет контракт, а не только маркеры

Исходная падающая проба переносится в постоянные native-тесты: проверяются формат, происхождение, фактический payload итогового агента и context callable. Одного наличия строки в Router недостаточно: текущий код уже сохраняет её в historical reference.

Нужны положительные проверки через реальные standalone exports и native loop, HTTP-проверка настоящего preprocessing, отрицательные проверки подделки и повторного использования, новая реплика после изменения памяти, approvals по существующей политике, два пользователя, A+B/A+A и финальный handoff. Проверки реального memory retrieval и живой LLM учитываются отдельно от scripted provider.

## Risks / Trade-offs

- Изменение внутреннего initial_output → адаптер формата и HTTP-контроль границы доверия; отсутствие подтверждения не расширяет контекст.
- Избыточное доверие старой памяти → request-local state и свежее серверное чтение на новом запросе/подтверждённом resume.
- Смешанный knowledge-каталог → фильтрация по источнику, attachments и actor ACL; неопределённая запись исключается.
- Дублирование native-пар → fingerprint вместе с областью запроса и проверка полной пары на каждом продолжении.
- Отсутствие реальной LLM в локальном контуре → scripted evidence обозначается явно; ручной сценарий и обезличенный протокол приёмки остаются отдельной незакрытой задачей до реального результата.
- Несинхронизированные основные specs → учитывать delta предыдущих changes; новые требования добавлены отдельно и не переписывают их определения. Этот change не архивирует и не завершает чужую LLM-приёмку.

## Migration Plan

1. Зафиксировать постоянный красный native-тест и отрицательные случаи; реализовать адаптер, lifecycle и проекции в рамках apply.
2. Пересобрать обе Functions. На отдельном OWUI 0.13.3 выполнить unit/native и HTTP-приёмку, сохранив обезличенные результаты в репозитории.
3. Обновить документацию контекста и границы совместимости. Сохранить информационный смысл metadata версии и отсутствие runtime guard; миграция БД и изменение карточек агентов не нужны.
4. Перед обновлением рабочей установки сохранить оба старых export и Valves. Загружать согласованную пару Filter/Pipe. При откате восстановить пару и Valves; чаты, файлы и grants не изменяются этой миграцией.
