# Proposal

## Why

Пользователям Open WebUI приходится самостоятельно выбирать специализированную модель и управлять её возможностями. Нужна одна общая модель Router, которая отвечает на общие вопросы или через routing Skills передаёт текущий запрос подходящему агенту в том же чате, учитывая права пользователя.

## What Changes

- Создать новый самостоятельный проект для **Open WebUI v0.12.3** с устанавливаемым комплектом из одного Filter и одного Pipe со встроенным Tool `lite_delegate`.
- Хранить общий каталог в конфигурационном Python-словаре `AGENTS: dict[str, str]`: Workspace Model ID агента → ID существующего routing Skill OWUI. Администратор пишет routing Skills вручную; генерация из описаний моделей не требуется.
- На каждом новом сообщении формировать персональный реестр из настроенных, активных и разрешённых пользователю агентов, применяя штатные правила OWUI для групп и индивидуального доступа.
- Из одного реестра строить манифест routing Skills с явным `agent_id` и персональный `enum` аргумента `lite_delegate.agent_id`. Перед исполнением повторно проверять адресата.
- Оставить решение о передаче внутри обычного цикла генерации Router: чтение подходящего Skill, самостоятельный ответ либо настоящий Tool call. Отдельного LLM-классификатора не добавлять.
- Задавать базовые Tools и Skills Router в административных Valves Router Preparation: `base_tool_ids` и `base_skill_ids`. Pipe подключает их автоматически, без attachments в карточке Router и без отображения как включённых пользователем ресурсов в интерфейсе чата.
- После handoff автоматически подготавливать модель агента: её системный промпт, параметры генерации, Tools/MCP и Skills. Набор возможностей определяется конфигурацией модели, не переключателями пользователя.
- Сохранить общую переписку, дать Router обзор завершённой работы инструментов и формировать агенту только его собственную допустимую служебную историю. Исходную историю чата не переписывать ради подготовки контекста.
- Использовать штатное скрытие моделей агентов через `meta.hidden`, сохранив их активность и групповые разрешения. Запрет прямых API-вызовов не входит в задачу.
- Обеспечить работу без интернета после установки: локальные модели и сервисы, два самостоятельных Python-файла Functions, без отдельного сервиса оркестрации.

Минимальная версия: один Router, несколько заранее настроенных агентов, одна передача одному агенту на пользовательский запрос и последующие Tool-продолжения этого агента. Новое сообщение пользователя снова обрабатывает Router. Создание самих агентов, вложенная делегация, последовательный запуск нескольких агентов, автоматический пересказ истории и миграция старого комплекта не входят в первую версию.

## Capabilities

### New Capabilities

- `user-agent-registry`: конфигурационный каталог, персональный отбор по правам, согласованные манифест и `enum`, скрытие агентов в интерфейсе.
- `skill-based-handoff`: выбор через routing Skills, проверяемая передача текущего запроса и жизненный цикл исполнения без отдельного чата.
- `workspace-model-execution`: базовые возможности Router из административных Valves, автоматическая подготовка агентов из их моделей, обязательный набор Tools/Skills, совместимость с OWUI v0.12.3 и автономная установка.
- `conversation-context`: общая переписка, обзор инструментов для Router, история по исполнителю и сохранение валидных Tool-продолжений.

### Modified Capabilities

Нет: проект новый, существующих основных спецификаций нет.

## Impact

- Будут добавлены Python-исходники подготовки реестра, исполнения, Skills и истории, сборка двух самостоятельных устанавливаемых файлов, тесты и инструкция администратора. Точные интерфейсы описаны в `design.md`.
- Используются внутренние Python API OWUI v0.12.3 для моделей, доступа, Tools, Skills, фильтров и completion. Поддержка других версий не заявляется.
- Референс — `../owui-tools/handoff_router` для OWUI v0.11.1: он показывает same-chat handoff, но его поведение и проверки не переносятся автоматически.
- Схема БД и исходники OWUI не меняются. Пользователь запроса сохраняет свою идентичность и штатные права на модели и ресурсы; выдача разрешений группам остаётся настройкой администратора.
- Runtime использует Python и библиотеки установленного OWUI. Новая инфраструктура, внешние облачные API и дополнительные runtime-библиотеки для маршрутизации не требуются.
