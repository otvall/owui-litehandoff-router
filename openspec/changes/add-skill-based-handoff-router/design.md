# Design

## Context

Мотивация и продуктовые границы приведены в [proposal.md](proposal.md). Репозиторий новый: runtime-кода и основных specs пока нет. План рассчитан на OWUI **v0.12.3**, локальные модели и доступные внутри закрытого контура сервисы.

Прочитан референс `../owui-tools/handoff_router`: README, настройка Router, системный промпт, подготовка реестра, runtime, подготовка Skills, completion adapter и тесты истории/подготовки моделей. В нём уже есть ручное соответствие Model ID → routing Skill ID и handoff через штатную Tool-цепочку. Референс предназначен для v0.11.1; его совместимость с v0.12.3 не предполагается.

Проверенные особенности целевой версии:

- Фильтрация списка моделей и проверка запуска используют групповые/индивидуальные разрешения; проверка запуска также учитывает базовые модели. Основа адаптера доступа — [utils/models.py v0.12.3](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/utils/models.py#L450-L561).
- При встроенных Skills каталог может включать все активные Skills пользователя. Запрос также несёт отдельное состояние упоминаний и версий Skills. Поэтому одного списка attachments недостаточно для нужного разделения. См. [подготовку Skills](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/utils/middleware.py#L2266-L2405).
- Встроенные операции чтения — `view_skill`, `read_skill_file`, `grep_skill_files`. Их штатная авторизация проверяет пользователя. См. [builtin.py](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/tools/builtin.py#L3194-L3386).
- OWUI умеет заново связывать callable с актуальными injections. Обычная внешняя обёртка, потерявшаяся при таком обновлении, не обеспечивает ограничение Skills или истории. См. [get_updated_tool_function](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/utils/tools.py#L252-L320).
- Native Tool-продолжение повторно вызывает completion и передаёт `bypass_system_prompt=True`. Установку промпта адресата необходимо проверять именно на этом пути, а не только на первом вызове. См. [middleware.py](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/utils/middleware.py#L5561-L5578).
- Стандартный селектор скрывает `info.meta.hidden`, сохраняя модель в серверном каталоге. Это интерфейсная видимость, а не отдельное разрешение запуска. См. [Selector.svelte](https://github.com/open-webui/open-webui/blob/v0.12.3/src/lib/components/chat/ModelSelector/Selector.svelte#L227-L273).

Эти наблюдения задают точки интеграции. Описанные ниже модули и поведение — проектируемая реализация, а не утверждение о наличии такого кода в репозитории.

## Goals / Non-Goals

**Goals:**

- Один устанавливаемый Filter, один Pipe и один Tool; раздельные внутренние модули для реестра, исполнения, Skills и истории.
- Один источник для персонального реестра, routing-манифеста и delegate schema.
- Явная граница между настройками модели, данными чата и состоянием конкретного запроса.
- Проверяемая интеграция с native Tool loop v0.12.3, включая продолжения и смену системного промпта.
- Использование штатных прав пользователя при неизменяемом им наборе возможностей выбранной модели.

**Non-Goals:**

- Отдельный сервис, графовый оркестратор, собственная БД разрешений или изменение исходников OWUI.
- Совместимость с прежним комплектом v0.11.1 и автоматическая миграция его конфигурации.
- Полная эмуляция всех функций Workspace: Actions, произвольные outlet/stream-фильтры адресата, терминальные агенты и дополнительная система nested delegation не входят в заявленную поверхность MVP.
- Создание и редактирование Skills самим агентом как новая встроенная функция. Для использования Skills достаточно чтения.
- Делегирование закрытых ресурсов от имени владельца, сокрытие инструкций от пользователя и серверный запрет прямого API-доступа к агентам.
- Автоматический перенос сырых чужих Tool results, пересказ истории, восстановление результатов повторным запуском Tools.

## Decisions

### 1. Native Functions вместо отдельного процесса

Runtime — Python среды целевого OWUI с его FastAPI/Pydantic и внутренними APIs. Собственная маршрутизация не требует новых runtime-библиотек. Тестовые зависимости устанавливаются заранее; фиксировать нужно окружение v0.12.3, а не обновлять зависимости работающего OWUI ради плагина.

Выбор позволяет участвовать в текущем чате, пользоваться идентичностью пользователя, native Tools и существующими Workspace Models. Внешний HTTP-router потребовал бы заново переносить permissions, Skills, Tool execution и сохранение ответа. LangGraph и аналогичные фреймворки здесь не дают требуемой интеграции со штатной Tool-историей сами по себе.

Предлагаемая структура исходников:

```text
src/lite_handoff_router/
  registry.py
  runtime.py
  model_execution.py
  skills.py
  history.py
  owui_adapter.py
  entrypoints/
    router_preparation.py
    lite_handoff_router.py
    lite_delegate.py
tools/build_functions.py
dist/
  router_preparation.py
  lite_handoff_router.py
  lite_delegate.py
tests/
docs/
```

Сборка на стандартной библиотеке встраивает используемые общие модули в три самостоятельных файла. В установленном комплекте допустимы импорты стандартной библиотеки и OWUI; импорты `lite_handoff_router` из этого checkout недопустимы. Сборка должна быть воспроизводимой, а экспортированные файлы проверяются отдельно от модульных исходников.

### 2. Роли трёх устанавливаемых компонентов

| Компонент | Ответственность |
|---|---|
| Router Preparation Filter | Начало нового запроса: сохранить исходную текущую ветку истории, сбросить старую передачу, прочитать `AGENTS` и административные Valves базовых ресурсов, сформировать персональный снимок реестра и серверный контекст подготовки |
| Router Pipe | Подготовить текущего исполнителя, его историю, промпт, параметры и возможности; установить согласованные схемы/исполняемые Tools; принять валидный handoff; вызвать completion adapter |
| `lite_delegate` Tool | Проверить запрос на передачу по текущему серверному контексту и вернуть служебный результат выбора; не запускать LLM или отдельный чат самостоятельно |

Filter прикрепляется к публичной Router Workspace Model как обязательный, без пользовательского toggle и без Global. Pipe проверяет, что подготовка относится к текущему запросу и пользователю. Отсутствующий или устаревший контекст даёт ошибку настройки, а не разрешает использовать снимок предыдущего запуска.

К агентам отдельный preparation Filter прикреплять не нужно. Их подготовку ведёт Pipe.

Базовые возможности Router задаются в административных **Valves Router Preparation**, не в UserValves и не attachments публичной Router-модели:

| Valve | Значение по умолчанию | Назначение |
|---|---|---|
| `base_tool_ids` | `["lite_delegate"]` | IDs установленных базовых Tools Router; ID установленного delegate Tool можно заменить на фактический |
| `base_skill_ids` | `[]` | IDs существующих базовых Skills Router; routing Skills добавляются отдельно из персонального реестра |

Пример конфигурации:

```json
{
  "base_tool_ids": ["lite_delegate", "base-helper"],
  "base_skill_ids": ["router-guide"]
}
```

Поля Tools и Skills в карточке публичного Router остаются пустыми. Pipe не использует их как запасной источник и не объединяет с Valves. Системный промпт и параметры Router по-прежнему задаются его моделью.

Filter копирует нормализованные списки из своих Valves в серверный снимок нового запроса. Pipe использует их на первом вызове и продолжениях; новое сообщение получает актуальные Valves. Недоступный обязательный базовый ресурс вызывает ошибку подготовки. При наличии агентов базовый набор должен содержать установленный Tool с методом `lite_delegate`.

Подключение выполняется только в серверном контексте и запросе к LLM: базовые IDs не публикуются как пользовательский выбор ресурсов и не записываются для этой цели в карточку модели или сохранённые настройки чата. Поэтому они не появляются как включённые пользователем подключения в поле ввода. Фактические Tool calls и Skill reads остаются видимыми в истории. Это правило касается отображения подключения, а не секретности имён или содержимого ресурсов.

### 3. Статический каталог и персональный снимок

Единственный ручной каталог находится в конфигурационной секции устанавливаемого Router Preparation:

```python
AGENTS = {
    "agent-a": "route-agent-a",
    "agent-b": "route-agent-b",
}
```

Слева — канонический Workspace Model ID; справа — существующий Skill ID. Содержимое routing Skill пишет администратор. Описания моделей не превращаются в Skills автоматически. Переименование отображаемого имени не меняет адресата; изменение ID требует обновления словаря и инструкций Skill.

При подготовке:

1. Проверить форму каталога: непустые строковые IDs, корректные ссылки, отсутствие адресатов, ведущих обратно в этот Router Pipe.
2. Прочитать актуальные записи настроенных моделей. Проверить active, наличие в runtime-каталоге и штатный доступ текущего пользователя. `hidden` не использовать как отказ в маршрутизации.
3. Для разрешённых моделей проверить наличие, активность и read-доступ к routing Skill. Непригодную запись исключить с диагностикой, не публикуя непригодный адресат в одном из представлений.
4. Сохранить снимок из `agent_id`, `routing_skill_id`, имени/описания Skill и ссылки на выбранную Workspace Model. Для маршрутизации сохранять только необходимые сведения; рабочие инструкции агентов не загружать Router.
5. Из этого снимка построить routing-манифест и копию схемы `lite_delegate` с `enum` точных Model IDs.

Манифест имеет явное поле `agent_id` рядом с ID Skill. `view_skill` по-прежнему принимает Skill ID; `lite_delegate` — Model ID. Alias между этими аргументами не вводится. Полное содержание routing Skill не подменяется автоматически сгенерированным текстом.

Пустой реестр агентов означает отсутствие `lite_delegate` и routing Skills при сохранении остальных базовых Tools/Skills из Valves и самостоятельного ответа Router. Пустой `base_skill_ids` не отключает routing Skills доступных агентов. Схема установленного Tool не изменяется глобально: новая копия создаётся в конкретном запросе. Валидатор передачи проверяет текущий снимок независимо от того, соблюдает ли провайдер JSON Schema `enum`.

Обмен между установленными Functions идёт через request-scoped metadata с сериализуемыми значениями. Снимки не хранятся в атрибутах общего экземпляра Pipe/Filter или в глобальной пользовательской переменной. Серверная привязка запроса не восстанавливается из клиентских служебных полей.

### 4. Выбор является частью обычного Tool loop

```text
New user message
        |
        v
Router Preparation --> user registry + original history
        |
        v
Router Pipe --> Router LLM + own tools + routing skills
        |                |
        |                +--> normal answer --> current chat
        |
        +--> view_skill --> lite_delegate(agent_id)
                                  |
                                  v
                          validate current exchange
                                  |
                                  v
                         prepare selected agent
                                  |
                                  v
                        agent tools <--> agent LLM
                                  |
                                  v
                          answer in current chat
```

Filter не вызывает LLM для классификации. Router использует описания routing Skills, при необходимости читает полные инструкции и вызывает настоящий `lite_delegate`. Обычный текст, назвавший агента, не переключает модель.

Состояния одного запроса: `router` → `pending-handoff` → `agent` → завершение/ошибка. Tool проверяет текущий снимок и записывает pending-выбор, привязанный к пользователю и запросу. Pipe принимает его только после однозначного завершённого exchange самого `lite_delegate` в текущем запросе. Вывод другого инструмента и произвольный marker-подобный JSON не являются доказательством передачи.

Протокол результата можно сохранить совместимым по форме с референсом: `{"__lite_delegate__": "v2", "agent_id": "agent-a"}`. Это внутренний сигнал, не механизм обхода проверок. Поддерживать Skill ID вместо Model ID и старые marker-форматы не требуется.

Для MVP выбран один агент на сообщение пользователя. После передачи следующие вызовы модели, вызванные результатами его Tools, остаются у этого агента. `lite_delegate` и встроенная параллельная делегация не подключаются агенту. В системных инструкциях Router передача выполняется отдельным Tool call. Несколько конкурирующих вызовов передачи в одной генерации не принимаются; уже выполненные Tools автоматически не повторяются. При этом штатное объединение истории нескольких продолжений в одну assistant-запись не считается несколькими передачами: важны конкретные exchanges и pending-состояние текущего исполнения.

Следующее реальное пользовательское сообщение начинает новый цикл Router. Границу определяем по событию/идентичности пользовательского запроса OWUI, а не просто по последней записи с ролью `user`: OWUI использует такую роль и для служебных изображений Tool results.

### 5. Подготовка выбранной модели с атомарной публикацией

Вход подготовки — актуальная Workspace Model, идентичность пользователя, неизменённая история и контекст текущего запроса. Выход — готовый payload и набор исполняемых Tools для одной модели. Изменения публикуются в действующий runtime только после успешной подготовки целиком.

Порядок:

1. Заново проверить active и доступ к модели, прочитать её конфигурацию.
2. Отделить данные запроса от развёрнутых настроек предыдущего исполнителя: убрать его промпт, inference fields, Skills, Tools, loader и служебное состояние упоминаний. Сохранить исходный запрос, файлы, идентичность чата и параметры транспорта.
3. Подготовить штатные серверные Tools/MCP и Skills с реальным пользователем запроса. Для Router исходными наборами служат `base_tool_ids`/`base_skill_ids` из серверного снимка Valves плюс персональные routing Skills; для агента — актуальные attachments его карточки.
4. Собрать историю для выбранного исполнителя, затем установить его собственный промпт и Skill context.
5. Запустить дополнительные прикреплённые inlet-фильтры выбранной модели в штатном порядке. Они получают уже подготовленный контекст.
6. Проверить целостность зарезервированных Skill readers и схемы передачи, сохранить итоговую историю для Tools, затем опубликовать подготовленное состояние и вызвать провайдера.

Адаптер установки системного промпта использует helper-логику OWUI для подстановок и обеспечивает ровно одно применение промпта адресата. Он явно управляет `bypass_system_prompt` на native продолжениях, чтобы внешний флаг не сохранял промпт Router у агента и не накапливал копии промпта. И `temperature`, и другие развёрнутые поля вроде `top_p`, `top_k`, `custom_params` берутся из выбранной модели, а не случайно наследуются от Router.

Клиентские `tool_ids`, `skill_ids`, поля с именами `base_tool_ids`/`base_skill_ids`, UserValves, упоминания и переключатели не являются источниками базового набора Router или возможностей агента. Для комплекта обязателен native function calling: Router Preparation закрепляет этот режим до штатной обработки Tools, а подготовка адресата не принимает клиентское переключение в legacy как способ отключить инструменты. Серверные запреты, модельные capability flags и права пользователя при этом сохраняют действие. Дополнительный доверенный фильтр может менять запрос своей модели; конфликт с обязательным Skill reader приводит к ошибке конфигурации до обращения к провайдеру.

Не следует переиспользовать runtime-модель через изменение `request.app.state.MODELS`. Подготовка работает с локальной копией, сохраняя request-scoped привязки. После ошибки нет частично установленного target или комплекта чужих Tools.

### 6. Права на модель и ресурсы проверяются штатно

Требование пользователя относится к обязательному набору возможностей и отсутствию переключателей. Оно не требует закрытых для пользователя ресурсов или исполнения от имени администратора. Для MVP выбран обычный режим: permission actor и `__user__` — текущий пользователь.

Администратор предоставляет группам read-доступ к моделям, базовым ресурсам из Valves, соответствующим routing Skills и используемым рабочим ресурсам; возможность менять карточки/Functions и административные Valves остаётся настройкой OWUI. Дополнительные проверки самих Tools и авторизация MCP продолжают действовать от имени пользователя. Один доступ к модели не считается автоматическим разрешением на закрытый ресурс.

Если routing Skill непригоден, запись исключается из персонального снимка с диагностикой. Если уже выбранному агенту недоступен обязательный рабочий ресурс, его подготовка завершается понятной ошибкой. Частичное подключение с незаметно пропавшими возможностями не допускается.

Такой режим проще и соответствует native проверкам v0.12.3. Альтернатива с доступом владельца модели потребовала бы отдельного контракта делегированных полномочий, identity binding, UserValves и авторизации внешних сервисов; в эту первую версию она не входит.

### 7. Skills: отдельный каталог и проверка каждого чтения

У Router допустимый набор равен `base_skill_ids` из снимка административных Valves плюс routing Skills персонального реестра; `skillIds` карточки Router этот набор не расширяют. У агента — актуальным `skillIds` его модели, перечитываемым при каждой подготовке. Существование, активность и штатный read-доступ к разрешённым Skills проверяются и на продолжениях.

Общая подготовка явно заменяет управляемый Skill context. Старый широкий каталог OWUI, загруженные инструкции предыдущего исполнителя, клиентские упоминания и чужое состояние Skill context не объединяются с текущим набором.

Механизм ленивой загрузки сохраняется. Для `view_skill`, `read_skill_file` и `grep_skill_files` устанавливаются проверяемые callable, которые:

- сначала проверяют ID по допустимому набору модели текущего запроса;
- затем вызывают штатную операцию OWUI с реальным пользователем и текущими injections;
- сохраняют штатную работу файлов, страниц и версий;
- сохраняют ограничение после `get_updated_tool_function`, не позволяя восстановить исходный неограниченный builtin;
- не переиспользуют контекст другой модели при смене адресата.

Нужен один механизм ограничения для всех трёх чтений. Проверка только `view_skill` оставила бы обход через чтение файла или поиск. Только исправленный манифест не мешает модели запросить известный ID. Полное включение всех инструкций в системный промпт увеличило бы контекст и потеряло полезную файловую загрузку.

Автоматическое добавление операций создания/редактирования Skills из широкого набора builtin-функций не входит в набор данного адаптера чтения. Публичное имя, схема и исполняемый reader устанавливаются согласованно. Коллизия с пользовательским Tool того же зарезервированного имени диагностируется, а не разрешается молчаливой подменой.

### 8. Одна исходная история, разные представления

Источник — текущая ветка чата, полученная OWUI, включая структурированные Tool calls/results и пользовательские вложения. Результаты подготовки не заменяют этот источник. При native продолжении новые exchanges добавляются к текущему источнику, чтобы смена представления не теряла свежий Tool result.

Каждый exchange описывается конкретным вызовом, результатом, границей пользовательского запроса, группой исполнения и автором (`router`, Model ID агента или `unknown`). Совпадения имени Tool или глобального `tool_call_id` недостаточно для определения автора. Историческое авторство не переписывается под текущий каталог; удалённый агент не становится другим исполнителем.

| Получатель | Представление |
|---|---|
| Router | Общие вопросы и итоговые ответы, пользовательские вложения, справка о завершённых Tools всех исполнителей из всей доступной текущей ветки; собственная текущая Tool-цепочка |
| Агент | Общие вопросы и итоговые ответы, пользовательские вложения, его собственные допустимые завершённые exchanges и вся валидная текущая цепочка; без handoff и чужой служебной трассы |

Справка Router содержит данные о вызовах и фактические результаты как справочный материал. Она не добавляет схемы исторических инструментов в список текущих возможностей. Для исторических Skill readers в справке остаются ID Skill, операция и статус; полные чужие инструкции и найденные фрагменты инструкций не копируются.

На текущем продолжении собственные Skill-загрузки остаются у исполнителя, иначе он не сможет использовать прочитанное. На следующем пользовательском запросе полные результаты Skill readers исключаются из нативной истории, в том числе у того же исполнителя: при необходимости модель читает Skill заново. В справке Router сохраняются факт, ID и статус такой прошлой операции.

Фильтрация действует на полные пары, учитывает повторные IDs и штатную сгруппированную историю v0.12.3. Невалидные или неоднозначные exchanges не попадают в нативную историю агента. Доступные факты о них можно оставить в справке Router с неизвестным автором, не выдумывая принадлежность.

Tools, принимающие `__messages__`, связываются с окончательным представлением своей модели после inlet-фильтров. Refresh callable может обновить `__files__`, но не должен вернуть внешнюю историю Router. Это проверяется тем же native helper, которым пользуется OWUI, а не только прямым вызовом тестовой обёртки.

В MVP нет нового суммаризатора или скрытого усечения по умолчанию. История передаётся в пределах возможностей провайдера; при переполнении возвращается ошибка, а исходный чат сохраняется. Если новому агенту нужны сырые данные другого исполнителя, доступны общие ответы и файлы; автоматическое извлечение и передача отдельного скрытого data package — последующее расширение, не дополнительный аргумент текущего `lite_delegate`.

### 9. Ошибки и наблюдаемость

Подготовка ведётся как операция с фиксацией результата после всех проверок. При отказе сохраняется исходная история, не остаётся активного наполовину подготовленного агента, пользователь видит ошибку. Отказ провайдера, недоступность ресурса и превышение контекста не превращаются в тихое переключение модели или автоматический повтор действий.

При успешном handoff отправляется штатный status с названием выбранного агента. Ответ, Tool calls и Skill reads продолжают отображаться в этом чате. Отладочная диагностика включает идентификатор запроса, выбранную модель и причины исключения записей; полные промпты и Tool results не требуется писать в лог по умолчанию.

### 10. Проверки строятся вокруг контрактов

Чистые преобразования реестра и истории тестируются без установленного сервера. Интеграционные проверки отдельно охватывают экспортированные entrypoints и native вызовы целевой версии. Моки не считаются доказательством совместимости v0.12.3.

Первый сквозной пример: у Router пустые списки Tools/Skills в карточке, базовые ресурсы заданы Valves, а один routing Skill получен из `AGENTS`. Router вызывает `lite_delegate`, A выполняет простой локальный Tool и отвечает в том же chat/message. Проверяются отличающиеся промпты и температуры Router/A, повторный вызов A после Tool result и отсутствие базовых ресурсов среди выбранных пользователем подключений в UI. Затем добавляются две группы с непересекающимися агентами, конкурентные запросы, неизвестный `enum`, чтение чужого Skill, смена attachments и история с повторяющимися IDs.

Стриминговый путь в UI — обязательная приёмка. Ответ completion adapter также обрабатывает штатные JSON/HTTP ошибки, чтобы не терять причину отказа до начала стрима. Проверка без интернета выполняется на заранее подготовленном v0.12.3 окружении с локальным тестовым провайдером/моделями и локальным MCP, без скачивания пакетов в runtime.

## Risks / Trade-offs

| Риск или компромисс | Мера |
|---|---|
| Зависимость от внутренних API OWUI | Узкий `owui_adapter`, ссылки на v0.12.3 и интеграционные проверки этой версии; новая версия требует отдельной проверки |
| Промпт и параметры могут наследоваться из внешнего Router payload | Явная подготовка адресата и тест первого вызова вместе с native Tool continuation |
| Широкий Skill-каталог или refresh callable возвращает чужой доступ | Собственный управляемый каталог, guard всех чтений и проверка после destination inlets |
| Полная справка Router растёт с чатом | Честная ошибка контекста, сохранение исходных данных; отдельное будущее изменение для лимитов/сводок |
| Ошибка сопоставления Tool history смешивает исполнителей | Привязка к запросу и конкретным exchanges, неизвестные пары исключаются из нативной истории агента |
| Группе выдана модель, но не её ресурс | Документированная настройка read-grants и понятная ошибка обязательного ресурса |
| Скрытый агент всё ещё может быть вызван через API | Это согласованная граница: используется штатный `hidden`, отдельный API-запрет не проектируется |
| Провайдер не соблюдает enum или инструкции делегации | Серверная проверка адресата, реальный Tool exchange и запрет неоднозначной передачи |

## Migration Plan

Это первая установка нового проекта; миграции данных и старого комплекта нет.

1. Подготовить целевой OWUI v0.12.3 и доступные внутри контура модели/сервисы. Router LLM и модели, вызывающие Tools, должны поддерживать native tool calling.
2. Собрать и импортировать три файла из `dist/`. Настроить реальную модель-оркестратор в Pipe; не указывать в этом поле сам Pipe.
3. Создать публичную Router Workspace Model на базе Pipe с обязательным Router Preparation; поля Tools и Skills в карточке оставить пустыми. Задать `base_tool_ids` и `base_skill_ids` в административных Valves Router Preparation, а словарь `AGENTS` — в его конфигурационной секции.
4. Создать или использовать существующие Workspace Models агентов, их routing Skills и рабочие attachments. Выдать группам модели и необходимые read-права на ресурсы.
5. Сделать агентов активными и скрытыми через `meta.hidden`, оставить Router видимым и установить его по умолчанию. Проверить обычный селектор и отдельные учётные записи групп.
6. Выполнить сквозную приёмку сначала для одной передачи, затем для двух групп, Skill isolation и продолжения разговора.

При обновлении сохраняются словарь и Valves перед заменой устанавливаемых файлов. Для отката достаточно вернуть прежние экспортированные версии Functions/Tool и конфигурацию; удалять чаты или ресурсы агентов не требуется.
