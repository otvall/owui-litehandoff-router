# Design

## Context

Мотивация и пользовательская последовательность приведены в [proposal.md](proposal.md). База — реализованный change `add-skill-based-handoff-router`; основных specs пока нет. Его запрет дочерних чатов сохраняется для операции handoff. Новая операция параллельных заданий допускает внутренние чаты и не меняет смысл `lite_delegate`.

Уточнение политики ресурсов распространяется на все способы исполнения через Router. В базовом change и текущем коде загрузка ресурсов использует права пользователя чата. Новый контракт `model-bound-resource-access` заменяет это требование проверкой прав владельца на настроенные ресурсы; пользователь исполнения и его доступ к модели, чатам и обычным файлам сохраняются. Пройденная приёмка параллельного исполнения с grants пользователя не подтверждает эту ещё не реализованную политику.

Наблюдения по текущему коду:

- `runtime.begin` создаёт один `active_agent`, `pending` и серверный scope HTTP-запроса. `publish` изменяет общий `metadata.tools` in-place для внешнего native Tool loop. Использовать этот контейнер одновременно для A и B нельзя.
- `prepare_model` устанавливает промпт, параметры и Tools/Skills выбранного агента, ограничивает Skill readers и запускает destination inlets. `agent_projection` исключает служебные результаты Router и других агентов: результаты параллельной группы не попадут к C автоматически.
- `OWUIAdapter` изолирует внутренние APIs и допускает только OWUI 0.12.3. Сборщик `tools/build_functions.py` создаёт два самостоятельных установочных файла. Нужные новые модули должны попасть в эту сборку.
- Существующие `tests/native/test_chain.py` проверяют streaming Tool loop с тестовым транспортом, но не являются проверкой штатного запуска дочерних задач или браузерного открытия чатов.

Наблюдения по установленному OWUI 0.12.3 и исходникам тега:

- [Builtin `delegate_task`](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/tools/builtin.py) не принимает Model ID. Его внутренний исполнитель получает `metadata.model_id`, сохраняет `chat_context` и запускает новый запрос через `CHAT_COMPLETION_HANDLER`.
- [Исполнитель `utils/subagents.py`](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/utils/subagents.py) создаёт внутренний чат в обоих режимах. Foreground ждёт выполнения и возвращает строку, ограниченную `subagents.max_output`; ID дочернего чата и структурированные файлы в эту строку не входят. Дочерний запрос получает `state.internal=True` и собственный ASGI scope.
- [Native middleware](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/utils/middleware.py) распараллеливает только вызовы с точным именем `delegate_task`. Обычные Tools выполняются последовательно. Полный native pipeline также способен добавить широкий каталог Skills пользователя.
- [Хранилище чатов](https://github.com/open-webui/open-webui/blob/v0.12.3/backend/open_webui/models/chats.py) исключает `meta.internal=True` из обычных списков, поиска и папок. Чтение конкретного чата проверяет штатный доступ. Маршрут `/c/<id>` использует обычный компонент чата.

Это подтверждает точки интеграции, но не работоспособность предлагаемого моста: её проверяет первый этап реализации.

## Goals / Non-Goals

**Goals:**

- Разделить получение результатов задач и передачу владения ответом.
- Использовать существующую подготовку агента и native исполнение Tools без объединения возможностей моделей.
- Сохранить один видимый основной чат, доступную историю выполнения и прежний двухфайловый комплект.
- Разрешить использовать настроенные Tools/Skills/MCP модели без отдельных grants пользователя, разделив владельца ресурсов и пользователя исполнения во всех путях.
- Проверять фактическое выполнение callable, перекрытие задач во времени и результат каждого этапа, а не только схемы Tools.

**Non-Goals:**

- Графовый движок, рекурсивный вызов агентов, фоновые уведомления с автоматическим возобновлением Router и восстановление после рестарта.
- Отдельная БД, новый сервер, изменение frontend или исходников OWUI.
- Перенос локальных путей между изолированными средами, копирование произвольных файловых систем и автоматический повтор действий.
- Изменение текущего публичного результата `lite_delegate` или внедрение ранее обсуждавшегося компактного контракта.

## Decisions

### 1. Одна ожидаемая группа и последующий handoff

Добавляется inline Tool `lite_parallel(tasks)`. Задание содержит `agent_id`, непустой `task` и необязательный список `file_ids` из доступных вложений. `agent_id` использует тот же request-local enum, что и `lite_delegate`. Дополнительные поля выбора модели, параметров, Tools и Skills модель не задаёт.

Предлагаемые административные Valves Preparation: `max_parallel_tasks=4` и `parallel_timeout_seconds=300`. При значении `max_parallel_tasks=0` функция отключена; остальные поддерживаемые значения — целые числа от двух. Одна группа содержит от двух до установленного предела задач. Повторение агента разрешено для разных заданий, но каждая задача получает отдельное исполнение. Эти значения — проектные defaults для проверки на приёмке.

`lite_parallel` публикуется только Router, при непустом персональном реестре, включённом штатном `subagents.enable` и сохранённом основном чате. Для временного чата возвращается понятная причина недоступности. Персональная схема и callable публикуются в ранний общий реестр, как у текущего inline delegate. Коллизия зарезервированного имени завершается ошибкой настройки. Клиентские списки ресурсов и UserValves этот набор не меняют.

Состояние группы отдельно от `active_agent`: `idle -> running -> completed | partial | failed | cancelled | timed_out`. Для задач терминальные состояния — `completed`, `failed`, `cancelled`, `timed_out`. После запуска группа считается использованной независимо от исхода. Router остаётся исполнителем основного ответа до финального `lite_delegate`. Последующие реальные сообщения начинают обычный новый цикл Router.

```text
                   +--> task A --+
User --> Router ---|            |--> all results --> Router --> handoff C
                   +--> task B --+                       |
                                                       +--> own answer
```

Вызов группы должен быть единственным Tool call своей фактической генерации. По серверному наблюдению генераций отклоняются совместный `lite_parallel` с handoff, несколько групп и смешивание с другими Tools. Уже завершённые Skill reads, объединённые OWUI в историческую запись, не считаются конкурентными вызовами. Проверка действует в обоих управляющих callable до запуска работников или принятия handoff. Другие Tools, которые middleware уже исполнил, не повторяются и не объявляются отменёнными задним числом.

Альтернатива — несколько одиночных новых Tools. Она зависит от специального имени в middleware либо запускает их последовательно. Одна batch-операция явно задаёт границу ожидания и не использует имя штатного `delegate_task` для подмены его смысла.

### 2. Native исполнитель и доверенный вход в выбранного агента

Новый слой исполнения группы вызывает внутренний `subagents.delegate` в режиме `background=False` для каждой задачи и ждёт их параллельно с ограничением количества и времени. Все импорты внутренних APIs остаются в `owui_adapter.py`. Прямое выполнение только одного completion недостаточно: работнику нужен весь native цикл Tools.

Предлагаемый мост:

1. Родительский запрос создаёт случайный серверный ticket для каждой задачи. Запись содержит пользователя, основной chat/message/request ID, индекс задачи, выбранный agent ID, снимок входных данных и пределы выполнения. Снимок включает конкретное задание, исходный пользовательский запрос, общую видимую переписку текущей ветки и выбранные доступные вложения; служебная трасса и инструкции Router/других работников не копируются. Эти данные передаются работнику как контекст задания.
2. Адаптер передаёт native исполнителю минимальную metadata. Транспортная модель — публичная Router-модель, чтобы обязательный Preparation Filter и Pipe присутствовали в дочернем запросе. В `chat_context` передаётся только серверная ссылка на ticket; туда не копируются промпт, параметры, Skill versions, Tools и фильтры Router. `file_ids` передаются штатно после проверки принадлежности вложениям.
3. Preparation распознаёт внутреннее исполнение только при сочетании серверного `state.internal=True`, действующего ticket и штатной записи дочернего чата с ожидаемыми владельцем и родителем. На первом входе ticket связывается с единственными child chat/message IDs. Клиентский JSON, роль `user`, исторический результат или один ticket без этих проверок не запускают этот режим.
4. Вместо discovery и повторной маршрутизации создаётся новый дочерний runtime с заранее выбранным агентом. Pipe применяет обычную подготовку его текущей Workspace Model и его защищённые readers. Router LLM в дочерней задаче не вызывается. `lite_parallel`, `lite_delegate` и штатная рекурсивная делегация работнику не публикуются.
5. Native pipeline ведёт запись исполнения и Tool loop в дочернем чате. Task-owned состояние хранит фактического агента независимо от транспортного ID Router; этот ID агента сохраняется также в namespace metadata дочернего чата без замены штатных `internal/type/parent_*` полей.

Для связи двух загруженных Functions используется выделенный временный registry в `request.app.state`, индексированный непредсказуемыми tickets и привязанный к родительскому запросу. Это не общий текущий агент: записи и mutable-контейнеры разных задач не пересекаются. Tickets удаляются при завершении, ошибке и отмене группы. Возобновление в другом процессе или после рестарта не заявляется; текущий native запуск происходит внутри того же процесса.

Каждый дочерний ASGI scope владеет своим runtime, metadata, executable Tools, Skill state, историей и MCP-сессиями. `app.state.MODELS`, конфигурация Functions и `CHAT_COMPLETION_HANDLER` не изменяются. Проверки используют явно разделённые роли из решения 7: модель и пользовательские данные проверяются от пользователя чата, настроенные ресурсы — от владельца модели. Лимиты сабагентов и глобальные запреты ресурсов сохраняются. Родительские Tools остаются неизменными во время сбора.

Прямой native запуск `model_id=agent_id` рассмотрен, но сам по себе не обеспечивает ограничения readers и каталога Skills нашего Pipe. Собственный новый Tool loop дублировал бы middleware. Поэтому выбран мост через существующую подготовку, с обязательной проверкой до продуктовой интеграции.

### 3. Предварительная проверка и обязательный технический gate

До dispatch проверяются структура всей группы, разрешённость всех адресатов и файлов, лимиты, пригодность сохранённого чата и поддерживаемый режим исполнения. Группа с недопустимым заданием не начинает остальные задачи. Перед фактическим стартом каждого работника доступ пользователя к модели и права её владельца на обязательные ресурсы проверяются повторно; отзыв прав после предварительной проверки отражается как ошибка задачи.

Первый эксперимент выполняется на изолированной БД OWUI 0.12.3 с локальным детерминированным провайдером. A и B имеют разные промпты/температуры, одноимённые Tools с разными результатами, собственные Skills и доступный пользователю посторонний Skill. Тест доказывает:

- фактическое перекрытие интервалов A и B без вызова Router LLM в дочерних задачах;
- успешное исполнение двух последовательных Tools у каждого работника;
- ограничение readers, включая callable refresh, и отсутствие чужих инструкций/возможностей;
- регистрацию child IDs, чтение полного ответа и доступного файлового результата;
- открытие `/c/<child_id>` скрытой модели в браузере и сохранение чата скрытым из списка;
- остановку всех незавершённых дочерних задач при отмене родителя;
- сохранение штатного режима подтверждения Tools: отсутствие подтверждения не считается выполнением и не приводит к принудительному `full`.

Точный поддерживаемый путь native приостановок проверяется на этом этапе. Если ожидание подтверждения нельзя корректно поддержать, группа в таком режиме отклоняется до dispatch с явной ошибкой совместимости. Никакого автоматического обхода проверки или продолжения частично работающего решения нет. Если мост в целом требует патча OWUI либо не сохраняет изоляцию, дальнейшая интеграция останавливается и дизайн пересматривается с пользователем; скрытого fallback на новый движок нет.

### 4. Результат задачи и входные данные для C

После возврата native вызова адаптер использует привязанные child IDs и перечитывает сохранённое сообщение. Успех требует терминального завершения без ошибки. Приостановленное сообщение, пустой ещё работающий placeholder и отмена не считаются успешным прогнозом.

`subagents.max_output` не определяет полноту нашего результата: читается полный сохранённый текст/структурированный output и поддерживаемые ссылки на файлы. Если полный результат недоступен либо не помещается в допустимый контекст, система возвращает явную ошибку или доступный полный файл; строка с усечением не становится успешным полным прогнозом. Автоматический пересказ и перезапуск не вводятся.

Публичный результат `lite_parallel` содержит общий исход и упорядоченные по входному списку результаты: агент, статус, текст, доступные файлы, ссылка на чат и понятная ошибка при её наличии. Секретный ticket, nonce, auth token, ASGI state и внутренняя трасса туда не включаются. Публичный URL необходим для просмотра, отдельный технический ID рядом с ним не нужен.

До handoff пакет результатов хранится в доверенном состоянии группы. При передаче C подготовка добавляет его как явно обозначенные входные данные от A/B с исходным заданием и источником каждого результата. C получает весь пакет, а не обязательный пересказ Router. Служебные Tool exchanges и полные Skill instructions работников остаются в дочерних чатах. Совпадение имени Tool или наличие `agent_id` в произвольном тексте не создаёт чужую историю или подтверждение результата.

Поддерживаются штатные файловые ссылки OWUI, доступные тому же пользователю. Перед передачей файлы проверяются заново и добавляются в эффективные вложения/контекст получателя согласованно. Произвольный локальный путь работника не считается переносимым артефактом. Исходные сообщения и вложения пользователя не переписываются ради подготовки C. Сохранённый родительский Tool result позволяет Router видеть результаты и ссылки при следующем сообщении; новый запрос не восстанавливает активную группу.

Альтернатива — подставить результат A как Tool result C. Она нарушает авторство и текущий контракт истории. Обязательный пересказ результатов Router добавил бы генерацию с риском потери данных.

### 5. Ошибки, барьер и жизненный цикл

Группа ждёт терминальных исходов всех задач; ошибка одного работника не повторяет его действия и не превращает результат другого в ошибку. После успеха всех задач возможен финальный handoff. После `partial/failed/timed_out/cancelled` любой handoff этого запроса отклоняется, Router показывает доступные результаты и причины. Пользователь может дать новую инструкцию следующим сообщением.

По истечении общего срока, при Stop или отмене родителя адаптер останавливает незавершённые native tasks по известным child IDs, дожидается завершения cleanup в пределах ограниченного срока и освобождает MCP-сессии/tickets. Отмена до связывания child ID должна также завершать native dispatch без оставленного работника. Позднее завершение не возобновляет Router и не запускает C. Уже совершённые действия не откатываются и не исполняются повторно.

Фоновый `background=True` не используется: отдельные уведомления о завершении не гарантируют барьер A+B и могут создавать новые внутренние user-сообщения родителя. Ожидание в одном запросе сохраняет нынешнюю границу «новое реальное сообщение -> новый Router».

### 6. Просмотр без отдельной папки

При связывании дочернего чата публикуется событие статуса: название агента, состояние и относительная ссылка `/c/<child_id>`. Ссылка сразу сохраняется в поддерживаемой видимой части родительского сообщения, чтобы пережить Stop и перезагрузку до возврата Tool result; одного transient status или невидимой metadata недостаточно. Ссылки входят также в сохраняемый результат группы, включая доступные ошибочные исполнения. Конкретное штатное событие сохранения и его сосуществование с native streaming проверяются в техническом gate. Если сбой произошёл до создания чата, ссылка не выдумывается.

Пользователь открывает обычный чат и видит сохранённое задание, Tool calls/results и итог. Полные скрытые рассуждения или несохранённые данные модели не обещаются. Просмотр не является автоматическим продолжением родительской группы. Дочерние чаты сохраняют `internal=True`; обычное открытие не снимает флаг. Штатные права чтения и удаление дочерних чатов при удалении родителя через соответствующий native endpoint сохраняются.

При отсутствии доступа или удалении чата native API не выдаёт его содержимое. Для удалённого выполнения принимается штатное поведение OWUI 0.12.3: переход по сохранённой ссылке возвращает на главную без уведомления. Router не восстанавливает чат и не повторяет Tools; отдельное сообщение об ошибке или frontend-патч не требуются.

Не вводятся отдельная папка, публикация чатов другим пользователям, новый endpoint или обязательный frontend-плагин. Браузерная приёмка проверяет реальное отображение ссылки и скрытой модели: доступность backend API не заменяет эту проверку.

### 7. Владелец ресурсов и пользователь исполнения

Общая подготовка модели разделяет две роли:

- **Пользователь исполнения** — владелец текущего запроса. Его права определяют доступ к Router, выбранному агенту и цепочке базовых моделей, обычным файлам и чатам. Он передаётся в `__user__` локальных Tools, определяет их UserValves и пользовательскую авторизацию внешних вызовов.
- **Владелец ресурсов** — владелец актуальной Workspace Model, чей набор готовится. Его права определяют возможность загрузить настроенные Tools, Skills и подключения. У Router это владелец публичной Router-модели, а не транспортной LLM; у A/B/C — владелец соответствующего агента. Владелец не выбирается из клиентского body, metadata или аргументов Tools.

Текущая серверная запись модели даёт согласованный снимок владельца и attachments на одну подготовку. Изменение владельца или набора при следующей подготовке не использует прежний снимок. Внутренний transport Router для параллельной задачи не превращается во владельца ресурсов работника: им остаётся владелец фактической выбранной модели.

#### Реестр и ресурсы Router

Discovery сохраняет штатную проверку доступа пользователя к моделям. Наличие, активность и read-доступ routing Skill проверяются для владельца публичного Router. Отсутствие grants пользователя на Skill больше не исключает разрешённого агента. Для базовых Tools/Skills из Valves действует тот же владелец. Непригодный routing Skill исключает отдельного адресата с диагностикой; отсутствие владельца Router или обязательного базового ресурса завершает подготовку ошибкой.

#### Рабочие Tools, UserValves и MCP

Локальные и серверные Tools загружаются только по ID актуальной конфигурации, с проверкой доступа владельца. При этом административные Valves самого Tool сохраняются, `__user__` содержит пользователя чата, а UserValves выбираются по его ID. Native `get_tools` OWUI 0.12.3 использует один аргумент пользователя и для ACL, и для поиска UserValves: простая подстановка владельца недостаточна. Версионный адаптер должен разделить эти назначения и подтвердить результат настоящим вызовом и callable refresh.

Для MCP/серверных подключений право использовать настроенное подключение проверяется от владельца, а пользовательские OAuth-токены, session auth и forwarded user headers формируются от пользователя исполнения. Общие bearer credentials остаются серверной конфигурацией подключения. Native `connect_mcp_server` также связывает ACL и построение заголовков одним `user`; разделение выполняется внутри адаптера OWUI 0.12.3 без изменения общего каталога подключений или глобальной подмены функций. Отсутствие требуемой пользовательской авторизации возвращает ошибку, а не запускает вызов с токеном владельца. У каждой задачи и пользователя остаётся собственная MCP-сессия и прежний cleanup.

#### Skills и граница набора

Манифест и все три reader — `view_skill`, `read_skill_file`, `grep_skill_files` — сначала ограничены текущим набором модели. Для прошедшего эту проверку Skill штатное чтение выполняется с правами соответствующего владельца, включая активность, версии, файлы и пагинацию. Контекст владельца применяется только к операциям чтения Skills; он не заменяет пользователя остальных Tools. Права владельца на посторонний Skill не расширяют allowlist. Обёртка сохраняет обе роли, набор и проверки на native refresh и Tool-продолжениях.

#### Отказы и пользовательские данные

Отсутствующий владелец, недоступный ему обязательный Tool/Skill/подключение или глобально выключенный ресурс дают явную ошибку подготовки; неполная генерация, подстановка другого владельца/администратора и автоматический повтор не выполняются. Перед каждым стартом повторно проверяется доступ пользователя к модели; при подготовке и применимых вызовах — актуальные ресурсы и права владельца.

Пользователю не выдаются новые grants. Приватные Tools/Skills/подключения остаются недоступны ему через отдельные native APIs и для самостоятельного подключения. Передача вложений, проверка результатов и просмотр истории используют права пользователя чата. Авторизация ресурса владельцем модели не даёт доступа к чужим чатам или обычным файлам и не меняет владельца созданного пользовательского артефакта. Штатное скрытие агентов по-прежнему относится к селектору, а не к запрету прямых API-вызовов разрешённой модели.

Дополнение проверяется отдельным native gate до продуктовой адаптации: приватные ресурсы без grants пользователя, отличающиеся UserValves владельца и двух пользователей, все три reader после refresh и разделение ACL подключения от OAuth/forwarded identity. Результаты исходного parallel gate остаются доказательствами прежнего поведения. При невозможности сохранить роли без патча OWUI пересматривается именно эта часть дизайна; скрытой подстановки владельца в исполнение не допускается.

## Risks / Trade-offs

- Внутренний API OWUI не гарантирует стабильности между версиями -> сохранить version guard 0.12.3 и native gate, не объявлять поддержку следующей версии автоматически.
- Native pipeline может восстановить широкий каталог Skills или раскрыть родительские настройки -> final preparation выбранного агента заменяет контекст и executable registry; проверяются все три reader и продолжения.
- Конкурентные задачи могут менять общий registry или неправильно закрыть MCP cancel scopes -> отдельные дочерние scopes и сессии, проверки одновременных пользователей и отмены.
- Native результат может быть усечён, ожидать подтверждения или не содержать файлов -> читать сохранённое терминальное сообщение и проверять полноту/доступ, не считать строковый ответ достаточным доказательством успеха.
- Возросшие токены и время -> административные пределы группы, штатные лимиты OWUI, передача полных доступных файлов вместо скрытого усечения; лимиты не гарантируют достаточную параллельную мощность LLM-сервера.
- Временный мост существует только пока жив родительский запрос -> отсутствие восстановления явно входит в ограничения; рестарт не считается успешным выполнением.
- Native загрузчики связывают разрешения и личные настройки одним пользователем -> явно разделить владельца ресурсов и исполнителя в версионном адаптере; проверить UserValves, OAuth, forwarded identity и отсутствие утечек между запросами.
- Права владельца шире набора агента -> сохранять серверный список ресурсов и строгие Skill readers; возможность прочитать посторонний ресурс владельцем не разрешает его модели.

## Migration Plan

1. Пройти технический gate на отдельном OWUI и зафиксировать доказательства, включая браузер. Затем реализовать продуктовый интерфейс без патча OWUI.
2. Пересобрать и заменить обе Functions согласованной версией; проверить наличие новых модулей в самостоятельных exports. Дополнительный Workspace Tool не устанавливать.
3. Проверить `subagents.enable`, штатные ограничения и новые административные пределы. Обновить инструкции Router и routing Skills: независимые задания возвращаются через `lite_parallel`, финальная передача выполняется отдельно через `lite_delegate`.
4. Выполнить приёмку двух групп пользователей, A+B->C, доступа к дочерним чатам и исходных A->B->Router сценариев. Обновить документацию ограничений и результатов проверки.
5. Для отключения новых групп установить `max_parallel_tasks=0`. Для полного rollback вернуть предыдущую пару Functions. Сохранённые внутренние чаты остаются штатными записями OWUI; миграция схемы и удаление пользовательских данных не требуются.
6. После дополнения о правах пересобрать оба exports и проверить обычный handoff и A+B->C без grants пользователей на ресурсы. Обновить инструкции установки и приёмку; автоматической выдачи или отзыва существующих grants нет. При синхронизации с базовым change заменить прежнее требование проверки всех ресурсов от пользователя новым разделением ролей, сохранив проверки пользователя для моделей и данных.
