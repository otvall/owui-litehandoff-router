# Design

## Context

Router Preparation связывает внутренний дочерний запрос с заданием по серверному ticket. Pipe подготавливает ресурсы выбранного агента, а штатный Tool loop OWUI исполняет его вызовы. Родитель ждёт состояние всей группы и читает сохранённые ответы и файлы дочерних чатов. [Привязка и сбор результатов](../../../src/lite_handoff_router/parallel.py) · [Текущий адаптер](../../../src/lite_handoff_router/owui_adapter.py)

Два прогона одного набора на изолированных официальных slim-образах дали 92 успешные проверки на 0.13.3 и 12 проваленных проверок и 11 ошибок на 0.13.5. Отдельная проба на 0.13.5 с синтетическим обработчиком подтвердила отказ старой сигнатуры и фоновую семантику. Оба воркера стартовали, а первый отчёт создал новый ход родителя до завершения второго. Набор также выявил ошибки в интеграциях Machines, обычных файлов, MCP и защищённого контекста. [Релиз OWUI 0.13.5](https://github.com/open-webui/open-webui/releases/tag/v0.13.5)

## Goals / Non-Goals

Цель — провести весь запрос A+B → C через штатный Tool loop 0.13.5 с прежними границами полномочий и предоставить штатный просмотр дочерних чатов. В объём входят два самостоятельных экспорта Router и их существующие сценарии.

Фоновые поручения с ответом в отдельном ходе, синхронизация списка агентов Router с карточкой Sub-agents, собственный планировщик и отдельный фронтенд для просмотра выполнений находятся вне объёма. Штатная вкладка Threads достаточна для этой версии. Автоматическое разделение экрана остаётся отдельным решением интерфейса.

## Decisions

### Сохранить групповую координацию в Router

Сохранить инструмент с именем `delegate_task`, по которому OWUI группирует вызовы и сопоставляет ответы с исходными call IDs. Router проверяет всю группу и разрешения на вложения до запуска, ждёт терминальных исходов и возвращает результат каждого задания в порядке исходных вызовов. При остановке воркера, ошибке или таймауте применяются действующие правила частичных результатов и блокировки C. Проверку глобального включения и нового административного разрешения OWUI 0.13.5 выполнять при публикации и перед dispatch; пользовательские переключатели чата не задают область ресурсов Router. [Группировка OWUI](https://github.com/open-webui/open-webui/blob/v0.13.5/backend/open_webui/utils/middleware.py#L6037-L6061) · [Право сабагентов](https://github.com/open-webui/open-webui/blob/v0.13.5/backend/open_webui/utils/tools.py#L842-L851)

Builtin выбранных моделей подходит для самостоятельных фоновых поручений. Его возврат `dispatched`, наследование родительских ресурсов и последующий автозапуск ответа расходятся с контрактом A+B → C. Ожидание после фонового dispatch оставляет активным штатный механизм добавления отчёта в родительский чат. Использование `automation_id` подменяет назначение поля и затрагивает другие ветви жизненного цикла. Патч OWUI потребовал бы изменить существующий способ поставки. [Запуск и отчёты](https://github.com/open-webui/open-webui/blob/v0.13.5/backend/open_webui/utils/subagents.py#L564-L648)

### Переиспользовать внутреннее исполнение и жизненный цикл OWUI

В 0.13.5 адаптер создаёт стандартный внутренний дочерний чат, привязанный к родительскому сообщению, создаёт отдельный аутентифицированный запрос пользователя и запускает внутренний `CHAT_COMPLETION_HANDLER` как штатную задачу дочернего чата. В этой ветке обработчик ждёт внутреннюю генерацию. Повторно использовать доступный серверный механизм аутентификации сабагента и стандартное хранение сообщений. Дочерняя задача возвращается только ожидающему Router, поэтому штатная постановка фонового отчёта в очередь родителя не участвует. Для 0.13.3 сохраняется вызов явного foreground `delegate`. Различия внутренних контрактов определяются по доступному API в адаптере, без запрета запуска по строке версии. [Внутренний обработчик OWUI](https://github.com/open-webui/open-webui/blob/v0.13.5/backend/open_webui/main.py#L1914-L1984)

Использовать текущую проверку ticket для привязки пользователя, родителя, сообщения и задания и повторно проверять права перед подготовкой ресурсов. Регистрировать дочернюю задачу и отправлять штатное событие обновления списка, чтобы API детей и UI видели один и тот же сохранённый запуск. При остановке из Threads, остановке родителя и таймауте закрывать принадлежащие выполнению ресурсы, дожидаться уборки и фиксировать фактический исход. Поздний ответ или уже завершившийся внешний Tool не порождает повторного запуска. Все результаты и вложения брать из доступного сохранённого чата, соблюдая текущую границу доступных пользовательских данных. [Список Threads](https://github.com/open-webui/open-webui/blob/v0.13.5/backend/open_webui/routers/chats.py#L1460-L1492)

### Адаптировать изменившиеся нативные контракты

- Обработать источники идентификаторов Machines и старые настройки Terminals на границе OWUI. Сохранить серверный выбор ресурса модели и вызов от имени пользователя выполнения.
- Адаптировать тип возвращаемых данных файла и авторизацию MCP без ослабления проверок или подстановки личности владельца модели вместо пользователя.
- Использовать актуальное хранилище сообщений OWUI и учитывать допустимую форму записей Tool calls. Проверять пары вызов–результат, идентичность исполнителя и происхождение защищённого контекста при фактической генерации. Старые сохранённые сообщения должны проходить те же проверки после штатной миграции.
- Публиковать одну пару автономных Functions с информационной отметкой 0.13.5. Локальная тестовая матрица покрывает обе версии. Живой GLM-прогон используется для проверки выбора инструментов, которую синтетический провайдер не измеряет.

## Risks / Trade-offs

- Внутренние API OWUI могут меняться между версиями → локализовать зависимости в адаптере и покрыть их нативными тестами на обеих версиях.
- Дочерняя задача может остановиться до завершения привязки → регистрировать идентификаторы до начала работы, синхронизировать привязку с остановкой и проверять состояние сохранённого сообщения перед выдачей результата.
- Нативные Threads отображают состояния OWUI, а группе нужны точные исходы → сохранить текущие ссылки и статусы Router для ошибок, отмены и таймаута.
- GLM может выдать задания последовательно или повторить Tool при синтезе → измерить это на фактическом потоке вызовов с синтетическими данными и отдельным протоколом. Прогон управляемой модели подтверждает контракт ПО, а не поведение GLM.

## Migration Plan

Подготовить два изолированных инстанса и прогнать существующую матрицу. Затем проверить обновление штатной миграцией OWUI на копии базы 0.13.3 с основным чатом, сохранённой передачей и дочерними чатами. Установить новый экспорт, восстановить `AGENTS`, Valves и административные настройки и повторить браузерную проверку. Для рабочего обновления сохранить резервную копию данных и старые экспорты. При откате 0.13.3 поднимается на копии до миграции с прежними экспортами и настройками. [Штатная миграция](https://github.com/open-webui/open-webui/releases/tag/v0.13.5)
