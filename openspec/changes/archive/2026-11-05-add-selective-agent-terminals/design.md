# Design

## Context

Мотивация и границы пользовательского изменения описаны в `proposal.md`. Контракты находятся в трёх delta specs этого change.

Исследован текущий checkout и установленный пакет OWUI 0.12.3:

- `model_execution.prepare_model` загружает актуальную Workspace Model и владельца, собирает новый registry Tools, добавляет только выбранные встроенные Skill readers и затем выполняет inlet-фильтры адресата. Унаследованные терминальные Tools таким образом не сохраняются.
- `ResourceScope` проверяет только текущие Tool/Skill IDs; идентификатор `terminal:<id>` сейчас ошибочно попал бы в ветку обычного Tool. Понадобится отдельный вид ресурса.
- `parallel.py` создаёт native подзадачу без `terminal_id`; целевая модель и дочерние chat/message IDs устанавливаются при подготовке работника. Здесь нельзя начинать наследовать выбор родителя ради терминального подключения.
- OWUI хранит подключения в `Config['terminal_server.connections']`. `get_terminal_tools` разрешает подключение по ID, проверяет ACL, получает specs/инструкции и создаёт callables с `type='terminal'` и `tool_id='terminal:<id>'`. Однако один параметр `user` используется и для ACL, и для `X-User-Id`, поэтому прямой вызов от владельца модели подменил бы исполнителя, а от пользователя потребовал бы лишний прямой grant.
- Штатная маршрутизация использует `X-Session-Id = metadata.chat_id`; helpers `terminal_context_available`, `terminal_context_id` и `get_terminal_server_url` учитывают политику подключения и orchestrator. Разные chat IDs сами по себе не изолируют файловую систему raw Open Terminal.
- Внутренним native сабагентам OWUI не предоставляет интерактивные `read_user_terminal` и `send_user_terminal_input`. Терминальный `display_file` создаёт запись `source='open_terminal'`, которая отличается от обычного OWUI file ID.

Текущая документация исключает терминальных агентов из поддерживаемой поверхности. Это ограничение меняется только в рамках серверных команд выбранного подключения. Production-инсталляция и её терминальные backend не исследованы; основание совместимости — локальная штатная 0.12.3 и последующий disposable acceptance.

## Goals / Non-Goals

**Goals:**

- Подключить терминальный ресурс в общей атомарной подготовке модели, чтобы одна реализация работала для handoff, работника и финального агента.
- Сосредоточить знание native terminal API в адаптере, а проверку принадлежности ресурса модели — в `ResourceScope`. Подготовка модели получает готовые Tools и одну строку серверных инструкций.
- Оставить существующие установки без привязок и их Tools/MCP/Skills совместимыми без миграции.

**Non-Goals:**

- Создание или удаление сред, принудительная изоляция файловой системы, изменение политики cwd/хранения, новые контейнеры и остановка общего terminal backend.
- Терминал публичного Router, персональные/direct/browser подключения, управление панелью пользователя, автоматический импорт терминальных Skills и AGENTS.md.
- Новый транспорт файлов между агентами, автоматическое копирование входных OWUI вложений в терминал, новые права на terminal download endpoints или изменение схемы делегирования.
- Реализация «терминального режима» для прямых вызовов модели в обход Router или патч OWUI.

## Decisions

### 1. Необязательная привязка хранится в metadata агента

Предлагаемое публичное поле конфигурации: `info.meta.lite_handoff.terminal_id`. Пример metadata Workspace Model:

```json
{
  "toolIds": ["a_lookup"],
  "skillIds": ["a_working_guide"],
  "capabilities": {"terminal": true},
  "lite_handoff": {"terminal_id": "internal-analysis"}
}
```

`lite_handoff` отсутствует, `terminal_id` отсутствует, равен `null` или пустой строке после удаления краевых пробелов — терминал выключен. Непустое значение должно быть строкой с точным ID зарегистрированного подключения; неверный тип или некорректный контейнер настроек возвращает ошибку. Явное `capabilities.terminal=false` вместе с непустой привязкой считается конфликтом конфигурации. При отсутствии флага сохраняется native default, но без привязки он ничего не включает.

Привязка читается только из актуальной серверной Workspace Model адресата; не из `body`, `chat_context`, UserValves или аргументов Tool. У Router она не применяется. `AGENTS` остаётся отображением model ID → routing Skill ID. Несколько выбранных агентов могут указывать одно подключение; уникальный сервер на каждого не требуется.

`ModelMeta` 0.12.3 допускает дополнительные поля (`extra='allow'`), поэтому миграция БД и интерфейс OWUI не нужны. В документации следует показать настройку через штатный экспорт/импорт JSON или API сохранения модели с сохранением остальных metadata. Не предполагать, что стандартный UI уже содержит редактор этого поля.

Рассмотрены: привязка в `AGENTS` смешала бы маршрутизацию с рабочими ресурсами; общая Valve усложнила бы сопровождение карточек; выбор в родительском чате противоречит принятому закреплению за выбранным агентом.

### 2. Терминал получает отдельный адаптер с разделёнными authority и actor

Добавить в `OWUIAdapter` узкую поверхность разрешения подключения и загрузки терминальных Tools. При необходимости вынести разбор настройки и композицию возможностей в `terminals.py`, не превращая `capabilities.py` в универсальный framework.

Адаптер использует штатные `Config`, `get_terminal_servers`, `has_connection_access` с группами владельца и terminal routing/schema helpers. Он проверяет глобальный `ENABLE_TOOL_SERVERS`, `enabled`, доступность chat-контекста, наличие необходимого сохранённого chat ID и доступных серверных specs. Полностью пустой набор после исключения интерактивных операций — ошибка подготовки.

Создание запросов повторяет native семантику terminal API с использованием существующих helpers: заголовки и cookies строятся с **пользователем исполнения**, затем явно задаются `X-User-Id`, фактический `X-Session-Id` и вычисленный `X-Terminal-Context-Id`. Поддерживаются штатные для терминала режимы `bearer`, `session`, `system_oauth`, `none`; другие режимы возвращают ошибку совместимости. Для обязательных пользовательских session/OAuth credentials отсутствие токена — явная ошибка без fallback. Серверный bearer key остаётся конфигурацией подключения.

Вызовы выполняются через native `execute_tool_server` с актуальным подключением и разрешённой operation. Сохраняются native schema cleanup, дополнение `display_file` и описание текущего cwd для `run_command`, инструкции сервера и возвращаемая форма результата. Callables получают `type='terminal'` и `tool_id='terminal:<id>'`, чтобы штатный loop распознал terminal events/results. Интерактивные операции `read_user_terminal` и `send_user_terminal_input` исключаются во всех трёх ветках запуска агента.

Прямой `get_terminal_tools(..., owner, ...)` отклонён из-за подмены личности; вызов от actor отклонён из-за обязательного прямого ACL. Monkey patch глобальных ACL, выдача grants и impersonation request не используются. Небольшая адаптация существующего паттерна OpenAPI/MCP в этом репозитории сохраняет две роли без патча сервера.

### 3. Подготовка заменяет терминальную область до публикации

В `prepare_model` после чтения актуальной модели определить привязку; очистить унаследованные terminal selection/каталоги и direct terminal descriptors из рабочего metadata. Исходный сохранённый запрос не изменять. Для агента с привязкой установить доверенный `metadata.terminal_id`; для остальных и Router удалить активный terminal ID. Системные сообщения строятся заново существующей проекцией, поэтому серверные инструкции терминала добавляются один раз в новый draft и не переносятся следующей модели.

Загрузить terminal Tools до истории, публичных schemas и inlet-фильтров, рядом с остальными возможностями. Не передавать их через `adapter.tools` как Workspace Tool IDs. Проверить конфликты имён с обычными Tools, MCP, Skill readers и routing Tools; вместо перезаписи вернуть ошибку подготовки.

В `ResourceScope` добавить необязательную привязку и отдельную проверку терминального ресурса. Перед исполнением проверить актуальный доступ actor к модели, неизменность owner, привязку к тому же terminal ID, capability, глобальные/серверные ограничения и ACL владельца. Старый callable после смены ID отклоняется; следующая полноценная подготовка может загрузить новую привязку. Адаптер заново разрешает текущую конфигурацию и проверяет наличие operation перед HTTP-вызовом, затем строит свежие credentials actor. Процессного кэша callables/пользовательских заголовков не добавлять.

Терминальный scope guard проходит через `bind_tool_context`, чтобы native refresh не снимал проверку. После inlet проверять неизменность ID и защищённого набора terminal Tools: callable, schema, `tool_id`, `type` и соответствие публичных schemas. Проверка действует и при отсутствии привязки, запрещая фильтру добавить terminal ресурс. Допустимые изменения контекста обычных Tools сохраняются. Только полностью подготовленный draft публикуется существующим механизмом; ошибка оставляет предыдущего исполнителя целым.

### 4. Параллельная ветка разрешает терминал после привязки дочернего контекста

Не добавлять `terminal_id` в пользовательский контракт `lite_parallel` или в `native_metadata` родительского dispatch. Работник получает terminal binding при своей обычной `prepare_model`, когда уже известны его настоящий дочерний chat ID и целевая Workspace Model. Native task сначала создаётся прежним путём, затем подключается ресурс адресата.

Для обычного и финального handoff используется основной chat ID; для каждого параллельного задания — собственный дочерний. Один и тот же агент в двух заданиях получает разные chat session IDs; backend с общей средой по-прежнему может предоставлять общий filesystem. Это принятое штатное поведение, а не неисправность Router. Отдельные task workspaces пользователь явно исключил из первой версии.

### 5. Отмена и файлы сохраняют существующие границы

HTTP-вызов терминала принадлежит текущей coroutine. Не создавать detached задачи или скрытые retries команд. Отмена native работника должна распространяться на ожидание HTTP-вызова; поздний результат не публикуется и не запускает C. Отмена HTTP не гарантирует завершения уже запущенного удалённого процесса: это свойство backend, а не новая обязанность управления средой. Общий сервер и его сохранённые файлы не удаляются при cleanup.

Текстовые результаты команд передаются через обычную историю Tool и полный результат работника. Терминальный путь или `source='open_terminal'` не превращается автоматически в переносимый OWUI file ID. `parallel.collect_result` и `adapter.file` продолжают требовать доступный пользователю обычный файл; если native terminal attachment не соответствует этому контракту, вернуть явную ошибку, сохранив действующую обработку неполной группы. Не повышать права на download endpoint и не объявлять такой результат успешным переносом. Сценарий полноценного переноса терминальных артефактов требует отдельного change.

### 6. Проверка разделяет локальные контракты и настоящий native loop

- Unit-проверки подготовки и scope: default off, опциональная привязка, отклонение client override, native capability conflict, отсутствие/запрет подключения, коллизии, inlet-подмена, native refresh, смена owner/привязки и сохранение старого исполнителя при ошибке.
- Native-проверки 0.12.3: зарегистрированное подключение с приватным owner ACL, два actor без прямых grants, bearer/session/system OAuth/cookies, корректные chat/context headers и отсутствие широкого каталога Skills. Существующие `tests/native/test_resource_access.py` и паттерны `server_tools` дают основу проверок двух ролей.
- Disposable acceptance из **двух собранных exports без исходного пакета**: настоящий `run_command` с безопасным уникальным маркером и чтением тестового файла; обычный handoff; смешанная A(T)+B(без T)→C со своей привязкой; A+A с одним подключением; два пользователя; прямой доступ по-прежнему запрещён; Stop/deadline и поздний ответ. Для исполнения команды использовать настоящий заранее установленный Open Terminal или совместимый terminal backend, а не только fake callable. Детерминированный LLM-provider допустим для выбора Tools.
- Браузер: открыть основной и дочерний чаты, проверить сохранённый Tool call/result и отсутствие требования открытой пользовательской terminal pane. Существующие Tool/MCP/Skills и Inline Visualizer остаются регрессионными контролями. Фикстуры, временные файлы и конфигурация acceptance восстанавливаются после прогона.

## Risks / Trade-offs

- [Native терминальный API не разделяет ACL и исполнителя] → Держать минимальную адаптацию в одном месте и проверять обе роли на неизменённой 0.12.3; не обещать другие версии без прогона.
- [Общая среда может разделять файлы нескольких агентов/пользователей] → Сохранять выбранную оператором политику, явно документировать пределы и проверять headers; отдельная изоляция не добавляется этим change.
- [Приватное подключение доступно через агент, но его downloads недоступны пользователю напрямую] → Не менять grants; сохранить явные ограничения передачи артефактов и тестировать отсутствие обхода ACL.
- [Удалённая команда может продолжаться после Stop] → Прекратить локальное ожидание и новые вызовы, не повторять команды; документировать зависимость завершения процесса от backend.
- [Автоматические терминальные Skills расширили бы разрешённый каталог] → Сохранить `meta.skillIds` источником рабочих Skills; не импортировать каталог терминала или AGENTS.md автоматически.

## Migration Plan

1. Сохранить два текущих exports и конфигурации моделей/подключений. Внедрять сначала в disposable OWUI 0.12.3.
2. Пересобрать оба Function exports через `tools/build_functions.py` и обновить существующие записи с сохранением IDs, Valves и реестра. Без новых metadata все агенты остаются без терминала.
3. Настроить или проверить существующее серверное terminal connection, его доступность владельцу модели и параметры auth/context. Изменение ACL ресурса не должно выдавать прямой grant пользователю чата.
4. Задать `meta.lite_handoff.terminal_id` только выбранному агенту, сохранить остальные metadata и пройти acceptance. Затем включать остальные нужные привязки по отдельности.
5. Для отключения удалить/обнулить привязку: новые подготовки не подключают терминал, старые callables отклоняются guard. Для отката остановить активные запросы, восстановить два exports и исходные metadata; не удалять серверные файлы или общую среду.
