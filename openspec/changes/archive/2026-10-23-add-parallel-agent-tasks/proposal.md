# Proposal

## Why

Текущий Router передаёт один пользовательский запрос одному агенту. Для составной задачи, например двух независимых прогнозов и презентации по ним, нужны параллельная работа специалистов, получение обоих результатов и последующая передача итоговой работы третьему агенту в том же пользовательском чате.

## What Changes

- Добавить встроенный в Pipe инструмент `lite_parallel`: Router задаёт нескольким разрешённым агентам независимые задания и получает результаты после завершения всей группы. Выбор выполняется в обычном цикле Router через routing Skills, без отдельного LLM-классификатора.
- Сохранить `lite_delegate(agent_id)` для передачи дальнейшего ответа одному агенту в основном чате. После успешной параллельной группы Router может передать создание презентации агенту C; его входные данные включают результаты A и B и доступные файлы.
- Использовать тот же персональный реестр для routing-манифеста и `enum` обоих инструментов. Для каждой задачи повторно проверять доступ пользователя к модели, а доступ к настроенным ресурсам — с правами владельца соответствующей Workspace Model.
- Выполнять каждую задачу со своим системным промптом, параметрами, Tools, Skills, историей и MCP-соединениями. Рабочие инструкции и служебные цепочки агентов не объединяются.
- Разделить владельца ресурсов и пользователя исполнения во всех путях: Router, обычный handoff, параллельные работники и финальный агент. Базовые ресурсы и routing Skills Router загружаются с правами владельца публичной Router-модели; рабочие ресурсы агента — с правами владельца агента. Отдельные read-grants пользователя на Tools, Skills и MCP-подключения не требуются. Личность пользователя, его UserValves, персональная авторизация и права на чаты/файлы сохраняются.
- Переиспользовать штатный исполнитель сабагентов OWUI v0.12.3 через адаптер. Первой задачей реализации проверить настоящий параллельный запуск выбранных моделей, изоляцию ресурсов, полный результат и открытие дочерних чатов. До успешной проверки этот путь не считается поддержанным.
- Сохранять задачи в штатных внутренних дочерних чатах, скрытых из обычной истории. В основном чате показывать прогресс и ссылки «Открыть выполнение». При открытии удалённого выполнения сохранять штатный возврат OWUI на главную без уведомления и повторного запуска. Папка для служебных чатов не требуется.
- Явно передавать результаты между этапами как данные с указанием автора и доступными файлами. Не подставлять чужие Tool exchanges в собственную историю получателя и не скрывать усечение за успешным результатом.

Первая версия: одна ожидаемая параллельная группа на сообщение пользователя, затем самостоятельный ответ Router или один финальный handoff. Предлагаемые административные пределы — до четырёх задач и 300 секунд на группу; пользователь ими не управляет. При неполном результате финальный handoff блокируется, Router сообщает проблему без автоматического повторения действий.

Произвольный граф зависимостей, вложенная делегация, фоновое возобновление после окончания ответа, продолжение после перезапуска OWUI и изменение исходников OWUI не входят в это изменение.

## Capabilities

### New Capabilities

- `parallel-agent-tasks`: запуск группы независимых заданий разрешённым агентам, изоляция исполнения, ожидание результатов и их передача следующему исполнителю.
- `agent-task-inspection`: внутренние дочерние чаты, связь с исходным запросом, статусы и открытие сохранённой истории выполнения по ссылке.
- `model-bound-resource-access`: использование настроенных ресурсов модели без отдельных grants пользователя, с проверкой прав владельца, ограничением набора и сохранением пользователя исполнения.

### Modified Capabilities

- `user-agent-registry`: пригодность routing Skill проверяется с правами владельца публичной Router Workspace Model без отдельного read-grant пользователя; доступ пользователя к модели агента остаётся обязательным.
- `workspace-model-execution`: настроенные Tools/Skills/MCP проверяются с правами владельца Workspace Model, а доступ к моделям и пользовательским данным, личность исполнения, UserValves и пользовательская авторизация сохраняются у пользователя чата.

Базовый change `add-skill-based-handoff-router` синхронизирован и архивирован перед этим change. Соответствующие MODIFIED-дельты согласуют его основные specs с `model-bound-resource-access`. Новая операция расширяет прежнюю границу «без дочерних чатов» только для параллельных задач; существующий same-chat handoff сохраняется.

## Impact

- Затрагиваются `model_execution.py`, `runtime.py`, `history.py`, `registry.py`, `capabilities.py`, `skills.py`, подготовка Filter/Pipe и версия-зависимый `owui_adapter.py`; добавляются исполнение группы и явное разделение прав владельца ресурсов и пользователя исполнения.
- Используются внутренние APIs `open_webui.utils.subagents`, штатное хранение чатов и native Tool loop OWUI **0.12.3**. Их совместимость проверяется отдельно от модульных тестов.
- Сохраняется установка из двух самостоятельных Functions, работа внутри закрытого контура и отсутствие нового сервиса или библиотеки оркестрации. Схема БД и исходники OWUI не меняются.
- Потребуются обновления routing-инструкций, документации установки/контекста/приёмки, тесты изоляции и сквозная браузерная проверка на отдельной тестовой БД.
- Изменение не зависит от ещё не реализованного упрощения результата `lite_delegate` и не меняет его текущий формат.
- Автоматические изменения grants и миграция прав не выполняются. Требуются native проверки приватных ресурсов без grants пользователя, правильных UserValves/OAuth и обоих exports; прежняя приёмка не подтверждает новую политику доступа.
