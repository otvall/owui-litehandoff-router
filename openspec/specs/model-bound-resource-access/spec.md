# model-bound-resource-access Specification

## Purpose

Позволить пользователю работать с настроенными агентами через Router без отдельных разрешений на их Tools, Skills и MCP-подключения, сохраняя личность пользователя исполнения, изоляцию моделей и штатный доступ к пользовательским данным.

## Requirements

### Requirement: Model access enables configured capabilities

Пользователь с актуальным доступом к выбранной модели SHALL использовать её настроенные Tools, Skills, MCP-подключения и явно привязанный серверный терминал без отдельных read-grants на эти ресурсы. Доступ к ресурсам SHALL проверяться с правами владельца Workspace Model. Это правило SHALL применяться к Router, обычному handoff, параллельным работникам и финальному агенту; терминальная привязка SHALL поддерживаться только у агентов.

#### Scenario: User lacks direct resource grants

- **WHEN** пользователю разрешена модель A, её владелец имеет доступ к прикреплённым ресурсам, а пользователь не имеет их read-grants
- **THEN** A использует свои обязательные Tools и Skills, включая чтение файлов Skill и поиск
- **AND** отсутствие отдельных grants пользователя не исключает A из доступных адресатов

#### Scenario: Parallel workers and final agent use private resources

- **WHEN** пользователю разрешены A, B и C с приватными рабочими ресурсами, доступными их владельцам
- **THEN** A и B выполняют задания параллельно, а C после успеха группы использует свои ресурсы в основном чате
- **AND** каждый этап располагает только собственным набором возможностей

#### Scenario: Bound terminal is private to the model owner

- **WHEN** пользователь может запускать A, подключение T привязано к A и разрешено владельцу модели, но не пользователю напрямую
- **THEN** терминальные Tools A исполняются через T
- **AND** отсутствие отдельного grant пользователя на T само по себе не блокирует подготовку

### Requirement: Router resources use the public model owner

Базовые Tools и Skills из административных Valves и routing Skills реестра SHALL загружаться с правами владельца публичной Router Workspace Model. Выбор доступных адресатов SHALL сохранять проверку прав пользователя чата на модели. Отсутствие прямого доступа пользователя к routing Skill SHALL NOT исключать разрешённого агента.

#### Scenario: Routing skill is private

- **WHEN** пользователю разрешён A, а его активный routing Skill доступен владельцу Router без отдельного grant пользователю
- **THEN** A присутствует в персональном routing-манифесте и enum обоих управляющих Tools
- **AND** Router может прочитать routing Skill

#### Scenario: Agent model is denied

- **WHEN** пользователю запрещена модель B, хотя владельцу Router доступны её routing Skill и ресурсы
- **THEN** B отсутствует в манифесте и enum пользователя
- **AND** вызов по известному Model ID не запускает B

### Requirement: Resource authority is limited to server configuration

Права владельца SHALL применяться только к ресурсам, заданным в текущей серверной конфигурации модели или административных Valves Router. Клиентские поля SHALL NOT выбирать владельца, менять набор или расширять разрешённые Skills. Ограничение SHALL действовать для всех трёх Skill readers, native refresh и продолжений.

#### Scenario: Owner can read an unrelated skill

- **WHEN** A запрашивает через view_skill, read_skill_file или grep_skill_files Skill вне набора A, доступный владельцу модели
- **THEN** чтение отклоняется до получения содержимого
- **AND** знание ID не расширяет возможности A

#### Scenario: Client supplies another owner or resource

- **WHEN** пользовательский запрос, аргументы Tool или сохранённая история содержат подставленный owner ID либо неприкреплённый ресурс
- **THEN** система использует текущую серверную конфигурацию
- **AND** подставленные данные не предоставляют новые возможности

### Requirement: Execution identity and personal settings are preserved

Локальные Tools SHALL получать пользователя чата в __user__ и его UserValves. Пользовательские OAuth-токены и заголовки идентификации внешних вызовов, включая терминальные, SHALL относиться к пользователю чата. Проверка права владельца на подключение SHALL NOT заменять пользовательскую авторизацию внешнего сервиса или личные настройки данными владельца.

#### Scenario: Two users share one model owner

- **WHEN** U1 и U2 вызывают одну модель с разными UserValves
- **THEN** каждый локальный Tool получает личность и UserValves своего пользователя
- **AND** значения владельца и параллельного запроса не подставляются

#### Scenario: User authorization is missing

- **WHEN** владельцу разрешено MCP-подключение, но требуемая пользовательская OAuth-авторизация отсутствует у пользователя чата
- **THEN** возвращается штатная ошибка пользовательской авторизации
- **AND** токен владельца или другого пользователя не используется как fallback

#### Scenario: Concurrent terminal calls preserve execution users

- **WHEN** U1 и U2 одновременно запускают A с одним владельцем и терминальным подключением T
- **THEN** каждый терминальный запрос содержит `X-User-Id` своего пользователя, его session/OAuth-авторизацию и cookies при включённой их передаче
- **AND** настроенный общий bearer key остаётся серверной настройкой, а пользовательские credentials не смешиваются

#### Scenario: Terminal requires unavailable user authorization

- **WHEN** T требует session или OAuth пользователя исполнения, а необходимая авторизация отсутствует
- **THEN** терминальное выполнение возвращает ошибку авторизации
- **AND** токен владельца или другого запроса не подставляется

### Requirement: Resource owners and permissions are checked afresh

Владелец и ресурсы SHALL определяться по актуальной серверной конфигурации и проверяться при подготовке и применимых вызовах. Отсутствующий владелец, удалённый или запрещённый ему обязательный ресурс SHALL приводить к явной ошибке без частично подготовленной генерации. Подстановка другого владельца или администратора SHALL NOT выполняться.

#### Scenario: Owner cannot load a required resource

- **WHEN** обязательный Tool, Skill или MCP-подключение недоступны владельцу выбранной модели
- **THEN** агент не начинает генерацию с неполным набором
- **AND** ошибка не обходится правами пользователя, другого владельца или администратора

#### Scenario: Owner changes or access is revoked

- **WHEN** между подготовками изменился владелец модели, её attachments или права на обязательный ресурс
- **THEN** следующая подготовка использует актуальную конфигурацию и права
- **AND** старый callable или результат не восстанавливает утраченную возможность

#### Scenario: Routing skill is unavailable to its authority

- **WHEN** routing Skill отсутствует, неактивен или недоступен владельцу Router
- **THEN** соответствующий агент исключается из персонального реестра с диагностикой
- **AND** отсутствие прямого read-grant пользователя само по себе не считается такой ошибкой

#### Scenario: MCP function filter changes before continuation

- **WHEN** MCP-сервер предоставляет `lookup` и `other`, а администратор между подготовками одного запроса меняет `function_name_filter_list` с `lookup` на `other`
- **THEN** следующая подготовка публикует разрешённый `other` и исключает запрещённый `lookup`
- **AND** открытое соединение не закрепляет прежний разрешённый набор
- **AND** пустой после фильтрации набор обязательного подключения вызывает явную ошибку подготовки

#### Scenario: A prepared MCP callable loses function permission

- **WHEN** после подготовки MCP-функции администратор исключает её из `function_name_filter_list`, а затем вызывается сохранённый callable
- **THEN** вызов отклоняется до отправки операции MCP-серверу
- **AND** проверка доступа владельца к самому подключению не заменяет проверку допустимости функции
- **AND** разрешённые вызовы сохраняют пользователя исполнения и его авторизацию

#### Scenario: MCP filter changes preserve native matching rules

- **WHEN** администратор меняет допустимый серверный фильтр в строковом формате или формате списка, включая штатные шаблоны
- **THEN** публикация и последующие вызовы применяют одинаковые правила сопоставления Open WebUI 0.12.5
- **AND** отсутствие ограничивающего фильтра не превращается в запрет всех функций

### Requirement: Direct grants and user data access remain unchanged

Использование ресурса внутри модели SHALL NOT создавать отдельные grants пользователя на Tools, Skills, MCP или терминал. Чтение чатов, входных файлов и результатов SHALL сохранять штатные права пользователя чата. Права владельца модели SHALL NOT подменять эти проверки или предоставлять владельцу доступ к пользовательским данным.

#### Scenario: Private resource remains private outside model execution

- **WHEN** пользователь успешно использовал приватные Tools и Skills через разрешённую модель
- **THEN** прямые штатные запросы пользователя к этим ресурсам по-прежнему отклоняются без отдельного grant
- **AND** ресурсы не становятся доступными для самостоятельного подключения только из-за вызова через Router

#### Scenario: Owner can read a file denied to the execution user

- **WHEN** модель или результат указывает обычный OWUI файл, доступный владельцу модели, но запрещённый пользователю чата
- **THEN** файл не передаётся пользователю или следующему агенту с правами владельца

#### Scenario: Successful agent command grants no direct terminal access

- **WHEN** пользователь без прямого доступа к T успешно выполнил команду через A
- **THEN** штатный прямой доступ к T остаётся запрещённым этому пользователю
- **AND** система не открывает терминальную панель и не выдаёт grant ради загрузки терминального файла

### Requirement: Model bound access preserves platform restrictions

Новая политика SHALL сохранять глобальные запреты ресурсов, активность моделей и Skills, режим подтверждения Tools и текущие ограничения параллельного исполнения. Она SHALL NOT менять режим подтверждения, выдавать административную роль пользователю исполнения или требовать патча OWUI.

#### Scenario: Attached resources are globally disabled

- **WHEN** обязательные Tools или подключения выключены серверной настройкой OWUI
- **THEN** доступ владельца не включает их в обход настройки
- **AND** подготовка сообщает недоступность обязательного ресурса

### Requirement: MCP sessions end with their owning request

При окончательном завершении запроса система SHALL освобождать принадлежащие ему локальные MCP-задачи и соединения в пределах 5 секунд, включая Stop, отмену и ошибку. Зависшая операция SHALL NOT блокировать локальное закрытие. Закрытие SHALL быть идемпотентным; ожидающие вызовы SHALL завершаться результатом, ошибкой или отменой и SHALL NOT запускаться повторно автоматически.

#### Scenario: Stop interrupts a hanging MCP call

- **WHEN** обычный запрос Router или handoff-агента остановлен во время MCP-вызова, который не возвращает ответ
- **THEN** штатное завершение запроса запускает локальное закрытие без ручного действия пользователя или теста
- **AND** принадлежащие запросу MCP-задачи и соединения завершаются в пределах бюджета закрытия
- **AND** активный и ожидающие вызовы не остаются в бессрочном ожидании
- **AND** новые операции, скрытый повтор и продолжение генерации после Stop не запускаются

#### Scenario: Cancellation arrives during the permission check

- **WHEN** вызов отменяется во время асинхронной проверки серверной политики перед отправкой операции
- **THEN** после проверки отменённый вызов не отправляется в MCP transport
- **AND** это правило действует, пока владелец запроса ещё завершает свой `finally`

#### Scenario: Completion and failure release request sessions

- **WHEN** запрос окончательно завершается успехом либо ошибкой подготовки, провайдера или чтения потока
- **THEN** все созданные им MCP-сессии проходят тот же механизм локального закрытия
- **AND** повторный cleanup не закрывает ресурсы другого запроса и не скрывает исходную ошибку

#### Scenario: Tool continuations keep a live request session

- **WHEN** одно пользовательское сообщение проходит несколько генераций и MCP-вызовов в штатном Tool loop
- **THEN** промежуточный возврат Pipe или окончание отдельного provider stream не закрывает сессию продолжающегося запроса
- **AND** последующие допустимые вызовы используют пригодную сессию своего пользователя и модели

#### Scenario: Request ends while MCP connection is opening

- **WHEN** отмена запроса происходит до завершения открытия MCP-подключения
- **THEN** локальная попытка подключения и созданные ею ресурсы завершаются в пределах бюджета закрытия
- **AND** общий бюджет включает отмену открытия, ожидание SDK cancellation и disconnect без отдельных последовательных таймаутов
- **AND** ожидающая подготовка получает отмену или ошибку и не публикует частичный набор Tools

#### Scenario: Parallel cleanup remains isolated and repeatable

- **WHEN** Stop или deadline параллельной группы и окончание её дочернего запроса одновременно закрывают одну MCP-сессию
- **THEN** повторное закрытие безопасно и завершает ожидающие вызовы
- **AND** MCP-сессии других работников и пользователей остаются независимыми
- **AND** закрытие локального соединения не считается доказательством отката удалённой операции
